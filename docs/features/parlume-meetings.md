# Parlume meeting preview

How Parlume joins Teams meetings, answers, suggests, records and bills, for the people who run it.

- **Audience**: Project administrators and operators
- **Owner**: Engineering team

Parlume is a default-off, project-scoped way to invite the built-in Fabric Agent or a project-bound custom agent to a Microsoft Teams meeting by link. Each project has a **Parlume page** at `/projects/{id}/parlume`, linked from Meeting Digest: administrators invite and remove the bot there and see its spend, and readers review sessions and requests. While Parlume is joining, the page shows the invite's progress (invite sent, waiting in the lobby) and, until it is admitted, asks the viewer to admit **Fabric Parlume** from the Teams lobby if they are the organizer or a presenter, or to ask the organizer, with the time it stops waiting (the invite's time plus `PARLUME_LOBBY_WAIT_SECONDS`), then a live card with the elapsed time, agent, mode, spend so far (for administrators) and the session's latest requests. Below it, a Sessions and Requests panel lists sessions five at a time and filters requests by session and by question or action. The bot appears as **Fabric Parlume**, records and transcribes meeting audio, responds to “Hey Fabric,” “Hey Parlume,” or “Hey Fabric Parlume,” (also when transcription writes the opening “Hey” as “A”, “Eh” or “Uh”, as it did for “A Parlume: how many open features…” on staging) and saves a transcript and generated notes to the project. The join URL is sent to the meeting provider but is not stored in Fabric.

## Organization setup (Settings → Meeting assistant)

An organization configures its own meeting bot and voice at `/app/{organization}/settings/meeting-assistant`. The page exists only while `PARLUME_MEETINGS` is on for the organization. Members can read it; only owners and admins can change it or run its tests. Settings saved here take precedence over the operator's environment defaults, as described for each item below.

- **Meeting bot.** The organization's Attendee API key (stored encrypted, shown only as its last four characters), an optional Attendee URL for a self-hosted Attendee (https only; empty is `https://app.attendee.dev`), and the Teams sign-in mode: anonymous guest, sign in only when the meeting requires it, or always sign in. With a sign-in mode, an optional **Teams login group** (`OrganizationParlumeSettings.teamsLoginGroup`, letters, digits, spaces and `._@-`, at most 120 characters) is sent as Attendee's `teams_settings.login_group_name`, so several organizations can share one Attendee project and key, each with its own bot account in its own group; empty uses the project's default login. The URL, sign-in mode and login group belong to the organization's own key and apply only with it: without one, invitations use the operator's Attendee project as a whole, the operator's key is never sent to an organization's URL, and no organization's group is ever sent with the operator's key (`environmentAttendeeSettings` always has `teamsLoginGroup: null`), so one organization cannot pick another's account on the shared project. Removing the key removes them all, and choosing the anonymous mode clears the group. The saved key is only ever sent to the URL it was saved with: changing the URL, including back to the default, needs the key typed again, and **Test connection** tries a different URL only with a key typed alongside it. **Test connection** calls Attendee's read-only bot list (`GET /api/v1/bots`), creates no bot and costs nothing, and reports a rejected key apart from an unreachable instance. A URL that points at a private or internal address is refused unless the operator lists its host in `PARLUME_ATTENDEE_ALLOWED_HOSTS`.
- **Voice.** Parlume answers in its standard (classic) voice by default. The realtime voice runs only when this card names the Azure AI Foundry deployment that serves the realtime voice model (lowercase letters, digits, dots and hyphens); empty keeps the standard voice. The Azure AI Foundry resource itself is set in **Settings → AI providers**. An OpenAI key is never used for meeting audio: the realtime voice is minted only on the organization's Azure AI Foundry resource. **Test realtime voice** mints a short-lived realtime client secret on that deployment, the way a meeting does, but opens no session and bills nothing, and shows Azure's own refusal; with no deployment named it says Parlume uses its standard voice. Usage and pricing always record the model id, whatever the deployment is called.
- **External guests** (`OrganizationParlumeSettings.guestPolicy`, `NOTES_ONLY` by default, or `INTERNAL_ONLY`). What Parlume does about a guest an invitation names; see [External guests](#external-guests). Saving it is audited like the other Parlume settings.
- **Channel replies** (`OrganizationParlumeSettings.channelIntegrationId`). An `ORGANIZATION_SHARED` Microsoft integration the organization chose for Parlume's posts in Teams channel meetings; the card lists only active shared connections (`listOrganizationSharedIntegrations`), and saving refuses any other id. When a session's channel chat is first reconciled, `resolveWorkflowIntegrationPreferring` pins the chosen connection if it is still shared, active and accessible, and otherwise falls back to the inviter's own (`resolveWorkflowIntegrationForProvider`). A session keeps the connection it pinned. The account must be a member of each channel; Graph refuses a post otherwise. Saving is audited (`channelConnectionSet`).

Two things can only be done at the vendor, and Fabric cannot do them for you:

1. **The Teams sign-in account.** The Microsoft 365 account the bot signs in with is entered as the Teams bot login in the Attendee dashboard; Attendee has no API for it. Choose a sign-in mode in Fabric only once that account is set up there. Attendee signs in without a person, so the account must be password-only: no multi-factor authentication, no conditional access policy that requires a managed device or a second factor, and a Teams license. A tenant with security defaults on enforces multi-factor authentication for every account, so keep the bot's account in a separate Microsoft 365 tenant with security defaults off. For a shared Attendee project, put each organization's account in its own login group and enter that group's name in Fabric.
2. **The Azure realtime deployment.** The deployment must exist in the organization's Azure AI Foundry resource. Without it Azure refuses the mint, and Parlume keeps the classic voice; it never falls through to an OpenAI key.

The Parlume page lists whatever an invitation is still missing (the meeting bot, a voice provider, or the operator's media bridge), each with a link to the settings page that fixes it and back. A member who cannot change settings is told that an owner or admin can.

## Auto-join a linked meeting series

Parlume can join every occurrence of a recurring Teams meeting on its own, so nobody has to paste the link each time. It is set per linked series; there is no switch that joins every meeting.

**Turning it on.** Link the series to the project first: **Add meeting** lists the series from your Teams calendar over the chosen past range and the next 14 days, so a series can be linked, and auto-join turned on, before it first meets. In the project's **Meeting Digest** tab, choose **Configure meetings**. Each linked series has a **Parlume joins automatically** switch, shown while both `PARLUME_MEETINGS` and `MEETING_AGENDA` are on for the organization. Switching it on reveals the same choices as the invite card: **Read-only** or **Actions**, **Suggestions and recap**, and, while that is on, **Who sees suggestions** (`ProjectLinkedMeeting.parlumeAutoJoinSuggestionAudience`, copied into each session the series starts). A save that leaves the audience out keeps the series' current audience, so an older client cannot reset a team-only series to the meeting chat. Changing any of them saves straight away. The switch needs the same permission as inviting Parlume by hand (project administration). It is refused, with the reason and where to fix it, when you have no Microsoft connection (Settings → Integrations) or when Parlume is not ready to join meetings (a meeting bot in Settings → Meeting assistant, a voice provider in Settings → AI Providers, and the operator's media bridge). It cannot be switched on for a series whose syncing is stopped, because the scheduler skips those; resume syncing in the project's Settings → Meeting Transcript Sync first. A switch already on when syncing stops stays on but does nothing until syncing resumes, and the series says so.

**Whose calendar and permissions.** The person who turns the switch on becomes the series' enabler, and the panel names them. Fabric reads their Teams calendar, through their Microsoft connection in the project's organization, to find each occurrence, and every join runs as them: their project permissions, their voice provider and the built-in **Fabric Agent — this project**. The series must therefore be on the enabler's own calendar; an occurrence they were not invited to is not found and not joined. Anyone who changes the mode or suggestions later becomes the enabler instead. If the enabler loses project administration, joins stop and the series says so until someone turns the switch on again; if their account is deleted, the series asks to be turned off and on again.

**Timing.** A Temporal schedule (`parlume-auto-join-planner`) runs every five minutes. It reads each enabler's calendar once for the window from ten minutes ago to fifteen minutes ahead and matches occurrences to the linked series by join link. For each occurrence that is not cancelled it schedules one join about a minute before the start, or immediately if that has passed. It still joins up to ten minutes after the start, and leaves alone an occurrence that began longer ago. Each occurrence gets at most one session, however many planner runs see it. Just before joining, Fabric reads the enabler's calendar again for two minutes either side of the scheduled start, and joins only if the occurrence is still there, not cancelled and starting within a minute of that time. A cancelled occurrence is skipped; a moved one is skipped at its old time and planned again at its new one. Fabric then checks everything else again: the switch is still on and the series still syncing, both flags are on, the project is not in Read-only mode, the enabler still has permission, Parlume is ready, and the occurrence has no session yet. Last, right before the bot starts, `runParlumeAutoJoin` compares the time with the occurrence's start plus ten minutes: a join that arrives later, after a worker outage, a slow calendar read or the request's retries, sends no bot, and the series says "Parlume did not join a meeting of this series because its join came more than 10 minutes after the meeting started."

**One Parlume per meeting.** Inviting Parlume by hand with the link of a linked series records that series on the session. While any session of a series is in its meeting or on its way (pending, joining, active or leaving), auto-join does not send a second bot. The same holds for any meeting the organization has a live session in, found by the meeting the session stored (`findParlumeMeetingSessions`, which compares Teams links as the tag count does, so the web link and the invitation link of one meeting match). A second bot would count the first as a guest it cannot confirm, and both would leave. A second invitation from the same project sends no bot either: while the session there is pending, joining or active, `startParlumeMeetingSession` returns that session with `alreadyInMeeting: true`, so the invitation lands on the same Parlume page, with the settings the first invitation chose. An automatic join that finds one this way is skipped without a series notice. The invitation is refused, with "Parlume is already in this meeting." and what to do, while that session is leaving ("Its session is leaving; invite Parlume again once it has left.") or when it belongs to another project of the organization ("It was invited from another project."). The check runs in the transaction that creates the session, after a transaction-scoped advisory lock on the series and on the meeting, so of two invitations at once only the first creates a session and the second gets it back. Each session stores the meeting its link names as one key (`ParlumeMeetingSession.meetingKey`, from `parlumeMeetingKey`: the decoded Teams meeting or channel identity, otherwise the lower-cased join link), and the partial unique index `parlume_meeting_session_one_live_per_meeting` on `(organizationId, meetingKey)` for pending, joining, active and leaving sessions makes a second live session for one meeting impossible in the database too. Sessions that were live when the index was added got their key in its migration, the newest one where several named the same meeting; ended sessions from before it have none. The check cannot match a link that names no meeting (stored as none, with no key), nor a short `/meet/<id>` link Fabric could not resolve against a session stored with the full invitation link. A participant named like Parlume's bot still counts as a guest: a display name proves nothing.

**Read-only mode.** A bot joining a meeting counts as a write to a connected source, so auto-join does not join while the project is in Read-only mode, and the series says so. Calendar reads continue. Inviting Parlume by hand is not affected.

**The lobby.** An automatic join behaves like an invite: the organizer may have to admit Parlume from the lobby, and Parlume leaves after five minutes unadmitted, ending the session as **Not admitted from the lobby**. Because the join is asked for a minute before the start, an organizer who arrives up to four minutes late can still admit it. The enabler is told, as an inviter is (see **Join notices** under Boundaries). Auto-join records every occurrence without anyone inviting Parlume again, so tell the series' regular attendees before you turn it on. The switch shows the notice Parlume posts when it joins (below), and the series records who turned it on and when (`parlumeAutoJoinUserId`, `parlumeAutoJoinEnabledAt`); both are set again whenever someone saves the switch on, and cleared when it is turned off.

**Guests in an automatic join.** Just before joining, Fabric reads the occurrence's invitee list from the enabler's calendar. An invitee whose email domain differs from the enabler's counts as an external guest (with no enabler email to compare, every invitee does), and the session is marked `externalInvitees`. With **Internal meetings only** that occurrence is skipped; otherwise Parlume joins in notes-only mode for the whole session. The same read asks Microsoft Graph (`list_calendar_meetings` with `inviteeEmailDomain`, the enabler's domain) for the addresses of the invitees from the enabler's own domain, rooms and equipment left out. They travel lower-cased, each once, at most 200, through `confirmParlumeAutoJoinOccurrence` and `/api/internal/parlume/auto-join` (`inviteeEmails`), and `parlumeInternalInviteeEmails` (`parlume-guests.ts`) filters them again by the same rule before they are stored in `ParlumeMeetingSession.inviteeEmails`. No external invitee's address is read or stored, and the logs carry none. A manual invitation has no invitee list.

## Parlume's notice in the meeting

Once Parlume is admitted and its media stream is verified, it posts one notice in the meeting chat (`packages/utils/lib/parlume-join-notice.ts`):

> [P1] **Fabric Parlume (AI assistant) is in this meeting**
> I transcribe the meeting and write notes. I keep transcripts for 90 days, and notes until someone deletes them.
> To pause me, say or type "Parlume, pause". [Parlume page](…)

The link goes to the project's Parlume page (`buildParlumePageUrl`). `/api/internal/parlume/verify-stream` hands the bridge the text and a one-sentence spoken version (`joinNotice`), and the bridge posts it once per session, however often the stream reconnects (the bridge keeps it in its chat state). It posts the notice, and the guests notice for a guest named in the invitation, once the stream's audio arrives whole (`ParlumeAudioReadiness` in `party-cf/src/parlume-audio-ready.ts`): two seconds in which chunks covering at least 90% of the time arrived, timed by the `timestamp_ms` Attendee stamps on each chunk when it sends it. The audio of a newly joined bot arrives incomplete for about its first ten seconds (641 and 792 of about 1,000 chunks in staging sessions, with gaps up to 0.8 s), and a request said then went unheard, so the notice tells the meeting Parlume is in only once it can hear. It waits at most 15 seconds after the stream is verified (checked on each chunk, and on a bridge alarm set for that deadline, so it is posted even when no audio comes; a stream that reconnects before then keeps the earlier stream's notices and deadline, and an alarm whose access check ends the session posts none), and logs `parlume.bridge.welcome.audio_ready` with `waitedMs` and `whole`. When the chat shows the post, the bridge reports it to `/api/internal/parlume/join-notice` (`via: "chat"` with the post's tag), and Fabric records `ParlumeMeetingSession.joinNoticeAt` and `joinNoticeTag` the first time only. When the meeting gives Parlume no chat box, it says the spoken sentence instead of the usual "I can't write in this chat" line, once, and Fabric records the time with no tag (`via: "voice"`). A report Fabric could not take is sent again on the bridge's next delivery check. The notice is sent while a guest is in the meeting too, because it is the disclosure every participant must get: the post is exempt from the guests' chat rule, and the spoken sentence (`floor.speakJoinNotice`) is exempt from the guest condition of the speech gate only. The cap and a pause still keep it unsaid. "Parlume, pause" is announced in the notice; see [Stop, pause and resume](#stop-pause-and-resume).

## Who is in the meeting

Fabric checks every participant Attendee's `participant_events.join_leave` webhook reports (`forwardParticipantEvent` in `apps/web/app/api/internal/parlume/callback/guests.ts`, `confirmParlumeAttendee` in `packages/api/modules/projects/lib/parlume-attendee-access.ts`). It fails closed: a participant is refused unless every step confirms them.

1. A participant who joined without signing in (a Teams visitor or anonymous id) or whom Teams labels "(Guest)", "(External)" or "(Unverified)" (`isParlumeExternalParticipant` in `parlume-guests.ts`) is refused without a lookup. A display name exempts nobody.
2. A signed-in participant carries an `8:orgid:<Entra object id>` id, in `participant_uuid` or `participant_user_uuid`. No such id is refused.
3. The inviter is known without a Graph call: their object id is the account their own Microsoft Teams connection was made with (`WorkflowIntegration.settings.oderId`, Graph's `/me` id, from `resolveOwnWorkflowIntegrationForProvider`), so an expired token cannot refuse them.
4. Anyone else is looked up with the inviter's Microsoft Teams connection (`parlume_channel` operation `user`, `GET /users/{id}`, which the connection's `User.ReadBasic.All` allows for the inviter's tenant only), and matched to the Fabric user with that `mail` or `userPrincipalName`, verified. A failed lookup, someone from another tenant included, is refused.
5. That Fabric user, the inviter included, must hold `PROJECT_READ` on the meeting's project (`mayReadParlumeProject` in `parlume-attendee-standing.ts`).

The bridge is told twice about each join (`?action=guests`). Before the lookup, `placing: [{ id, pending: true }]`: while anyone is being checked, Parlume says nothing (the floor's gate closes and a reply in progress stops; chat posts other than notices are refused with `guests_present`). After it, `placing: [{ id, pending: false, userId }]` for a confirmed project reader, or the participant in `updates: [{ id, joined: true }]` for a refused one. A leave clears both. Each check carries `at`, when Attendee saw the join or leave (`timestamp_ms`). An outcome counts only for someone the bridge is still checking, and a check for a join seen before that participant's last leave (a delivery Attendee repeated after the leave) is ignored, so neither puts back someone who left; a later join is checked as a new one. For a refused join, Fabric then has Parlume leave (`requestParlumeLeave` with `ATTENDEE_NOT_AUTHORIZED` and a `notice`). The bridge posts the notice once, as one plain paragraph, before the leaving line (`?action=leaving` with `{ notice }`): "I'm leaving: I could not confirm that {display name} can see this project in Fabric. I answer only when everyone in the meeting can." Links and addresses are taken out of the name (`printableName` in `parlume-attendee-standing.ts`), and a name with nothing left prints as "a participant"; no address is ever printed or logged. Someone seen as the bot comes in, before the meeting chat showed the join notice (`joinNoticeAt` is unset), gets the notice another way: a post made then is lost. In staging, a notice the bridge posted 1.4 seconds after the stream was verified, and one posted through Attendee as the bot came into the call, never showed although Attendee took both, while every join notice, posted 11 to 15 seconds after the stream was verified, did. So the request claims the leave first (capture stops, and the bridge gets no notice), waits up to 30 seconds (`PARLUME_IN_CALL_WAIT_MS`) for Attendee to report the bot in the call (a `joined_*` state), since Attendee refuses a chat message from a joining bot, waits until the bot has been in the call for 15 seconds (`PARLUME_CHAT_SETTLE_MS`, counted from `joinedAt`, or from when Attendee reported it in the call), posts the notice through Attendee and leaves. A bot not in the call by then leaves without it, logged as `parlume.leave.notice_failed`. An open channel thread takes the bridge's post at once. A second request to leave while that request waits, such as another participant's check or the bridge's access check when the welcome is due, does not have the bot leave (`parlume.leave.notice_claimed_elsewhere`): the request that claimed the notice leaves after posting it. The participant callback allows 90 seconds for this.

**Before anyone is checked.** The verified stream tells the bridge that Fabric checks attendees (`checksAttendees` from `verify-stream`). From then on, Parlume answers nothing, and posts no recap or suggestion, until Fabric has confirmed at least one participant (`ParlumeGuests.open` in `party-cf/src/parlume-guests.ts`), and never while anyone is being checked. Whether Attendee reports the people already in the meeting when the bot is admitted has not been confirmed; if it does not, Parlume stays silent until someone joins and is confirmed. A recap that arrives while Parlume is silent waits on the bridge (`heldRecap`) and is posted once, as one paragraph, when Parlume may next answer (`postHeldRecap`); the Parlume page lists it, recorded before the post, and the chat route gives it its tag once the bridge sends it (`recap: true` on the post, `recordParlumeRecapTag`). The recap may tell the meeting what an earlier meeting of the series decided: its inputs (the previous session's notes or the series' synced transcript, never a confidential series, a confidential meeting or a raw Parlume transcript, and the project's changed work items) are project content any project reader can already open in Fabric, and everyone present is a confirmed project reader, so it reveals nothing they could not read.

**At each turn.** The bridge sends each turn the Fabric accounts of the confirmed attendees present (`attendees`) and the account of the confirmed participant who asked (`requester`, from `ParlumeGuests.userFor` for the speaker or chat sender). Before the turn runs, the turns route checks `PROJECT_READ` for each of them again, from the database alone (`findParlumeAttendeeWithoutRead`). If one has lost it, no turn runs, and Parlume leaves with the same notice, naming that person by their Fabric name. The turn then runs as the asker; see [Governance policy](#governance-policy).

A channel meeting is refused as a whole at its first join (`isParlumeChannelMeeting`): a bound channel thread, a `@thread.tacv2` join link, or a short link not yet resolved to an ordinary meeting. Everyone in the channel reads its chat, and the connection has no scope that lists a channel's members (no `ChannelMember.Read.All`), so the chat's readers cannot be checked: "I'm leaving: this meeting's chat belongs to a Teams channel, and I cannot check that everyone who reads it can see this project in Fabric."

Fabric records the first external guest as `ParlumeMeetingSession.guestJoinedAt`, and marks chat messages from a guest as from a guest. Attendee sends no join or leave for its own bot.

**A bridge that predates the checks** reads only `updates`, so for it the checks change nothing: a confirmed participant never appears there, and a refused one appears as a guest, as before. A bridge that predates `checksAttendees` sends no `attendees`, so its turns are not checked again.

## External guests

**Settings → Meeting assistant → External guests** (`OrganizationParlumeSettings.guestPolicy`) applies to a guest an automatic join's invitation names; a guest who actually joins is refused as above, whatever the policy:

- **Notes only** (`NOTES_ONLY`, the default). Parlume joins and keeps transcribing and writing notes. It posts, after the join notice, `[P{n}] **Notes only** · a guest is in this meeting` / "I keep notes. I do not speak or answer in this chat while a guest is here." Then, for the whole session: it does not speak, it posts nothing else in the chat (answers, a voice reply's detail, suggestions, the recap, proposals and their outcomes are refused with `guests_present` and stay on the Parlume page, and the request records why), it acts on no chat command a guest types, a guest's wake phrase starts no turn, and the realtime voice is not used.
- **Internal meetings only** (`INTERNAL_ONLY`). An automatic join whose invitation names a guest is skipped.

For an automatic join, the guests come from the invitation (above); such a guest counts for the whole session.

## Speaker marks

Each speaker is marked `member`, `guest` or `unknown` (`ParlumeSpeakerMark`, `parlumeSpeakerMark` in `packages/api/modules/projects/lib/parlume-guests.ts`). The mark comes from the same check that decides what the bridge is told (see [Who is in the meeting](#who-is-in-the-meeting)), so it cannot disagree with which requests the bridge takes:

- When `forwardParticipantEvent` has checked a participant who joined, it records them with `recordParlumeSpeakerMark` (`parlume-speaker-marks.ts`) before it relays the outcome: their Teams id goes to `ParlumeMeetingSession.memberSpeakerIds` when `confirmParlumeAttendee` returned a Fabric account (relayed as `placing … userId`), or to `guestSpeakerIds` otherwise (relayed in `updates` as a guest, whose wake phrase and typed commands other than pause the bridge refuses through `ParlumeGuests.isGuest`). A channel meeting's participants are not looked up and are marked guests.
- `parlumeSpeakerMark` reads a speaker's Teams id and name against those lists: `guest` when `isParlumeExternalParticipant` matches or the id is in `guestSpeakerIds` (a guest mark wins); `member` when the id is in `memberSpeakerIds`, or a request recorded its confirmed asker (`ParlumeMeetingTurn.requesterUserId`, which a realtime request carries without a speaker id); `unknown` otherwise, for a segment Teams gave no speaker, or a participant not checked (yet).
- The sign-in data used is what Attendee already sends and the repository parses: `participant_uuid` and `participant_user_uuid` (an `8:orgid:<Entra object id>` for a signed-in participant, `8:teamsvisitor:` or `8:anonymous:` for one who did not sign in) and `participant_name` from `participant_events.join_leave`, and `sender_uuid` and `sender_name` from chat messages. Attendee's payloads in the repository carry no tenant id; a participant from another tenant is a guest because the Graph lookup through the inviter's connection cannot resolve them. `participant_is_host` is not used.
- Finalization writes a guest's segments as `Name (unverified speaker): …` (`Unverified speaker: …` without a name). Parlume's own chat posts come back to the bridge under the bot's own sender id, which is anonymous (`8:teamsvisitor:…`) when the bot joins without signing in, so the check above would mark the bot a guest. The bridge therefore saves a chat line without its speaker id when it is the first echo of a post this session sent (`observeParlumeChatMessage` matched its tag to a post still waiting for confirmation) and its sender is named as the bot (`receiveMessage` in `parlume-chat-channel.ts`), and finalization writes a line with no id and no guest name label unmarked. Any other line under the bot's name keeps its sender id, so a participant who calls themselves "Fabric Parlume" keeps the guest mark. The one exception is a participant under the bot's name whose message carries the tag of a post Parlume has sent and the meeting chat has not yet shown: that message confirms the post and is saved unmarked, as the same message already confirmed the post's delivery. Bot lines with no tracked tag keep the bot's id and the mark: the leave notice Fabric posts through Attendee itself (`parlume-leave.ts`), and a post the bridge forgot after an unknown send result (`forgetParlumeChatPost`). The notes leave Parlume's posts out whatever their mark (see **Anchored notes**). The Parlume history procedure adds `speakerMark` to each request and does not send the Teams-id lists or `requesterUserId` to the page; `ParlumeSpeakerMark` shows an **Unverified speaker** badge in the Requests list and on the live card.
- Only the Teams id and the mark are stored. `purgeParlumeSessionContent` clears both lists with the segments, on a member's delete and in the retention sweep. Transcript readership is unchanged.

The turns route does not check the mark itself: the bridge refuses a guest's request before it becomes a turn, and the route already runs a turn with only the confirmed asker's access.

## When Parlume stops speaking on its own

The bridge lets Parlume speak only while the meeting is open (before the four-hour cap), it is not paused, and no guest is in (`floor.maySpeak()` in `party-cf/src/parlume-voice-floor.ts`). Every way to speak checks it: a sentence the worker sends (`say`), a reply the worker streams (`speak`), the bridge's own lines and a post read aloud (`speakLocally`), and the realtime voice before it starts or plays a response. When it stops being true while Parlume is speaking, the bridge stops the audio at once, drops what was queued (for the realtime voice, its queued audio, and the response is cancelled), and logs `parlume.bridge.speech.stopped` with the cause (`guest` or `cap`). The request in progress still finishes, and its answer goes to the Parlume page. A guest arriving mid-answer is the usual cause; the four-hour cap is the other, and ends speech differently (below).

**The four-hour cap** (`party-cf/src/parlume-cap-warnings.ts`). The alarm's one schedule in `onAlarm` also wakes 10 and 2 minutes before `hardStopAt`. Each warning posts one essential chat line (`**Leaving in 10 minutes** · …`, shown while a guest is in) and is read by `floor.speakNotice`, which waits for what Parlume is saying and a pause in the meeting and speaks only through `maySpeak()`. What was given is stored under `capWarnings` with its `hardStopAt`, so a restart never repeats one, and a cap Fabric moved starts over; an alarm that comes late gives only the later warning (`parlume.bridge.cap.warned`, with `skipped`). The access check, retry and chat wakes stay in the same `Math.min`. From 2 minutes before the cap (`parlumeCapClosing`), the bridge starts no spoken answer: `startTurn` sends every turn, queued ones included, with `replyChannel: "CHAT"`; a spoken wake goes through the floor's queue to get there; Flux's early end-of-turn starts nothing; and the realtime voice takes no new request (`answeringRealtime()`) and starts no response of its own. `onClosing` calls the engine's `closeForCap()`, which disarms it, and from then on `startNext` checks the host's `closing()` (the same `parlumeCapClosing`) and hands every response still queued to `answerInChat`: a request it held is asked of Fabric as a job (`realtime.request_to_chat`), a Fabric result, that job's included, is posted with `resultToChat`, the unheard rest of an answer cut short is posted as on a missed resume (`realtime.resume_to_chat`), and a tool's follow-up gives the Fabric result it carries and is otherwise dropped. When no request text was heard, a held request comes while a Fabric job is still running (the engine checks `jobs.size` as `ask_fabric` does, so it starts no second job for the turns route to refuse with 409 "Turn busy"; `realtime.request_to_chat` logs `busy` for a heard request only; a turn the chat route started is not in `jobs`, so a held request can still meet that 409, and an asker already asked to type gets no second line), or a moved follow-up's tools left the asker without an answer (a `read_chat`, a refused `post_to_chat`, a busy or invalid `ask_fabric`), the engine posts one line asking the asker to type the request, once per asker (`askToType`), which the chat route then answers (`realtime.tool_to_chat` logs `unanswered`). A held wake request is the bridge's partial transcript at the time it armed the voice, so Fabric may be asked a request cut short, and a request also heard by the bridge's final transcript can be answered twice in the chat. What is still heard is the two-minute warning itself and a response that started before the last two minutes. At the cap, `floor.finishAtCap(5_000)` lets the sentence being heard end: Aura playback starts no further sentence once `endAtSentence` is true (`playParlumeAuraSentences`), the outlet drains, and after at most 5 s `stop("cap")` clears the rest before the watchdog is called. The realtime voice has no sentence bounds: its audio already queued plays for at most those 5 s.

**The video tile** (`party-cf/src/parlume-status-tile.ts`). Attendee's `POST /api/v1/bots/{id}/output_image` takes `{ type: "image/png" | "image/jpeg", data: <base64> }` and shows the image as the bot's camera ([API reference](https://docs.attendee.dev/api-reference)). The bridge derives `LISTENING`, `PAUSED` or `ANSWERING` from the pause state and `floor.speaking || floor.isAnswering()`, re-reads it 400 ms after any speech or listening event and after a turn is accepted, every 2 s while answering (a realtime answer has no end event), and on each alarm, and posts a change to `/api/internal/parlume/status-image`. That route checks the service token and the `ACTIVE` session's bot, and sends the PNG with the organization's Attendee key (`outputParlumeStatusImage`, `packages/api/modules/projects/lib/parlume-status-image.ts`). The 640×360 images are drawn in code, a dot, the pause sign or a sound wave in the design system's dark-theme secondary, highlight and primary colours, with no text, so no font or image library is needed. The bot is created without an image: the first one, usually `LISTENING`, is posted the same way, 400 ms after `stream.verified`. The route logs `status_image.shown` for each image Attendee took and `status_image.failed` for one Attendee refused (a 502). It logs nothing for its other answers: 401, 400, 503 (no Attendee settings) and `accepted: false` (the session is not `ACTIVE`). The bridge logs `tile.failed` for any answer that is not a 2xx and sends that state again on the next change or alarm; it counts an `accepted: false` answer as shown and does not send that state again. Whether Teams shows the image on the tile, and how fast, has not yet been checked in a staging meeting. The spoken join notice is the one exception to the guest condition: it is said while a guest is in, and a guest arriving does not cut it (`speech.stopped` then carries `keepsJoinNotice: true`).

**Seeing what happened.** Sessions an auto-join started appear on the Parlume page's sessions list marked **Auto-joined · {series}**. When a join could not happen, the series in Configure meetings shows why, with a link to the settings page that fixes it: a Microsoft connection that needs reconnecting, a calendar that could not be read (retried every five minutes, or, just before a join, three times ten seconds apart before that occurrence is skipped), Read-only mode, Parlume not being ready, the enabler's lost permission, or the meeting provider's own reason for refusing the bot. A cancelled or moved occurrence, or a meeting Parlume is already in, is skipped without a notice. The notice clears on the next successful join, when the switch is set again, or, for a calendar problem, as soon as the calendar can be read. The web API and worker log every decision as `parlume.auto_join.*` events.

## Stop, pause and resume

**One stop.** Every stop goes through `floor.stop(cause, actor)` in `party-cf/src/parlume-voice-floor.ts`. The cause is a closed union (`ParlumeSpeechStopCause` in `party-cf/src/parlume-stop.ts`): `cap` and `guest` are the speech gate's, `voice` is a stop said aloud, `chat` is a typed stop, `page` is the Parlume page's **Stop speaking**, and `pause` is a pause. The stop acts while Parlume speaks, while the outlet still plays audio it already received, and while an answer is still being prepared. Before its first await it clears every outlet, ends a reply still arriving in parts, and, for the realtime voice, sends `response.cancel` and `conversation.item.truncate` to what the meeting heard. It does this after `response.done` too, while the outlet still drains: the cancel then carries no response id, and the engine ignores the `response_cancel_not_active` error it may get back. Each stop logs `parlume.bridge.speech.stopped` with `sessionId`, `voiceGeneration`, `cause`, `actorId`, `speaking`, `stopped`, `keepsJoinNotice`, `detectMs` and `confirmed` (a spoken stop's, see **Spoken stop**; `null` for any other), and returns `{ stopped, asker }`. While a post is read aloud, `asker` is whoever asked for the read, a typer included.

**Which stops end the turn.** `voice`, `chat`, `page` and `pause` end the answer, and only the current answer. The bridge moves to a new voice generation, keeps the stopped one as `stoppedThrough` in Durable Object storage, and posts `/api/internal/parlume/interrupt` with `stop: { cause: "VOICE" | "CHAT" | "PAGE" | "PAUSE", by }`. Fabric sets the turn to `STOPPED`, with `ParlumeMeetingTurn.stopCause` and `stoppedBy` (the display name), and cancels its workflow. The bridge silences the answer before it reports the stop, so the worker can finish and record the turn `COMPLETED` first; in a staging meeting, a typed stop and a page stop both ended that way. When no turn is active, Fabric therefore sets the latest `COMPLETED` turn of the stopped generation to `STOPPED` when it finished in the last 30 seconds (`STOP_RACE_MS` in the interrupt route). The meeting-turn activity heartbeats every second under a 15-second heartbeat timeout (`packages/temporal/src/workflows/parlume-meeting-turn.ts`), so the cancellation reaches it with its next heartbeat and aborts the agent run. The timeout leaves room for a busy worker; the delay is not heard, because the bridge has already silenced the answer and refuses its posts. The activity runs once (`maximumAttempts: 1`), and Temporal never retries a cancelled activity, so a stopped or timed-out turn is never answered twice. A re-run would also find the turn no longer `PENDING` and do nothing. The bridge refuses any chat post the worker still sends for a stopped generation (`{ sent: false, reason: "stopped" }`); answers, the rest of a spoken answer, proposals and `post_to_meeting_chat` posts all carry their `voiceGeneration`. A change a member already confirmed runs apart from the turn and is not stopped. `cap` and `guest` keep the older behavior: the turn runs on and its answer stays on the Parlume page.

**Typed stop.** A whole chat message that is a stop phrase runs `floor.stop("chat", sender)` (`party-cf/src/parlume-chat-commands.ts`). Nobody stops Parlume without telling Parlume to stop, so the phrases are split. Unaddressed, only `stop`, `stop talking` and `stop speaking` count (`BARE_STOP`, with an optional "please" or "ok"). Addressed by an @mention, "Parlume, …", a wake phrase or a private message, the full list counts (`ADDRESSED_STOP`): also `wait`, `cancel`, `hold on`, `never mind`, `not that`, `that's enough`, `be quiet` and a few more. An unaddressed "wait" or "cancel" is usually said to people and is ignored. When something was stopped, the chat gets one notice, `**Stopped** · {actor} stopped the answer for {asker}`, and nothing else from that turn. A guest's typed stop is ignored, as with every other command from a guest.

**Spoken stop.** Talk over Parlume never stops it, its requester's included: only a stop phrase does, in either voice (`ParlumeSpokenStop` in `party-cf/src/parlume-spoken-stop.ts`, with `classifyParlumeStop` in `party-cf/src/parlume-barge-in.ts`). The classifier returns `stop`, `stop-then-request` ("Parlume, stop. What is next?", which goes on to ask the rest) or `none`. Addressed by Parlume's name or a wake phrase, the long list counts (`ADDRESSED_STOP`: `stop`, `wait`, `hold on`, `never mind`, `cancel`, `that's enough`, `be quiet` and more), in a partial or a final transcript. Unaddressed, only a strong stop said as the whole final utterance counts (`STRONG_STOP`: `stop`, `stop talking`, `stop speaking`, with "please", "ok" or "okay"), from anyone, a speaker Teams has not named included: speaker labels arrive late, and "wait" or "hold on" are common in side talk. "Parlume, pause" and "Parlume, stop listening" are a pause, never a stop. Words that match the sentence Parlume is saying, two words or more, are its own voice heard back and are ignored. An addressed stop in a Flux partial holds Parlume at once: every outlet pauses (`ParlumeAudioOutlet.pause()`), and the bot plays out only its 200 ms lead. The final transcript decides: a stop runs `floor.stop("voice", speaker)`, anything else resumes the same audio (`resume()`, with the 300 ms lead-in again after a gap) and logs `speech.stop_withdrawn`. With no final within 4 s, the stop stands. `detectMs` in `speech.stopped` is from the end of the stop's words to the hold, or to the stop when nothing held it; `confirmed` says a final confirmed a hold. A stop is never asked as a request of its own. Flux's early end-of-turn can still start a request; a guess Flux takes back ends that request only until its answer's first audio frame, after which only a stop ends it. A Teams mute does not stop Parlume: Attendee reports no microphone state, so the user guide points to the stop phrases, the typed stop and the page button.

**Pause.** "Parlume, pause" or "Parlume, stop listening", said or typed, and the page's **Pause listening** button pause listening. Anyone may pause, guests included, because a pause only makes Parlume take in less. A pause (`party-cf/src/parlume-live-controls.ts`) closes the gate before its first await, runs `floor.stop("pause", actor)`, forgets a bare wake phrase and disarms the realtime voice, and posts `**Listening paused** by {actor}` as an essential notice. While paused, the bridge drops meeting audio before it reaches Flux or the realtime voice, keeps no transcript, chat segment or request, does not report idle silence, and gives the join notice no voice. The Flux socket stays open; its gap filler sends silence for at most 30 seconds. The paused state lives in Durable Object storage under `listening`, so it survives a restart.

**Resume.** Only the page's **Resume listening** button resumes. It posts `**Listening again** · resumed by {actor}`.

**What Fabric records.** The bridge reports each pause and resume, in order, to `/api/internal/parlume/listening` (`{ sessionId, botId, paused, by, at, offsetMs }`), and retries one Fabric did not take on the next alarm. Fabric sets or clears `ParlumeMeetingSession.pausedAt` and `pausedBy`, which the page's live card shows, and stores a transcript marker: a `ParlumeMeetingSegment` with `source: EVENT` at the offset where it happened. The saved transcript shows it as `[Parlume] Listening paused by {actor}.` The bridge logs `parlume.bridge.listening.paused` and `listening.resumed` with `actorId`, and `listening.report_failed` when Fabric is unreachable.

**The page controls.** `projects.parlume.stopSpeech`, `pauseListening`, `resumeListening` and `continueReading` (`packages/api/modules/projects/procedures/parlume/live-controls.ts`) need `PROJECT_READ`, the same as opening the page: each only stops Parlume or lowers what it takes in, restores a pause, or reads the next chapter of a post Parlume is already reading. Each requires an `ACTIVE` session of the project, calls the bridge's `?action=stop-speech|pause|resume|continue-reading` with the member's user id and name, and records `project.parlume.speech_stopped`, `listening_paused`, `listening_resumed` or `reading_continued` in the audit log under the member's account. `continue-reading` answers `{ changed: false }` when no chapter waits, and the page says "No part of a post is waiting to be read." A bridge that does not answer gives "Parlume's media bridge did not answer. Try again."

**Requests that wait.** The voice floor owns one request queue (`ParlumeRequestQueue`, `party-cf/src/parlume-request-queue.ts`) for everything that arrives while Parlume speaks, reads or prepares an answer in either voice: a spoken request (endpointed as usual, then queued with `PendingTurn.queued`), a typed request, and a `say`/`go` read with an asker. None of them calls `interrupt()`; Fabric refuses a concurrent turn with 409 anyway. The queue is stored under `requestQueue` in Durable Object storage, so a restart keeps it, and holds at most five entries, one per asker key (`parlumeSpeakerKey`: participant id, else lower-cased name; a speaker the meeting cannot name is exempt). A refused entry gets one chat notice (`**Not queued** · …`), and an entry older than two minutes is dropped with `**Not answered** · …` once Parlume is free. The next entry starts when the floor is free (`occupied()`: classic answering, a read in progress, or `realtime.holdsFloor()`), after up to 1.5 seconds for an open Flux turn to end (`noteHeard`), or, after a stop, once two seconds pass with no transcript (`afterStop`). A pause or a closed speech gate clears the queue. A turn that waited opens with its asker's first name: the classic voice prefixes the reply's first `/say` sentence, a read prefixes its text, and the realtime engine adds a system instruction. The queue logs `queue.added`, `queue.refused`, `queue.started`, `queue.expired` and `queue.cleared`. Notices and the join notice are read without an asker and never wait in the queue.

The realtime engine keeps its own response queue, in order, with the requester stored per response, so `requesterKey()` names who asked for the answer being heard. A wake response starts as soon as the previous response is done; a chat or tool response waits up to 1.5 seconds for OpenAI's turn detection to report a pause; a Fabric result waits for a pause and, after 60 seconds, is posted to the chat (`realtime.result_to_chat`). A typed request answered in the chat never interrupts the floor; in a realtime meeting it waits in the floor's queue while the realtime voice holds the floor, and a typed request asking for a spoken answer goes to the realtime engine's own queue.

**Spoken budget and chapters.** Parlume speaks at most 45 seconds at a time (`PARLUME_SPOKEN_BUDGET_SECONDS`). A post read aloud is split by `ParlumeReadChapters` (`party-cf/src/parlume-chat.ts`) into chapters that end at sentence ends and fit the budget with the continue hint ("There is more. Ask me to continue, or type continue in the chat.") and an asker's name. The next chapter waits five minutes from the last chapter read, and is read on "Parlume, continue" (a final transcript, only while a chapter waits), a typed `continue`/`go on`/`keep going` (addressed or not), or the page's **Continue reading**. A new read replaces the waiting chapters; a stop keeps them. The realtime session's `max_output_tokens` is set in the bridge's `session.update` from `OUTPUT_AUDIO_TOKENS_PER_SECOND × 45 s` plus a text allowance (`party-cf/src/parlume-realtime.ts`); the rate is provisional until measured on staging. Each response logs `realtime.done` with `status`, `reason` (`status_details.reason`), `outputAudioTokens`, `outputTextTokens`, `audioBytes` and `audioMs` (bytes / 48 at 24 kHz PCM16 mono), with no transcript text, for that measurement. A response that ends `incomplete` for `max_output_tokens` logs `realtime.capped` and posts one `**Cut short** · …` line.

## Speech telemetry

The bridge logs how Parlume's speech goes in both voices, and keeps totals per meeting that Fabric stores and logs for alerting. Bridge logs stay in Cloudflare Workers Logs; only the web app's logs reach App Insights, so alert rules read the web event `parlume.speech_health` below, and the bridge events are for tracing one meeting. Every field is an id, a count, a duration in milliseconds or a closed label: no transcript text and no names (an actor is an id).

**Bridge events** (`parlume.bridge.*`; every one also carries `sessionId`, and the realtime voice's `botId`):

| Event | When | Fields |
|---|---|---|
| `speech.started` | A voice starts a reply: a classic playback or read takes the floor (`takePlayback` in `parlume-voice-floor.ts`), or the realtime voice sends `response.create` | `voice` (`classic` or `realtime`), `route` (`aura` for a reply the worker sends as sentences, `pcm` for its own audio, `aura-bridge` for a read or notice, `realtime`), `kind` (realtime only: `wake`, `chat`, `tool`, `result` or `resume`; the later events give `null` for a classic reply), `voiceGeneration` |
| `speech.first_audio` | That reply's first audio reaches the meeting's outlet | the reply's `voice`, `route`, `kind`, `voiceGeneration`, and `firstAudioMs` from `speech.started` |
| `speech.ended` | The meeting stopped hearing it: the outlet played it out, or dropped the rest | the first reply's `voice`, `route`, `kind`, `voiceGeneration`; `replies` (a reply queued before the one before it played out is heard in the same stretch and ends with it); `outcome`; `cause` and `actorId` of a stop (otherwise `null`); `heardMs` (speech queued less speech dropped, to within the 300 ms lead-in), `droppedMs`, `underrunMs` (starvation: the time after the 8 s gap allowance ran out, when the bot may mute), `waitMs` (the silence that covered a planned wait for the reply's next part, such as a tool call), `speakingMs` (first audio to end), `stallResets` |
| `speech.stopped` | Every stop (see **One stop**) | `voiceGeneration`, `cause`, `actorId`, `speaking`, `stopped`, `keepsJoinNotice`, `detectMs`, `confirmed` |
| `speech.resumed` | Speech goes on after a socket swap or a restart (classic, `cause` `socket_swap` or `restart`, with `gapMs`, `lostMs`, `sentences` for a read), or after a realtime session's end (`cause` `dropped`, `rotation` or `restart`, with `kind`, `gapMs`, `lostMs`, `heardChars`) | as listed |
| `outlet.underrun` | A reply that starved: its audio stayed out past the gap allowance, once at its end. A covered wait alone does not log it | `voice`, `route`, `kind`, `voiceGeneration`, `underrunMs`, `waitMs`, `speakingMs` |
| `outlet.stall_reset` | A reply in which a late timer restarted the outlet's clock, once at its end (`warn`) | `voice`, `route`, `kind`, `voiceGeneration`, `stallResets` |
| `realtime.capped` | A realtime answer reached the 45-second output limit | `audioMs` |
| `engine.fallback` | The realtime voice was given up for the classic one (`warn`) | `botId`, `engine` (`classic`), `reason` (`connect_failed` or `reconnect_failed`) |

`outcome` is `completed` (played to its end), `stopped` (a stop or a closed gate dropped it), `capped` (the realtime voice reached its limit), `failed` (Aura failed a sentence twice), `dropped` (the outlet dropped it with no stop, such as when the bot's socket went away without a replacement) or `silent` (a reply that sent no audio: a realtime response that only ran tools, or a playback refused before any audio). A `silent` or a `failed` reply that sent no audio ends when its voice is done with it (`speech.synthesized`, `speech.played` or `realtime.done`), or when the same voice starts its next reply.

**Counters.** `ParlumeSpeechHealth` (`party-cf/src/parlume-speech-health.ts`) builds the totals from these events: the Durable Object's `log` for the voice floor and the realtime voice goes through `observing`, so a counter moves exactly when its event is logged, and the meeting outlet tells it how each reply played (`queued`, `ended`). The totals are kept in Durable Object storage (`speechHealth`), so a restart keeps them, and the purge deletes them with the rest. They count from the start of the meeting:

| Counter | Counts |
|---|---|
| `replies` | `speech.ended` with audio |
| `speakingMs`, `underrunMs`, `waitMs` | the sum of their `speakingMs`, `underrunMs` and `waitMs`. A bridge from before `waitMs` counted covered waits in `underrunMs`, and its reports read as `waitMs` 0 |
| `stallResets` | the sum of their `stallResets` |
| `stops`, `slowStops`, `worstStopMs` | stops said aloud while Parlume was audible (`speech.stopped` with `cause: voice`, `speaking` and `stopped`); of them, those after which Parlume was audible for more than 1.5 s; and the slowest. The time to silence is `detectMs` plus the 200 ms lead the bot still plays (`PARLUME_OUTLET_LEAD_MS`) |
| `resumes`, `failedResumes` | `speech.resumed`, and `realtime.resume_missed` |
| `capped` | `realtime.capped` |
| `fallbacks` | `engine.fallback` |
| `auraRetries`, `auraRetryFailures` | `aura.retry`, and those with `played: false` |

**The speech-health route.** On every alarm, on the access-check cadence (once a minute while the meeting runs), and before Fabric's purge, the bridge posts the totals to `POST /api/internal/parlume/speech-health` (`apps/web/app/api/internal/parlume/speech-health/route.ts`) as `{ sessionId, botId, totals }`, only when they changed since Fabric last took them; a report Fabric did not take is retried on the next alarm (`speech_health.report_failed`). The route is authorized with the service secret (`X-Agent-Service-Token`) like its siblings and validates the body with zod; it answers `404` for a session the bot is not on. The totals only grow, so the route keeps the larger of the stored and the reported value of each counter: a repeated or late report changes nothing. It stores them on `ParlumeMeetingSession.speechHealth` (JSONB, migration `20261121135000_parlume_speech_health`).

**The web event for alerting.** Each report logs one `parlume.speech_health` line (`Properties.event`, `component: parlume`) with `sessionId`, `botId`, and for every counter above what this report added (`replies`, `speakingMs`, `underrunMs`, `waitMs`, `stallResets`, `stops`, `slowStops`, `resumes`, `failedResumes`, `capped`, `fallbacks`, `auraRetries`, `auraRetryFailures`), except `worstStopMs`, which is the meeting's slowest stop so far. Sum the deltas over the alert window; a repeated report adds zeros. The rules this supports:

- a stop said aloud that left Parlume audible past 1.5 s: `sum(slowStops) > 0`, with `max(worstStopMs)` for how slow;
- underrun over speaking time above 2 percent: `sum(underrunMs) / sum(speakingMs) > 0.02`, over enough speaking time to mean something. `waitMs` is not part of it: a covered wait is heard as a pause, not a cut;
- failed resumes: `sum(failedResumes) > 0`;
- realtime fallbacks: `sum(fallbacks) > 0`;
- Aura retries: `sum(auraRetries)` and `sum(auraRetryFailures)`, the second being a sentence nobody heard.

**How the web events reach App Insights.** The web app's log sink forwards warn, error and fatal lines, and an info line only when its properties carry `forward: true` (`LogSinkRecord` in `packages/logs/lib/logger.ts`). `parlumeLog` sets it on every Parlume line, so the lifecycle events (`parlume.session.started`, `session.finalized`, `leave.requested`, `session.swept`) and `parlume.speech_health` reach the web app's Application Insights resource as `traces` from `fabric.web`, info lines at Information severity. There every field is a string (`customDimensions["slowStops"]` is `"1"`), so a query converts numbers with `tolong`. The sink samples each event at 20 records a minute per web instance. The Temporal worker has no such sink: its `parlumeActivityLog` lines are in the container console logs (`ContainerAppConsoleLogs_CL`) only. Finalization and the stranded-session sweep log from the web app. The Parlume alert rules (join failure rate, stream errors, sessions stuck in LEAVING and the speech rules above) read these traces.

The Parlume page shows, on each stopped request, how it was stopped and who stopped it: "stopped by voice (Dev Example)", "stopped in the chat", "stopped on the Parlume page" or "stopped by a pause", from `ParlumeMeetingTurn.stopCause` and `stoppedBy` (`requestStateLabel` in `apps/web/modules/saas/parlume/lib/parlume-view.ts`). The name is the one the meeting gave and Fabric already stores, with the same readers as the request's speaker: anyone who can read the project, a confidential meeting's requests withheld as before.

## The live page: transcript, page questions and suggestion buttons

**Live transcript.** `projects.parlume.transcript` (`GET /projects/{projectId}/parlume/sessions/{sessionId}/transcript`, `procedures/parlume/transcript.ts`) needs `PROJECT_READ` and then `canReadParlumeTranscript`, the readers in [Transcript access](#transcript-access-deletion-and-retention). It returns the newest 200 segments (`PARLUME_LIVE_TRANSCRIPT_LINES`), oldest first, with their source (`SPEECH`, `CHAT`, `EVENT`); every other reader, and every reader once `transcriptDeletedAt` is set, gets `{ readable: false, segments: [] }`. The page polls it every 10 seconds while the session is live, and only when `canReadTranscript` is true.

**Page questions.** `projects.parlume.ask` (`POST …/sessions/{sessionId}/ask`, `procedures/parlume/ask.ts`) needs `PROJECT_UPDATE`, and for a confidential session `mayReadParlumeSessionContent`. It creates a `ParlumeMeetingTurn` with `replyChannel: PAGE`, `requesterUserId` the member, and a `page:<uuid>` dedupe key, and starts `parlumeMeetingTurnWorkflow` with a read-only acting grant minted for the member and `withConfidential: true` (the asker reads the confidential part). It does not go through the bridge, and it never claims `session.activeTurnId`: a page turn does not block the voice, and the interrupt route, which acts on the active turn, never stops it. It refuses a session that is not `ACTIVE` (`NOT_FOUND`), a confidential command (`BAD_REQUEST`; the page control applies it), and a member's second page question while the first is `PENDING` or `RUNNING` within five minutes (`CONFLICT`). In the worker, a `PAGE` turn skips the voice-generation check, gets the `PAGE` turn instructions, has no `post_to_meeting_chat` tool, posts no proposal in the chat (the proposal waits on the page), and completes with its answer stored on the turn only. Its audit row records `source: "page"`. Finalization reads turns with `replyChannel: { not: "PAGE" }`, and actions of those turns only, so a page question and what it proposed never reach the saved transcript, the notes or the next meeting's recap. The interrupt route's `markStoppedAfterFinish`, which marks the turn a stop raced as `STOPPED`, also skips `PAGE` turns.

**Suggestion buttons.** `projects.parlume.saySuggestion` and `projects.parlume.dismissSuggestion` (`POST …/suggestions/{suggestionId}/say` and `…/dismiss`, `procedures/parlume/suggestions.ts`) need `PROJECT_UPDATE` and `mayReadParlumeSessionContent`. **Say** takes an `ANSWER` or `MISSED_QUESTION` of an `ACTIVE` session, refuses with `CONFLICT` while `externalInvitees` or `guestJoinedAt` is set, and posts `?action=read-aloud` with `{ text, suggestionId, actor }` and the service secret to the bridge (`sendParlumeReadAloud`, `lib/parlume-page-controls.ts`); the bridge answers `{ spoken }`. **Dismiss** sets `ParlumeSuggestion.dismissedAt` and `dismissedById`, and the suggestions list leaves dismissed ones out. Each records `project.parlume.suggestion_spoken` or `project.parlume.suggestion_dismissed`. `listSessions` returns `guestsPresent` so the page turns Say off. `verify-stream` hands the bridge the session's `pageUrl`, which a suggestion post links as `[Say it](<pageUrl>?suggestion=P<n>)`; the page highlights that suggestion. On the bridge, `?action=read-aloud` is a page control (`ParlumeLiveControls.readAloud`): it needs the member `actor` and a `text` of at most 2,000 characters, and reads it through `floor.readAloud`, at once when Parlume is free or behind what waits in its queue. It answers `{ spoken: false }` while `maySpeak()` is false (paused, a guest in, past the cap) or no bot socket is live, and logs `parlume.bridge.page.read_aloud` with the suggestion id. The bridge keeps `pageUrl` in its `bridge` state (an http or https URL of at most 2,000 characters). A suggestion post stays one plain paragraph, with the link as its one action; `parlumePlainChatHtml` links a `[title](address)` link and nothing else.

**Notes-ready notice.** `parlumeNotesWorkflow` calls `notifyParlumeNotesReady` (`packages/temporal/src/activities/parlume-notes-ready.ts`) after the notes activity returns, behind `patched("parlume-notes-ready-notice")`, on the project-operations queue with one attempt and a one-minute timeout; a notice that fails does not fail the run, and a run whose notes activity failed never reaches it. The activity sends only when the notes are `COMPLETED` (a last attempt that recorded `FAILED` sends nothing), claims `ParlumeMeetingSession.notesNotifiedAt`, and sends each internal transcript reader (the inviter and the members in `inviteeEmails` who still read the project; for a confidential session only those in `attendeeUserIds`) a `PARLUME_NOTES_READY` notification in the `PROJECT` category and a `parlumeNotesReady` email with the Parlume page link. A reader whose project notifications are off (`isCategoryEnabled(…, PROJECT)` false) gets neither: the opt-out covers the email too. Neither carries the notes. Guests have no Fabric account on the project and get nothing. Nothing clears `notesNotifiedAt`, so a session is told at most once, and **Regenerate notes** never sends a second notice. The activity does not check whether the run regenerates: a regenerated run sends the first notice whenever `notesNotifiedAt` is still null, both when the first notes failed and when they finished before this notice existed.

## Replaying a meeting through the bridge

A replay fixture (`party-cf/src/fixtures/parlume-replay/*.json`) holds a meeting's audio timeline, the Flux events with the time each arrived, and the participant speech updates, all in seconds from the start of the audio, plus the questions the meeting asks Parlume. `replayMeeting` in `party-cf/src/parlume-replay.mts` plays one through the real bridge with the test harness's fake bot, Flux, Aura and Fabric, ten times faster than it happened (the bridge's own timers still run in real time), and returns a scorecard: the requests that reached Fabric with their text and attributed speaker, false wakes (requests from a speaker who asked nothing), missed questions, interrupts, and for each request the milliseconds from the Flux end-of-turn event that started it to the request leaving the bridge. That delay is the bridge's own time and excludes Fabric. `parlume-replay.test.mts` runs with the rest of the bridge tests (`node --test --experimental-strip-types "src/*.test.mts"` in `party-cf`) and replays two fixtures. `two-speakers.json` is a recording of real Flux hearing two synthetic Aura voices: QA Example asks "Parlume, what is the status of F-12?" while Dev Example is still finishing a sentence. In each of three recordings on 2026-10-27, Flux heard both speakers as one turn ("…before we call it done. Parlume, what is the status of f twelve?"), so the wake phrase was not at the start of a turn. The bridge used to miss the question; it now wakes on "Parlume" opening a sentence partway through the turn and attributes the request from the wake word on, and the test asserts one request, "what is the status of f twelve?", for QA Example. The fixture's question expects "status of f", the words Flux wrote, rather than "F-12". The same recording, with the second voice reported as Parlume's own, does not wake it. `two-speakers-split-turns.json` is hand-written, as its `source` field says, with Flux ending the first speaker's turn before the question; there Parlume wakes once, for QA Example, on Flux's early end-of-turn.

`party-cf/scripts/parlume-flux-replay.mts` records a fixture from real Flux. It speaks each line of a dialogue with Aura-2 (one voice per speaker), mixes the lines on one timeline with the overlap each line asks for, and streams the mix to Flux on Workers AI in real time, in 80 ms batches, with the bridge's Flux settings. It prints how Flux heard each line (word error rate, and the time from the end of the line's audio to its `EndOfTurn`), whether each keyterm appears in the transcript, and the bridge scorecard for the recording:

```bash
cd party-cf
CLOUDFLARE_ACCOUNT_ID=<account id> CLOUDFLARE_AI_TOKEN_FILE=<path to a Workers AI token> \
  pnpm flux-replay --out src/fixtures/parlume-replay/recorded.json --keyterm Parlume --keyterm F-12
```

`--keyterm` may repeat; without it the only keyterm is `Parlume`, as in the bridge. `--dialogue <file>` replaces the built-in two-speaker dialogue, `--eot-threshold` sets Flux's end-of-turn threshold (default 0.7, Flux's own), and `--account` and `--token-file` stand in for the environment variables. A token file is required, and the token is read from it and never printed; without `CLOUDFLARE_ACCOUNT_ID` or `--account`, the script uses the token's only account. Flux's request ids are left out of the fixture. The built-in dialogue is about 13 seconds of audio and 153 characters of Aura speech. Speech updates in a recorded fixture come from the known timeline and reach the bridge the moment they happen, earlier than Teams reports them.

In six more recordings of the built-in dialogue on 2026-10-27, after the mid-turn wake, Flux ran the question into Dev Example's turn every time. With the bridge's only keyterm, `Parlume`, Flux wrote "Parlume" in two of three and the bridge woke once, for QA Example (the other time Flux dropped "done." and wrote "…we call it Parlume, what is…", with no sentence end before the name, and the third time it wrote "Brethren"); with `Parlume`, `Fabric`, `Dev Example` and `QA Example` as keyterms, Flux wrote "Harlem", "Parliament" and "Harlem", and the bridge never woke. Over the whole dialogue, the word error rate was 0.107 in all three runs with one keyterm and 0.107 to 0.25 with four. The bridge keeps `Parlume` as its only keyterm.

## Measuring notes and suggestion quality

Measure a change to the notes or suggestion model, or to either prompt, on the evaluation set before making it. The set and its runner are in `packages/api/evals/parlume/`; the replay above measures the bridge's hearing, this measures the text Parlume writes from a transcript.

**The meetings.** `fixtures/*.json` holds eleven synthetic meetings. Each has numbered segments (`id`, `speaker`, `text`, which a chat message may split into several lines, `startMs`, `endMs`, and optionally `source` `CHAT` or `EVENT`, and `guest`), the ground truth (`truth.decisions`; `truth.actionItems` with `owner` and `due`, null when the meeting named none), and the suggestion passes a live meeting would get (`suggestions.passesAfter`, the fixture's `workItems`, `agenda` and `previousQuestions`, and the `expected` answers and missed questions). Everyone in them is "… Example", the organization is example-org, and every link is on example.com; none comes from a real meeting. The three-hour meeting generates its long stretches of discussion from `filler` templates, so its notes run as checkpoint parts and a merge. Ground truth names segments by their fixture `id`; the model sees transcript line numbers, and the report maps each note back to its segment.

| Fixture | What it covers |
| --- | --- |
| `sprint-planning-short` | A short meeting; decisions, owners and due dates said plainly; an owner named by someone else; an open question; both kinds of suggestion |
| `inverted-meaning` | A negation around words a quote can lift ("I'm not saying we should drop the audit log"); a date that moves; keeping something by saying it is not removed |
| `speech-to-text-noise` | Misheard names ("red is", "post gress", "Jason"), fillers and repeated words; a due date confirmed again after a dropped line; a topic parked, which is not a decision |
| `side-talk` | Side talk between items and joking "decisions" the meeting did not make |
| `guest-line` | A guest's lines, marked as an unverified speaker; a guest owning an action item; a guest's request to Parlume that the meeting refused |
| `no-decisions` | No decisions; a choice deferred; a commitment with no owner; a missed question carried from the previous meeting |
| `long-roadmap-3h` | Three hours: checkpoint parts and a merge; decisions in each hour; a later decision that replaces an earlier one; a due date that moves |
| `chat-and-markers` | Chat lines, one assigning an action; Parlume's pause and resume markers; a link in the chat |
| `parlume-chat-post` | Parlume's own detail post of several lines, which recommends a decision and an action the meeting did not make and which no note may cite; a person's chat message of several lines; a decision against the post's recommendation |
| `retro-actions` | Many action items, owners named by themselves, by someone else or not at all, and vague commitments |
| `design-review-tentative` | Proposals and preferences that were not decided, a choice deferred to next week, and thinking aloud that is not an action |

**What runs.** For each model and meeting, the runner writes the transcript with finalization's own line format (`parlumeTranscriptLine`), runs the notes passes the notes activity runs (`writeAnchoredNotes` and `parlumeNotesPass` in `packages/temporal/src/activities/parlume-notes-passes.ts`, with the same anchor check), and runs a suggestion pass after each listed segment through `requestParlumeSuggestion`, with the same anchoring as a live pass. A pass reads what a live one would at that moment: the last three minutes of speech, the earlier speech, the chat so far, the suggestions already made, and the fixture's work items, agenda and previous questions. It gets no project passages: retrieval is not under test. The instructions are the default prompt bodies, or a candidate given with `--notes-prompt <file>` and `--suggestion-prompt <file>`. Models are named by catalog name and resolved through the paying account's default provider (`getAIModelWithMetadata` with `modelOverride`, never a ChatGPT plan). With `--provider <AIProvider>` they are resolved instead on the account's own enabled config for that provider: the organization's with `--organization-id`, else the user's (`getAIModelOnProvider`). It builds the model the same way, with the same usage limits and usage logging, and refuses when the account has no such config or the provider has no mapping for the model. When the provider would serve a different model, or the model would run on a provider other than `--provider`, the runner stops before anything is sent, so one model's results never carry another's name. The calls are recorded as usual, under the `parlume` feature key and the jobs `parlume-meeting-notes` and `parlume-live-turn`, with `parlume-eval:<start time>` as their `conversationId`.

**The scores** (`scores.ts`), each added up over the meetings before dividing:

1. **Anchor validity**: of the note entries the model proposed, the share the anchor check keeps for their quote and segment, that is, not dropped as `empty`, `segment_unknown` or `quote_not_in_segment`. It counts every pass of a long meeting. A note can hold a valid quote and still say the opposite of the line, which the next scores catch.
2. **Owner and due accuracy**: each ground-truth action item is paired with the action note that matches its keywords and gets most of its owner and due date right; each pair counts two checks, owner and due date. An owner matches when every word of one name is in the other ("Dev" is "Dev Example"; a bracketed transcript mark is ignored). A due date matches when the words that say when, without "by", "on", "the", "of", "until" and similar, of one are all in the other ("by Friday" is "Friday"). Both absent is a match; one absent is not. Unpaired items are reported as `missed` and unpaired notes as `extra`, outside the score.
3. **Invented decisions**: the decision notes that match no ground-truth decision, as a count and as a share of the decision notes. A decision the meeting later replaced is still in the ground truth, so a note of it is not invented.
4. **Suggestion precision**: of the suggestions the model produced that passed the anchoring (a suggestion whose quote nobody said is dropped, as in a meeting), the share that match an expected one of the same kind. Each expected suggestion matches once; saying it again counts against precision.

Matching is lenient and deterministic. Text is compared word by word, lowercased. Two words are the same when they are equal, when the shorter one has at least four letters and starts the longer ("ship", "shipping"), or when they share their first six letters ("migrate", "migration"). A ground-truth item lists keyword slots; text matches when it meets every slot, where `keep|stay` is met by either word and a slot of several words needs all of them. The slots carry the meaning, negation included: "Keep the audit log" needs `keep|stay|retain`, so "Drop the audit log" does not match, and "The mobile app will not ship in March" needs `not|no|delay|april|…`, so "The mobile app ships in March" does not. A paraphrase that uses none of the listed words counts as a miss; widen the slot rather than the rule.

**Dry run.** Without `--confirm-spend` nothing is sent to a model. The runner prints, per meeting, the notes passes and suggestion passes it would run, their input and output tokens, and the cost for each model, with totals:

- Input tokens are the characters of each pass's instructions and prompt divided by 3, rounded up (`TURN_BUDGET_ESTIMATE.charsPerToken`; English prose runs nearer four characters a token, so this tends to estimate high). The notes prompts counted are the real first-stage prompts. A long meeting's merge pass depends on what those passes return and is counted as the instructions plus twice each part's output cap in characters. Earlier suggestions are not counted.
- Output tokens are each pass's output cap: 4,000 for a notes pass and 1,500 for a suggestion pass. This is an upper bound.
- Cost is tokens times the model's list price per million tokens in the AI model catalog (`packages/database/prisma/ai-model-catalog.ts`). A run's report uses the resolved provider mapping's own price when the mapping has one. A model with no price there shows tokens only. Cache discounts and Claude Haiku 5.5's higher rate for prompts over 100,000 tokens are not applied; no pass here comes near that size.

**Running it.** A run is billed to the AI provider of the account named by `--user-id` (and `--organization-id`), so the spend must be approved before it runs. Print the estimate first, then run with the target environment's `DATABASE_URL` and token-encryption settings loaded:

```bash
npx dotenv -c -e .env.local -- npx tsx packages/api/scripts/parlume-eval.ts \
  --models claude-haiku-5-5,claude-sonnet-5-5,claude-opus-5-5

npx dotenv -c -e .env.local -- npx tsx packages/api/scripts/parlume-eval.ts \
  --models claude-haiku-5-5,claude-sonnet-5-5,claude-opus-5-5 \
  --confirm-spend --user-id <id> --organization-id <id> --out parlume-eval.json

npx dotenv -c -e .env.local -- npx tsx packages/api/scripts/parlume-eval.ts \
  --models claude-haiku-5-5,claude-sonnet-5-5,claude-opus-5-5 \
  --confirm-spend --user-id <id> --organization-id <id> \
  --provider ANTHROPIC_DIRECT --out parlume-eval.json
```

Without `--provider`, a model is resolved on the account's default provider, and a model override that provider has no mapping for is skipped, so the run stops with "resolved to … the account's provider does not serve …". Use `--provider` when the account's default provider does not serve the models under test but another enabled config of the account does, for example an organization whose default is `OPENAI_DIRECT` with an enabled `ANTHROPIC_DIRECT` config for the Claude models. The dry run also takes `--provider` and then prices each model at that provider's mapping where the catalog has one.

`--fixtures` takes a comma-separated list of fixture files or directories (default: all ten). The run writes the report as JSON to `--out`, with every meeting's notes, the segment each cites, the pairs, misses and matches behind each score, and each model's tokens and cost from the usage the SDK returned. It writes a Markdown table beside it (`parlume-eval.md`), a row per model with the four scores, the tokens, the cost and any meeting that failed. A meeting that fails is reported with its error and the tokens it used before failing, and the others still run; the script then exits with 1.

**Tests.** `packages/api/evals/parlume/__tests__/` runs in the API package's unit tests with every model call mocked. `scores.test.ts` replays hand-written model replies (`recorded/*.json`) through the real passes: a note citing the wrong segment, a note with no quote, an invented decision with a valid quote, a wrong owner the cited line names, an inverted-meaning bullet that passes the anchor check and counts as invented, and suggestions matched, unmatched and dropped as unanchored. `runner.test.ts` checks that no model is resolved or called without `--confirm-spend`, the dry-run estimate formula and prices, a run's report, tokens and cost, that `--provider` reaches every model resolution, and that a provider serving another model, or a model on another provider than `--provider`, stops the run before any call. `packages/ai/__tests__/model-on-provider.test.ts` checks that `getAIModelOnProvider` runs on the organization's or the user's config for the named provider, never the default provider or a ChatGPT plan, and refuses a provider with no config and a model it does not map. `fixtures.test.ts` checks that every meeting parses, names only segments it has, holds only placeholder people and hosts, and that the three-hour meeting runs as checkpoint parts.

## Governance policy

Parlume answers in front of everyone in the meeting, so what it says or posts is what every person present may see.

**Default deny for shared answers.** Parlume speaks and posts only content that every person present may see. A verified attendee is a participant Fabric matched to a Fabric user with read access to the project (see [Who is in the meeting](#who-is-in-the-meeting)); Fabric records each one on the session (`ParlumeMeetingSession.attendeeUserIds`, `recordParlumeAttendee`). While anyone present is not verified, Parlume answers nothing in the meeting. Fabric keeps the strict mode it already had: a participant it cannot confirm makes Parlume explain and leave, and Parlume says nothing while someone is still being checked. So no answer is ever shared with an unverified person, and the narrower mode of sharing only non-confidential content with one present does not arise.

**Requester and recipient checks.** Every lookup runs as the person who asked, never as the inviter:

1. The bridge names the asker (`requester`). The turns route accepts the name only when it is a confirmed attendee present now and on the session's verified attendees (`parlumeTurnAudience` in `packages/api/modules/projects/lib/parlume-confidential.ts`).
2. The turn's acting grant is minted for the asker (`mintParlumeActingGrantForTurn`), with read scopes only, so Fabric MCP reads with the asker's tenant, project membership and permissions. Project knowledge and a custom agent's knowledge are searched as the asker too.
3. The worker checks the asker's project access again before it looks anything up (`hasProjectAccess` in `packages/temporal/src/activities/parlume.ts`).
4. When Fabric cannot place the asker (a bridge that does not name one, an utterance it cannot attribute, or an asker who lost access), the turn looks nothing up and says so: "I couldn't tell who asked, so I didn't look anything up. Ask me again, or type the question in the meeting chat, where I can see who is asking. For an answer only you see, ask the Fabric Agent in Fabric." (`PARLUME_UNCONFIRMED_REQUESTER_REPLY`). The Fabric Agent in Fabric is the private delivery: it answers only the person who asks, with their own access.
5. Every recipient is checked: each confirmed attendee present has `PROJECT_READ` checked again before each turn, and anyone who cannot be confirmed makes Parlume leave. The project-read ceiling on every turn (`mayUseInMeeting`) still applies, so an answer holds nothing beyond what every project reader may see.

The web route and the bridge must run the same version: a bridge that sends no `requester` gets the decline above for every turn.

**Confidential discussion.** Part or all of a meeting can be marked confidential:

- **In the meeting**, said or typed: "Parlume, confidential", "Parlume, off the record" or "Hey Parlume, this is confidential" starts the confidential part; "Parlume, end confidential" or "Parlume, back on the record" ends it (`parseParlumeConfidentialCommand` and `parseParlumeConfidentialRequest` in `packages/utils/lib/parlume-confidential.ts`). The whole utterance or message must be the command, so a remark that a topic is confidential changes nothing. The segments route and the turns route both apply it, once (`setParlumeConfidentialRange`), and a turn started by the wake phrase answers it aloud. The saved transcript gets a marker line where the part starts and ends, and the chat gets a notice naming who marked it. The notice is an ordinary post, so it waits while anyone is being checked.
- **In Fabric**: the Parlume page's live card offers **Confidential from now** and **End confidential part**, and each finished session **Mark meeting confidential** and **Remove confidential mark** (`ParlumeConfidentialControl`, `projects.parlume.setConfidential`, `POST /projects/{projectId}/parlume/sessions/{sessionId}/confidential`). For a live meeting it starts or ends the confidential part from now, as the command does; for a finished meeting it marks or clears the whole meeting and all its segments. The person who invited Parlume, a project manager, or anyone Fabric confirmed in the meeting may mark it. Removing the mark widens who reads the meeting, so only a project manager, or the inviter who was in the meeting, may remove it. Both are audited (`project.parlume.confidential_marked`, `project.parlume.confidential_cleared`).
- **Ending it from the meeting is refused while a guest is or was expected** (`externalInvitees`, `guestJoinedAt`); Parlume says a project manager can end it on the Parlume page, and only a manager can there.

What is said while the part runs is stored as confidential (`ParlumeMeetingSegment.confidential`), and the session is confidential from then on (`ParlumeMeetingSession.confidential`). A confidential session's derived outputs are kept to its verified attendees who still read the project and the project's managers (`PROJECT_MEMBERS_MANAGE`): its notes, requests and Parlume's answers, proposed changes, suggestions and transcript (`isParlumeConfidentialReader`, `mayReadParlumeSessionContent`, `withheldConfidentialParlumeSessions`). A summary cannot be split by segment, so the whole session's outputs are protected once any part of it is confidential. Someone absent from the meeting reads it only as a project manager. Everyone else sees that the meeting took place and is told its content is kept to the people who were in it. The recap of a later meeting never draws on it.

In the meeting, a turn uses the confidential part's segments and earlier answers only when everyone present is one of the session's verified attendees and no guest is or was expected in the meeting (`withConfidential`, from `parlumeTurnAudience`). A guest has no Fabric account, so the bridge never lists one among the attendees: the session's `externalInvitees` and `guestJoinedAt` stand in for them. Confidential content from other meetings is never used in a live turn. Nothing confidential is posted to the meeting chat while an unverified person is present, because Parlume posts nothing then.

**Existing meetings.** Meetings recorded before these rules stay non-confidential, and no earlier session, segment or request was changed. The rules apply from now on; a member can still mark a finished meeting confidential on the Parlume page.

**Rollout.** These rules are always on. There is no feature flag.

## Transcript access, deletion and retention

**Who reads a transcript.** A Parlume transcript is everything said in the meeting, and raw meeting content is for the people who were in the meeting, so fewer people read it than read the project: the session's `userId` (the person who invited Parlume, or the series' enabler for an automatic join), anyone with `PROJECT_MEMBERS_MANAGE` on the project (project owners and admins, and organization owners and admins), and a project member whose account email, compared lower-cased, is in the session's `inviteeEmails` (the internal invitees of an automatic join, see **Guests in an automatic join**). `PROJECT_MEMBERS_MANAGE` is the permission that invites and removes Parlume; `PROJECT_UPDATE` is not enough, because editors hold it. A manual invitation has no invitee list, so only its inviter and managers read it. The check is `canReadParlumeTranscript` in `packages/api/modules/projects/lib/parlume-transcript-access.ts`. It guards the context page (`/projects/{id}/contexts/{contextId}` shows "Only the people invited to this meeting, the person who invited Parlume and project managers can read this meeting's transcript"), the single download (`createContextDownloadUrl` refuses with `FORBIDDEN`) and the project download (`createContextsBatchDownloadUrl` leaves the transcript out). The Context tab list (`listContexts`) keeps the transcript's row and its notes, but returns `contentPreview` and `contentHash` as null; one `withheldParlumeTranscriptIds` lookup per request decides which rows. The context manifest (`readContextManifest`, behind `GET /projects/{projectId}/contexts/manifest`, the v1 route and the MCP tool) keeps the row but gives a withheld transcript a `revision` derived from its id and `updatedAt` instead of a digest of its content; a reader keeps the content digest. A summary reference to the transcript (`resolveContextSummaryReference`) refuses with `FORBIDDEN`, and so do the AI intake paths that take a caller-supplied context: a discovery run's OpenAPI context (`startDiscovery`) and scope intake (`startScopeIntake`). `listSessions` returns `canReadTranscript` and `canDeleteSession` per session; the Parlume page shows **Open transcript** with the first and **Delete session** with the second. Other project readers see the session, its status, its notes, its requests and its suggestions; a suggestion's `quote` is returned only to a reader of the transcript.

**Search and answers.** Parlume transcripts are never embedded: finalization starts the notes workflow only, not `contextEmbeddingWorkflow`. Every path that reads context text leaves them out. `findConfidentialTranscriptContextIds` returns every Parlume transcript context, so project-knowledge retrieval, feature-spec and living-document updates (`retrieveRelevantContextsForSpec`), document generation (`retrieveProjectContexts` in the document-generation activity), the MCP `get_project_context` tool, the agents' source reader (`/api/internal/project-source`), the assistants' recent-transcripts context (`meetingTranscriptSync.getContext`) and context summaries treat it as confidential. The knowledge search SQL (`knowledge-search.ts`) and the context-quality source reader (`context-quality-body.ts`) exclude any context that is a session's `transcriptContextId`. The notes live in the same context's `metadata.parlumeNotes` and stay readable to every project reader through the Parlume page (`listSessions`) and the series recap. They are not indexed for search on their own, as before this change. The live meeting is not affected: the bridge and the meeting-turn activity read the current session's segments directly.

**Delete a session.** `projects.parlume.deleteSession` (`POST /projects/{projectId}/parlume/sessions/{sessionId}/delete`, `packages/api/modules/projects/procedures/parlume/delete-session.ts`) needs `PROJECT_READ` and then `canDeleteParlumeSession`: the inviter or a manager. An invitee may read the transcript but not delete it for everyone. It refuses with `CONFLICT` a session that is not settled (status `ENDED`, or `FAILED` with `finalizedAt` set or with no provider bot): Parlume could still be in the meeting, and finalization would write the transcript again. It does not stop the bot; the member removes Parlume first. It also refuses while the notes are `PENDING`, because the notes are written from the transcript. In one transaction (`purgeParlumeSessionContent` with scope `SESSION`, `packages/database/prisma/queries/projects/parlume-retention.ts`) it deletes the session's segments, webhook receipts, actions, turns and suggestions, sets `ParlumeMeetingSession.transcriptDeletedAt`, empties the transcript context's `content`, clears its `embeddedAt` and `qdrantId`, and queues a `ProjectContextPendingVectorCleanup` for its vectors. After the commit it drains that record once; the pending-cleanup sweep finishes a drain that fails. The session row and the context row stay, so the notes stay. Deleting the context in the Context tab deletes the notes. The audit log records `project.parlume.session_deleted`. Fabric then asks the bridge to purge its storage (see **The bridge's copy**).

**The retention sweep.** The Temporal schedule `parlume-transcript-retention` (cron `35 * * * *`, `overlap: SKIP`) runs `parlumeTranscriptRetentionWorkflow`, whose activity `purgeExpiredParlumeTranscripts` (`packages/temporal/src/activities/parlume-retention.ts`) takes up to 50 settled sessions created more than 90 days ago (`PARLUME_TRANSCRIPT_RETENTION_DAYS`) with no `transcriptDeletedAt`, oldest first. For each it runs `purgeParlumeSessionContent` with scope `TRANSCRIPT`: segments and webhook receipts are deleted, each turn keeps its row with `requestText` emptied and `responseText` cleared, each suggestion loses its `quote`, and actions stay. The transcript context loses its text and vectors as for a delete. It then clears the index marks of up to 50 Parlume transcript contexts that are still embedded (from before this change, or a project's "embed all") and queues their vectors (`dropParlumeTranscriptVectors`). A failed drain is logged as `parlume.retention.drain_failed` and left to the pending-cleanup sweep. A purged session is not listed again, so a rerun is harmless. The schedule is registered by `ensureParlumeRetentionSchedule` in `registerSystemSchedules`.

**The bridge's copy.** The Durable Object keeps pending segments, requests, chat state and pause reports in its storage while the meeting runs. Fabric asks the bridge to drop it as soon as the session is over: once finalization has saved the transcript (`finalizeParlumeSession`), and when a member deletes the session. `requestParlumeBridgePurge` (`packages/api/modules/projects/lib/parlume-bridge-purge.ts`) posts `?action=purge` with the service secret, as the `leaving` control does, with a four-second timeout. The bridge refuses with `409` while a stream socket is still connected (logged as `parlume.bridge.bridge.purge_refused`, and by Fabric as `parlume.bridge.purge_deferred`); otherwise it deletes its alarm and then all its storage (`purgeParlumeBridge` in `party-cf/src/parlume-bridge-purge.ts`) and logs `parlume.bridge.bridge.purged` with `reason: "fabric"`. The request is best effort: a refusal or a failure (logged as `parlume.bridge.purge_failed`) never fails finalization or the delete. The hard-stop alarm stays the backstop: when the watchdog finds the meeting over, and Fabric has acknowledged the watchdog and taken every pending segment, request and pause or resume report, the bridge purges the same way and logs `parlume.bridge.bridge.purged` with `reason: "hard_stop"`. Until then the alarm retries every five minutes. A pause or resume made on a session whose stream never connected names no bot, so Fabric cannot record it; once the meeting is over the bridge drops such reports (logged as `parlume.bridge.listening.reports_dropped`) instead of keeping its storage for them.

## Boundaries

- The invite form tells the inviter that Parlume records and transcribes the meeting, and that participants should be told before it is invited. It is a notice, not a gate: there is nothing to tick, and Fabric stores no consent record. In the meeting itself, Parlume posts its join notice (see [Parlume's notice in the meeting](#parlumes-notice-in-the-meeting)), and Fabric records when it was shown.
- The inviter must have project administration permission, and a Microsoft Teams connection (`MICROSOFT_GRAPH` workflow integration): `startParlumeMeetingSession` refuses the invitation, manual or automatic, without one, because Parlume checks attendees through it (see [Who is in the meeting](#who-is-in-the-meeting)). It also makes one cheap call with the connection (`parlume_channel` operation `me`, `GET /me?$select=id`) and refuses the invitation, asking the inviter to reconnect Microsoft Teams, when that call fails.
- **Whose access an answer uses.** Every meeting answer, spoken or typed, looks things up as the confirmed participant who asked (`ParlumeMeetingTurn.requesterUserId`), limited to the meeting's project; the agent, its model and the bill stay the inviter's. A turn whose asker Fabric cannot place looks nothing up (see [Governance policy](#governance-policy)). Fabric's tools hold each call that reaches a project to the meeting's project and refuse another one (a page from another of the asker's projects is refused), and a change that names another project is refused. Every turn's ceiling is plain project read, whoever is in the meeting, the inviter alone included. One check enforces it (`mayUseInMeeting` in `packages/temporal/src/activities/parlume-actions.ts`): a turn calls only Fabric's portal project tools (`isFabricPortalProjectTool`) and the project-context and create-story built-ins; workflows, frames, pages, connected servers, integrations, Databricks knowledge, workspaces and spending tools (web search, images, code) are refused with "In a meeting I use only what every project member can read." Raw Parlume transcripts and confidential series are already out of every turn's sources (`findConfidentialTranscriptContextIds`, the knowledge-search SQL). Everyone present is someone Fabric confirmed with project read, so this is the access they share. One ceiling for every turn means nothing an earlier turn said, a reply a `say`, `go` or `more` plays again, or what the realtime voice remembers, ever held more than project read.
- Parlume is a voice adapter around the selected agent's normal execution path. Each request reloads the current active custom-agent version or the built-in agent's preferences. Configured instructions, knowledge, tools, models and permission checks remain owned by that agent. Agent changes apply to subsequent requests.
- Invitations default to **Read-only**, which refuses every change. Choosing **Actions** lets attendees ask for changes, and Parlume proposes each one; it makes none on its own. In every mode a live turn's acting grant carries read scopes only (`mintParlumeActingGrantForTurn`), so a turn can look things up with the asker's read access and cannot write. The gateway holds that line itself (`serviceSessionScopes` in `apps/web/modules/saas/mcp/lib/gateway/tool-scope.ts`): a grant that names a project holds the reads of the base service set plus its own scopes within `SERVICE_GRANT_MAX_SCOPES`, so the live turn's grant has no `workflows:write`, `workflows:run` or `frames:write` and a workflow or frame write is refused by scope. A confirmed change's grant names those scopes and keeps them. A chat grant names no project and keeps the whole base set. A write tool the agent calls records a `ParlumeAction` with status `PROPOSED` and `expiresAt` 24 hours on, and posts the proposal to the meeting chat (bridge post kind `proposal`) with **Confirm in Fabric** and **Dismiss** links, both built by `buildParlumeActionUrl` to `/app/{org}/projects/{id}/parlume/actions/{actionId}` (Dismiss adds `?intent=dismiss`). Opening a link changes nothing. The action page needs a session (it sends a visitor without one to sign-in and back with `loginPathReturningTo`), the organization, `PARLUME_MEETINGS` and project access; `projects.parlume.action` needs project read access and returns `canConfirm` (project edit rights). `projects.parlume.confirmAction` (project update permission) claims the proposal once (`PROPOSED` and unexpired → `EXECUTING`, with `confirmedAt` and `decidedByUserId`), so two confirmations run one change, and starts `parlumeConfirmedActionWorkflow` with a grant minted for the confirming member (`mintParlumeActingGrantForConfirmedAction`); the change runs as that member, who must still be able to edit the project. The run claims the action once before it acts (`ParlumeAction.startedAt`, set only while the action is `EXECUTING` and unclaimed), and a run that loses the claim does nothing. A start Temporal answers as already started counts as started. Any other start error may still have started the workflow (a lost reply), so the proposal reopens to `PROPOSED` only while no run has claimed it; otherwise the confirmation stands. Either way the change runs at most once. `projects.parlume.dismissAction` sets `CANCELLED`. A proposal past `expiresAt` is shown and recorded as `EXPIRED`. Only Fabric's own tools (`fabric-platform`, `builtin`) are proposed; a write through another MCP connection is refused, because it would run on the inviter's credentials. After a confirmed change ends, the worker posts **Done** or **Change not made** to the chat, naming the confirming member and the proposal's tag, while the session is live; Parlume does not speak it. No typed or spoken command confirms a change. A change that names another project is refused. A provider speaker label is continuity information, not a verified Fabric identity; people sharing a microphone may share that label, and a change asked for by a speaker Teams gave no label for is recorded as unattributed.
- Each change is recorded when it is proposed as a `ParlumeAction` with the requester's label, the tool, its arguments, and later its outcome. Confirming writes `project.parlume.action_confirmed` (shown as “Parlume change confirmed”) and dismissing writes `project.parlume.action_dismissed` (“Parlume change dismissed”), each with the member who decided as the actor. The change itself runs with the agent **Fabric Parlume** (`actorType` `agent`, `actorNameSnapshot` "Fabric Parlume") as the actor and the confirming member, with their email as `actorEmailSnapshot`, as the user it acted for. Once the change has run, by the in-process Fabric tool or through Fabric MCP, `executeConfirmedParlumeAction` (`packages/temporal/src/activities/parlume-confirmed-action.ts`) writes `project.parlume.action_executed` (“Parlume confirmed change ran”) with that agent actor, outcome `success` for `COMPLETED` and `failure` for `FAILED` or `OUTCOME_UNKNOWN`, and the action's status, tool, session, chat tag, the inviter as `invitedBy` and any created work item's id, kind and number as metadata, never the arguments or the outcome text; a run that finds the action already settled writes none. Each meeting turn that ends writes one `project.parlume.request_answered` row (“Parlume answered a meeting request”) with the same agent actor for the participant who asked (the turn's `requesterUserId`, whose access it read with), that participant's email as `actorEmailSnapshot` (no member when Parlume could not tell who asked, because such a turn reads nothing), the inviter as `invitedBy` in the metadata, outcome `success` for `COMPLETED` and `failure` for `FAILED` or `STOPPED`, and the status, session, source (`spoken` or `typed`) and the names of the tools the turn called, never the question, the answer or tool arguments; the write that ended the turn records it (`recordParlumeTurnAnswered` in `packages/temporal/src/activities/parlume-turn-audit.ts`, from the worker or from the interrupt route for a turn it stopped), so a turn has one row. A Parlume turn also sends `x-fabric-surface: parlume` with its Fabric MCP calls, so the gateway tells them from chat calls and writes its own audit rows for them (a created feature or bug, a context metadata change, an instruction set change, an agent run command) with the same agent actor. An identical call in the same turn is proposed once. A result that names what it made (for example a work item's identifier and link) and carries no error is recorded as completed; an uncertain outcome such as a timeout is recorded as `OUTCOME_UNKNOWN` without automatic retry. Check the destination before requesting an uncertain action again. Interrupting or cancelling a turn changes no proposal and no confirmed change.
- A typed request answered by its proposal post gets no second post. The turn's own reply ("P2 waits for a member…") only repeats the proposal, so when it is one short sentence naming a proposal the turn posted, the worker sends the bridge a close (`?action=chat` with `final` and `close`) instead of a post, which ends the chat request like a final post (`finishParlumeChatReply`). The reply stays on the request in the Requests list. A longer reply, or a bridge that refuses the close, is posted as before.
- Creating a work item answers within a few seconds. The item is created from what was said, as the agent named its kind, and its body is drafted afterwards by the same workflow that rewrites a body after a type conversion; the prior body is kept as a version, and the draft is discarded if someone edited the item meanwhile. The agent says what it created and, when asked for the link, sends it to the meeting chat.
- The Fabric Agent in a meeting also has the Fabric portal's project tools: who the asker is and their organization, the projects, features and their tasks and status, bugs, documents, project contexts, coding instructions (read, propose a change, add a lesson), project knowledge search. It is not given the asker's own workspaces (`fabric_list_workspaces`, `fabric_get_workspace`, `fabric_get_workspace_document`, `fabric_query_workspace`, held back by `FABRIC_MEETING_WITHHELD_TOOL_NAMES` although the gateway serves them to other project-bound sessions). It cannot list the asker's own AI chats or connected servers, because anyone who can speak in the meeting would hear them; the meeting's grant carries no `chats:read`, the gateway refuses both lists on a meeting's session, and a meeting turn is not given the in-process tools that list the inviter's own sessions, agents and connections (`list_recent_sessions`, `get_session`, `list_agents`, `list_connections`), which a staging meeting had used to read out the inviter's recent chats. The portal tools come through the Fabric MCP gateway on a grant the web app signs for each turn. The grant names the meeting's project and the scopes those tools need; the gateway keeps only the scopes within its own ceiling and admits the grant only when the asker can open that project in the organization acted in. Every call is then held to the inviter and that organization (the agent cannot switch to another organization, and lists only the one it acts in) and to the meeting's project: a call that names another project, a nested project id included, or a feature, document or context of another one is refused, and the project list is the meeting's project alone. Workflows and pages are named by id rather than by project, so their commands are held to the meeting's project too: listing, reading, running or changing a workflow, and reading, listing or changing a page, reach only the meeting's own project. Creating a new project is allowed and does not move the meeting off its own. The tools that request, check or revoke delegated authority and the memory tools are not offered, and a test fails when the gateway gains a platform tool that is neither offered nor named as left out. A new feature or bug is filed from the words given and drafted in the background, as for `fabric_create_story`. The portal schemas are about 29 KB, so a turn carries them only when the request asks for something they do (changing a feature or task, writing a document, context or instruction, searching project knowledge, projects, organizations or a workspace); a plain question does not. Read or change comes from the gateway's own listing, so a change in a read-only meeting is refused and in an actions meeting runs at once and is recorded.
- **External tools.** A meeting turn uses no external MCP server, integration or workspace: they would show what other systems hold to people in the meeting who may not have access to those systems. The Fabric Agent's servers and workspaces from the chat are left out, and so are a project agent's own (`loadParlumeAgent` gives it none, including a server listed only in the agent's older tool connections). There is no setting for it; the former **Use external tools in meetings** switch is gone, and the `AgentTemplateInstance.meetingExternalTools` column is no longer read or written. Fabric's own project tools are not external tools and stay available.
- Configured built-in actions use the shared agent tool mapping and implementations. Workflow starts use the same execution API as chat, including current organization and project permissions, workflow state, and concurrency limits.
- Parlume's suggestions, missed questions and recap go where the session's audience says. With **Everyone in the meeting (chat)** they are posted in the Teams meeting chat, so every participant, including external guests and anyone the organizer admits, reads them. With **Only your team (Parlume page)**, the default (`ParlumeSuggestionAudience` `TEAM`), nothing is posted in the chat, and they are visible only on the Parlume page. Either way the Parlume page lists them to the same readers as the Requests list (project read permission), scoped to the project and its organization. A team-only suggestion has no chat tag, so nobody in the meeting can have it read aloud with `go`.
- **Confidential series.** Each linked series in **Configure meetings** has a **Confidential** switch (`ProjectLinkedMeeting.confidential`, off by default), shown to the people who can change the series' other settings and saved by `meetingDigest.setConfidential` (project member management; the change is audited as `project.meeting_digest.confidentiality_changed`). While it is on, the series' transcripts, synced or from Parlume, stay out of later answers and recaps: Parlume posts no "Since last time" recap for the series, agendas, live suggestions and the agenda's open action items do not draw on its earlier meetings, project search (`retrieveProjectContexts`, which Parlume, the agents and the chat use) drops every chunk of its transcripts, the keyword search behind `fabric_search_project_knowledge` leaves them out, `fabric_get_project_context` refuses to return one (`FORBIDDEN`, saying the series is confidential; listings still show the source's title and type, never its text), `fabric_list_meeting_transcripts` does not list them, the daily brief leaves them out, publishing drafts do not use them (the dispatch count leaves them out as well, so they never trigger a draft), and the project summary does not fold them. Turning the switch on also retires the project's current summary when it may already hold one of the series' transcripts, because a summary run extends the previous summary, and cancels a run in progress, whose completion then leaves it cancelled; the next run rebuilds the summary from every source without them. The transcripts themselves are kept and still appear in the Meeting Digest to project readers, and turning the switch off brings them back into later answers. Generated project documents and feature-spec updates leave them out as well. The current meeting is not affected: Parlume still hears it and answers from what is said.
- The Parlume page's **Requests** list is available to project readers. It records questions, requester labels, timestamps, responses, exact action details, and each action's status and outcome. It does not create a personal attendee profile.
- A session ends, and records why (`endReason`), when an administrator presses Stop, when the meeting host removes the bot or the meeting ends (the provider's terminal callback also closes the live stream, and if no stream is open the next access check finalizes, so the transcript is saved within a minute), after **three minutes with no human speech** while Parlume is silent (`IDLE`), when the inviter loses project access, when someone joins whom Fabric cannot confirm, a confirmed attendee loses project read, or the meeting is a channel's (`ATTENDEE_NOT_AUTHORIZED`, shown as **Left for an unconfirmed attendee**; `EXTERNAL_GUEST` is no longer written), on an unrecoverable stream failure, or at the four-hour cap. Attendee itself gives up after five minutes in a lobby (`waiting_room_timeout_seconds`) or three minutes with nobody else present, and after the hard stop plus a two-minute backstop if Fabric's own leave never lands. Fabric has no live participant count for the people who remain, so "nobody speaking" is detected as silence; raise `IDLE_LEAVE_MS` in the bridge if quiet, attended meetings prove common.
- Spend is recorded in the project's AI usage under the `parlume` feature key with the session id as `conversationId`. The Parlume page shows the project total and a per-session split in cents, with “< $0.01” for spend under one cent, and the organization's AI usage page lists the same rows. Spend is shown only to the people who can invite and remove Parlume (project administration), because inviting it is what incurs the spend: the usage procedure (`GET /projects/{projectId}/parlume/usage`) refuses everyone else, and their Parlume page shows sessions and requests with no Cost column, spend so far or Spend card. The project's general usage views (`/projects/{projectId}/usage/*`: summary, breakdown, time series and recent calls) leave out `parlume` calls for the same readers, and keep calls that carry no feature key. Each source is priced as follows:
  - **Meeting bot** (`CUSTOM`, `attendee/teams-bot`, shown as Attendee · Teams meeting bot): one Attendee credit per bot-hour, priced at the $0.50 entry rate, recorded once at finalization. Bot time runs from the invite (the session's creation, just before Fabric asks Attendee for the bot) to the provider's terminal callback, or the leave request or capture stop when the callback never came, so time spent waiting in the lobby and a bot that was never admitted or never streamed are billed too, as Attendee bills them. The bot waits up to five minutes to be admitted, so an invite nobody admits costs about $0.04.
  - **Live transcription** (`CLOUDFLARE_AI`, `@cf/deepgram/flux`, shown as Workers AI): $0.0077 per audio minute, recorded at finalization for the streamed time only, from the verified media stream (`joinedAt`) to the same end.
  - **Realtime voice** (`AZURE_AI_FOUNDRY`, `gpt-realtime-2.1`): per response, from the tokens the bridge reads in `response.done`, at the rates in the realtime voice section below. Azure AI Foundry publishes the same text rates for `gpt-realtime-2.1` ($4 input, $24 output per 1M tokens) and no separate audio rates, so a session is recorded at the OpenAI list rates. Older sessions minted on an OpenAI Direct key keep their `OPENAI_DIRECT` rows.
  - **Speech** (`CLOUDFLARE_AI`, `@cf/deepgram/aura-2-en`): $0.03 per 1,000 characters sent to Aura, for the sentences the worker sends the bridge and for the speech the bridge synthesizes on its own (`/api/internal/parlume/speech-usage`).
  - **Agent turns, suggestions, warm-up and meeting notes**: ordinary model calls, priced by the model's tokens like any other AI usage.
- A live session's spend so far leaves out the bot's time and live transcription, which are added when the session is finalized; the live card, the session's Cost and the Spend card say so. The bot time and transcription rows, and the realtime voice rows, have no request latency (`latencyMs` is 0; older bot and transcription rows stored the meeting's length there): the AI usage page shows no latency for them and leaves them out of its average latency and latency filters.
- **Join notices.** The session's `userId` (the inviter, or the series' enabler for an automatic join) gets an in-app notification and an email while the bot is not in the meeting (`packages/api/modules/projects/lib/parlume-notices.ts`). `PARLUME_WAITING_IN_LOBBY`, titled "Parlume is waiting to join: admit Fabric Parlume from the lobby by HH:MM", goes out while the session is still `JOINING` and has never streamed (`joinedAt` null). Hosted Attendee never reports a Teams lobby: its `waiting_room` state is behind its server flag `ENABLE_WAITING_ROOM_STATE_FOR_WEB_BOTS`, off by default, and on staging a bot nobody admitted went from `joining` straight to `fatal_error` / `waiting_room_timeout_exceeded`. So the bridge's arm sets its first alarm 90 seconds after the invite (`LOBBY_CHECK_MS` in `party-cf/src/parlume.ts`; staging joins streamed in 24 seconds at the median and 50 at the 90th percentile), and a bridge still without a verified stream then posts `/api/internal/parlume/lobby` and waits for the hard stop. A self-hosted Attendee that reports `waiting_room` still sends the notice from the callback, matched to the session's bot. The time is five minutes (`PARLUME_LOBBY_WAIT_SECONDS`) after the invite (`createdAt`), so it is never later than Attendee waits, in the recipient's `User.timezone`, or UTC, with the zone's short name. When a session ends `START_FAILED` or `NOT_ADMITTED`, `PARLUME_JOIN_FAILED` carries the reason the session row holds (`lastError`, worded by `parlume-join-failure.ts`): from the callback on the first failure it records, and from the start path for an automatic join only, since a person who invites by hand reads the refusal on the invite card. Both are category `SYSTEM` (always on) and deduplicated per session while unread. The email uses the `parlumeJoinFailed` and `parlumeWaitingInLobby` templates, unless the recipient's email channel is on, which already mails every notification. Titles and subjects are fixed text; a series' calendar subject goes only in the snippet and the email body. A notice that cannot be sent is logged as `parlume.notice.failed` and never fails the webhook or the start.
- **Stranded sessions.** `sweepOverdueParlumeSessions` (`parlume-sweep.ts`) finalizes up to five sessions in `LEAVING`, `STOP_FAILED` or `FAILED` whose provider already reported the bot gone, at their hard stop or 15 minutes after that report. The project's session list runs it for that project, and the Temporal schedule `parlume-session-sweep` (cron `*/10 * * * *`, `overlap: SKIP`) runs `parlumeSessionSweepWorkflow`, whose activity `requestParlumeSessionSweep` asks `/api/internal/parlume/sweep` (service token) to run it for every project, so a lost bridge alarm no longer leaves a session open until someone opens its page. The schedule is registered by `ensureParlumeSweepSchedule` in `registerSystemSchedules`.
- Finalization records the bot time once. A finalization claim older than five minutes can be taken over by a later attempt, and only the attempt that still holds the claim may finish, so a stalled one that resumes saves no second transcript and records no second bot time.
- Every step logs a structured event (`component: "parlume"`, `event: "parlume.<name>"`, `sessionId`, `botId`, counts and latencies; never the meeting link, tokens, secrets, or transcript text) across the web routes, the API, the Temporal worker, and the bridge (Workers Logs, `parlume.bridge.*`). Rejected provider callbacks (`parlume.callback.rejected`) log the trigger, whether the token was present, and the reason: `token` or `signature`. A callback accepted on its token alone, because no webhook secret is set, logs `parlume.callback.unsigned` with the session and trigger. A redelivered callback logs `parlume.callback.duplicate`.
- Wake phrases are matched by sound, not spelling, because transcription spells the names by ear ("Fabrik", "Parloom", "Perlman"); a whole-word consonant comparison keeps "Fabrication" or "Parliament" from waking it. After a spoken greeting, a clipped "Fabr-" ("Hey, Fabry", "Hey Fabri") also wakes it. The bridge transcribes one mixed meeting track, so when a second person asks over someone else's talk, transcription runs both into one turn under the louder speaker and clips the words: in a staging meeting with three people, "Hey Fabric, how many documents does this project have?" said over side talk arrived as "…before Friday. Hey, Fabry. Check the launch checklist together.... does this project have?..." and was missed. Waking on it arms the realtime voice, which hears the question itself. "Parlume" (not "Fabric", an ordinary word in a sentence) also wakes it when it opens a sentence partway through a transcribed turn, after a full stop, question mark or exclamation mark, under the same rules as at the start of a turn: "…we call it done. Parlume, what is the status of F-12?" wakes it, "…we call it done. Parlume is slow." does not. Flux runs two speakers into one turn when the second starts before the first has finished, so the name is not always at the start. A final segment that looks addressed to Parlume but did not wake it is logged as `parlume.bridge.wake.near_miss`, with its reason and length but never its words: a greeting before a clipped name ("Hey, Fab"), a chat post command without the name before it ("go P3"), or "Parlume" where the wake rule does not take it. "Fabric" alone is not counted, because meetings say the product's name all the time, and a segment that follows a bare wake phrase is a request, not a near miss. A bare wake phrase waits 15 seconds for its speaker's request. When Attendee gave it no speaker, as for a short "Hey, Fabric." said before anyone else spoke, the next segment within 8 seconds is its request, whoever it is attributed to; in one staging meeting that request came 4.3 seconds later under the speaker's name and was not answered. A typed chat message must still open with its address. A leave Fabric requested (Stop, idle, revoked access, hard stop) ends normally even when the provider reports it as a failed bot.
- Attendee connects to the bridge as a WebSocket client, using the per-session URL (with its stream token) Fabric gave it when it created the bot, and streams the mixed meeting audio as 16 kHz JSON `realtime_audio.mixed` messages of 10 ms each. The bridge verifies the bot named by the first message before trusting the stream, and plays replies by sending `realtime_audio.bot_output` messages back on the same socket: 100 ms frames paced in real time, opened with 300 ms of silence so the bot's unmute does not clip the first word. A reply is open from its first audio until its speech has played out (`end`) or a stop drops it (`clear`), and when its next audio is late, such as while Aura synthesizes the next sentence or the realtime voice runs a tool, the outlet (`ParlumeAudioOutlet` in `party-cf/src/parlume-pcm.ts`) sends silence frames at the same pace for up to 8 s: with no audio for about 2 s, Attendee mutes the bot inside the reply, and its next unmute clips a word. The silence keeps the 200 ms lead, so a stop is as fast as before, and nothing is sent between replies or while a spoken stop holds the outlet (`pause`). After a longer gap the next audio opens with the 300 ms of silence again, as a reply from idle does. Each reply counts the silence it sent while it waited for its next part (`replyStats.waitMs`), the time its audio stayed out after the 8 s, when the bot may mute (`replyStats.underrunMs`), and how often a late timer restarted the outlet's clock (`stallResets`), and tells the speech telemetry how each reply played (`ParlumeOutletReplyObserver`; see **Speech telemetry**). Parlume's own chat posts wait until the outlet has sent the speech it holds, for at most 30 s (`chat.held_for_speech`, with `heldMs` and `timedOut`): Attendee sends no meeting audio while it posts, and a post in the middle of an answer drew attention from it. The hold covers every post the bridge makes, the worker's answers, the realtime voice's `post_to_chat` after its response is done, and notices, so the worker allows 45 s for a chat post; only an essential notice (the join and guest notices, a pause or resume line, the leaving notice) goes out at once. A tail shorter than a frame that waits for the rest of its reply does not hold a post, so a post the agent makes partway through an answer goes out once the sentences already written have played, and the answer goes on after it. Every post still goes as the HTML Attendee pastes in one step. The bot records nothing (`recording_settings.format` is `none`), and Attendee's own transcription is not used. The bridge transcribes the mixed meeting audio with Deepgram Flux on Workers AI, which also decides where a speaker's turn ends; it sends Flux 80 ms batches, as Deepgram recommends, because Flux fed Attendee's 10 ms chunks at 24 kHz transcribed nothing. Replies go back at Fabric's 24 kHz synthesis rate, which each `bot_output` message names. It attributes each turn to the participant Attendee reports as speaking during it: Attendee posts `participant_events.speech_start_stop` webhooks to Fabric, which relays them to the bridge, and both use the bot server's clock. A turn nobody was reported speaking in goes to whoever last started speaking within ten seconds; otherwise the speaker is unknown. Bridge logs `parlume.bridge.audio.started` and `parlume.bridge.transcriber.*` trace the audio path, and `parlume.bridge.audio.health` reports every 10 s how many chunks arrived, the longest gap between them, and how many batches went to Flux and events came back. Attendee's Teams bot sends no meeting audio while it posts a chat message. It typed plain text one key at a time (Selenium `send_keys`), about 6 to 7 ms a character, so the bridge heard nothing for 1.0 s after a 117-character post and 4.6 to 9.9 s after posts of 724 to 939 characters. Every 1011 seen on staging followed such a post by about five seconds: Flux closes a stream that hears nothing for five to seven seconds (a 10 s gap closed it about 6.5 s in; a three-minute soak of synthetic audio, at real time and at 1.7×, never did). Attendee pastes a message that contains HTML tags in one step instead, so Fabric sends each post as one escaped HTML paragraph (`<p>…</p>`), which Attendee documents for Teams. The audio the bot drops is gone either way, so the bridge also keeps an open stream fed: after a second without audio it sends Flux 80 ms of silence every 80 ms, a second behind the meeting, for at most thirty seconds, and when audio resumes it sends the rest of the gap as silence at catch-up speed (at most two seconds of it). Against real Flux, a 10 s gap filled this way kept the stream open, and the words after it came back at 17.04 s where the meeting heard them at 16.90 s. The bridge maps Flux's clock, which counts the audio it has heard, back to the meeting's by anchoring each stretch of sent audio to Attendee's timestamps, so a jump the silence does not fill (a longer gap, or audio held for a new stream) no longer shifts later turns or misattributes speakers. Before this, every later timestamp ran early by the length of each unfilled gap. Flux can still close the stream with 1011 for other reasons. The bridge reconnects on the next audio and replays what the new stream needs: the turn Flux had not finished, from three seconds before its start (thirty seconds at most), followed by the audio that arrived while reconnecting. Before this, the sentence being spoken when Flux dropped was lost. Held audio (this replay, and the audio that arrives while any stream connects) goes to Flux at three times real time, live audio queuing behind it until the stream has caught up. Sent all at once, Flux dropped the start of the backlog: replaying a 15 s recording in one burst lost its first 4.6 s and the words just after it, and every later timestamp came back 4.6 s early, so attendees were misattributed for the rest of the stream. In a staging meeting this turned "I think we should move the release to Friday. The testing is not done yet." into "is not done yet." and placed later speech 6 to 7 s early. Paced at 1.5, 2, 3 and 4 times real time, the same recording was transcribed exactly as when streamed live.
- Speaker attribution uses Flux's first-to-last spoken-word timestamps when valid, falling back to processed-audio windows when word timing is unavailable or invalid. A request whose wake phrase comes partway through a turn belongs to whoever spoke from the wake phrase's first word to the end of the turn, found from that word's Flux timestamp; the stored transcript segment stays one segment, attributed to the turn's speaker. When Flux's word times do not line up with the transcript's words, the request falls back to the turn's speaker. A request whose wake phrase is attributed to Parlume's own voice is ignored.
- Payload-free chat instructions such as "Write in the chat" wait for the same identified speaker's dictated message, adding 2.5 seconds of quiet after the last continuation, with an 8-second total cap; complete inline requests retain no extra wait, a new wake replaces the draft, and expiry passes only the captured text to Fabric without inventing content.
- Every webhook must carry its session's token before Fabric acts on it. Each bot's webhook URL carries a random token for its session, which Fabric stores only as a SHA-256 digest (`ParlumeMeetingSession.callbackTokenDigest`) and compares in constant time. The token is revoked, and the digest cleared, once Attendee's data for the bot is deleted, so a webhook URL found later in a request log no longer works. When Fabric has the Attendee project's webhook secret, the delivery must also carry a valid `X-Webhook-Signature`: the base64 HMAC-SHA256 of the payload's canonical JSON (keys sorted, no spaces), keyed with that secret. The secret is that of the Attendee project the bot was created on, which the session records when it starts the bot (`ParlumeMeetingSession.attendeeSource`: `ORGANIZATION` for the organization's own key, **Settings → Meeting assistant**, secret stored encrypted; `ENVIRONMENT` for `PARLUME_ATTENDEE_WEBHOOK_SECRET`). A key the organization saves or removes mid-meeting does not change the check for a bot already running (`resolveParlumeWebhookSecret`). A session from before the source was recorded resolves the organization's current settings, as before. Without a secret, invitations still work and webhooks are accepted on the token alone (logged as `parlume.callback.unsigned`); the readiness checklist shows an advisory, not a blocker. Each handled delivery that carries Attendee's `idempotency_key` leaves a receipt (`ParlumeWebhookReceipt`, keyed by session and that key); a redelivery with the same key is answered as a duplicate and not acted on, and a delivery Fabric refused (a non-2xx answer) releases its receipt so Attendee's redelivery is handled. A delivery without a key is handled as it arrives, with no receipt. The receipts are deleted with the token. A session invited before this check existed has no token digest, so its webhooks are refused; its stream close and the overdue sweep still finalize it.
- Bots are created with `transcription_settings: { enabled: false }`, so Attendee transcribes nothing and saves no captions of its own. Parlume's transcript is the bridge's, from the live audio; the audio stream, the speech start and stop events and the meeting chat are unaffected.
- A private request to the bot is not answered. Parlume can post only to the whole meeting chat, so its answer, and a proposal's quote of the request, would show everyone what was asked privately. The bridge posts `I can only answer in the meeting chat, where everyone reads it. Ask me there.` instead, starts no turn and keeps nothing of the message. A private `stop` or pause still works, and a private `say`, `go` or `more` acts on a post the whole chat already has.
- Replies are spoken a sentence at a time. The worker sends each sentence's text to the bridge as it is written (`?action=say`, newline-delimited JSON); the bridge synthesizes it with Aura and plays it, starting the next sentence's synthesis while the current one plays. Aura streams raw 24 kHz PCM, so the first audio arrives well before a sentence is fully synthesized. Each synthesized sentence is recorded as `CLOUDFLARE_AI` usage (`@cf/deepgram/aura-2-en`, $0.03 per 1,000 characters). When Aura fails on a sentence (an error, no audio, or no answer within 10 s), the bridge asks for it once more after 300 ms and plays it from its start, even when part of it was already queued: the meeting may hear the start of the sentence twice, which is better than losing a clause, and one error does not change the voice. Each retry is logged as `aura.retry` with the sentence index, whether part of it was replayed (`replayed`) and whether the second attempt played (`played`). Only a second failure reports where (`failedAt`, that sentence), and the worker then speaks from that sentence on through the fallback routes as PCM (`?action=speak`), without repeating the sentences already heard. Every answer to a later part of a reply, and to its withdrawal, says how many of its sentences were heard so far (`heard`). When the answer to the opening part is lost, such as when the bridge restarts or the connection drops, the worker withdraws the reply (`x-parlume-reply-cancel`, which also stops a reply the bridge already holds in full) and resumes at the highest heard count it was given, not at the first sentence; with no count at all it starts from the first sentence, as before. A post read aloud gets the same retry, and when it fails twice, the chat gets one line: `**Not read aloud** · My voice failed twice on that read. The text is still here in the chat.` This starts while the agent is still writing the answer, in read-only and actions meetings alike. On the fallback routes, gateway speech returns each sentence's clip whole and the OpenAI Direct route streams PCM as synthesis produces it. Markdown and URLs are not read aloud (a URL is spoken as "the link"). A request that comes with its wake phrase ("Hey Fabric, what is the status?") is handed to Fabric as soon as Flux ends the speaker's turn, with no extra wait. In the classic voice it starts earlier still: the bridge asks Flux for its early end-of-turn (`eager_eot_threshold` 0.5, against 0.7 for the final), starts the request on that guess (`parlume.bridge.turn.eager_started`), and keeps it when the final transcript asks the same words (`turn.eager_kept`). If Flux takes the guess back because the speaker went on (`turn.eager_resumed`), or the final transcript differs (`turn.eager_discarded`), the early answer is cancelled before it is heard and the final request is answered instead. Chat post commands ("Parlume, go P3"), dictation, and any request made while Parlume is already answering wait for the final transcript. A guess taken back costs the start of a model call that is then cancelled. A request that follows a bare "Hey Fabric" waits until the requester has been quiet for 300 ms (8 s cap); the requester's further words extend it, and Flux's empty start-of-turn events do not. The bridge's `parlume.bridge.turn.dispatched` log records `endpointMs` (wake phrase to the end of the request), `handoffMs` (until Fabric accepted it) and `fabricTiming`, the turns route's own steps in milliseconds since its handler started (`sessionMs`, `turnMs`, `claimMs`, `temporalClientMs`, `workflowStartMs`); the difference between `handoffMs` and the last step is the network and the platform's routing. When Fabric does not take the request (the session is no longer live, a newer request superseded it, or it is a duplicate), the bridge logs `parlume.bridge.turn.not_accepted` instead, so a request that was heard but not answered shows in the logs. The request is handed over without waiting for the transcript segments still being posted, which the worker reads once its workflow has started. The turns route imports the Temporal client entry (`@repo/temporal/client`), not the package root: on staging, a turn that reached an instance which had not served the route yet took about two seconds, against 184 ms on one that had. Once the early answer's first audio has played, a guess taken back no longer cancels it: only a stop ends an answer the meeting has begun to hear, and the final transcript is not asked again. Speech over Parlume never stops it, whoever speaks, the requester and an unknown speaker included. Only a stop phrase ends the answer, as **Spoken stop** describes; a new wake phrase waits its turn in the floor's request queue (**Requests that wait** below) and never interrupts the answer. Nothing mutes a reply any more: the interrupt route refuses the `kind: "mute"` report an older bridge sent. A stop phrase heard when nothing is being answered is ignored, and is never started as a request. Speech attributed to the bot itself is never a stop, but attribution comes from Attendee's speaker webhooks, which arrive after the audio, so the speaker of a stop may be unknown. Attendee cannot drop audio it already holds, so a stop or a hold silences a reply within about 200 ms rather than at once. Model generation, transcription and network latency still affect response time; live meeting latency has not been verified.

Spoken replies are tuned for speed. The model gets the least reasoning effort it accepts (OpenAI reasoning models only), the Fabric prompt enhancer is skipped, and the reply reads a small slice of the meeting: the last three minutes of transcript (at most 4,000 characters, the most recent kept), the opening 1,500 characters of three project passages (cut at a line break; whole passages ran to about 11,000 characters), and the last four answered questions. The agent's project search tool still reads whole passages when an answer needs more. The worker logs one `parlume.turn.timing` record per turn: the milliseconds each step took (agent load, decision, project retrieval, transcript and history queries, MCP and workspace lookups, model resolution, and before the model call the MCP connections, Fabric MCP tools, built-in tools, skills and tool preparation as `direct.mcpLoadMs`, `direct.fabricToolsMs`, `direct.builtInToolsMs`, `direct.skillsMs` and `direct.prepareToolsMs`), the model's time to first text and total time with its token, reasoning-token and cached-token counts, and each sentence's speech route, time to first audio byte and total time. When the bot is admitted, the worker also runs the first steps of a turn once (`parlume.session.warmed`) so the first question does not start cold, including one listing of Fabric's own tools from Fabric MCP as the inviter, with an acting grant minted for the warm-up as for a turn (`fabricToolsMs`; the listing took a meeting's first turn 2.5 seconds), and the web app loads the Fabric MCP gateway function, whose cold start had added about a second to a meeting's first answer. The prompt is kept lean without removing a tool: an earlier answer replayed in the history keeps its first 600 characters (the latest is replayed whole, so "continue" works). A meeting turn recalls no memories: the Fabric Agent does not search the inviter's memory, and a project agent loads neither its agent memory (learned instructions, skills, knowledge files, past episodes) nor its `agent-memory` tool, because anyone who can speak in the meeting would hear what they hold. The engine's `System context constructed` log records the characters of the system instructions, each context section, the memory and the history, and the number of tools, so a turn's input can be read off the log.

**Headline, then detail.** A spoken answer is one or two sentences. When more would help, the agent writes a line holding only `---` and then the detail; the worker speaks what comes before the line (at most 350 characters) and posts what follows it, together with anything past that limit when the line is missing, to the meeting chat as one tagged post when the turn finishes. Nothing is dropped: a reply that was spoken over posts everything not heard to its end instead. When the bridge has marked the chat unavailable, the reply speaks its detail too, up to the 45-second spoken budget (`PARLUME_MAX_SPOKEN_CHARS`, 675 characters at 15 a second, in `packages/temporal/src/activities/parlume-voice.ts`; the bridge holds the same budget as `PARLUME_SPOKEN_BUDGET_SECONDS` in `party-cf/src/parlume-chat.ts`), and ends with "There's more; ask me to continue." Live transcription is primed with the single keyterm "Parlume": the Workers AI binding takes one `keyterm` string, and whether it accepts several has not been verified.

**Writing in the meeting chat.** Ask Parlume to share, post or write something in the chat ("put the link to F-123 in the chat", "post that summary") and it calls `post_to_meeting_chat`. The tool works in read-only and actions meetings alike, because it changes nothing in Fabric, and it sends at most three messages per answer. `text` is sent as the participant asked, URLs included. `links` are resolved by the worker from the meeting's own project, after an access check, into full direct addresses: a work item by identifier (`F-123`, `123`, `B-9`) or id, a document by id or exact title, a Context source by id, a project tab (Overview, Daily Brief, Meeting Digest, Release Notes, Documents, Decisions, Context, Roadmap, Testing or Coding Instructions), or the repository the project's Coding Instructions sync from (its https address, without credentials or `.git`). A reference outside the project is refused and reported back, and the addresses use the project's own organization, so they work for guests of another organization's project. When no link can be found and there is no text, nothing is sent and the tool tells the agent so, with each link's reason, so the agent reports the failure rather than restating the request. The message is the text, then one link per line (`F-123 · Title — https://…`), within one post's 1,490 characters; the text is shortened before any link is dropped. It is laid out like every other post (see **How posts look**). A tab named the way people say it ("the Coding Instructions page", "roadmap tab") resolves to that tab, and the repository link needs no reference. An answer typed in the chat or passed back to the realtime voice is posted by Parlume itself, so its agent does not call `post_to_meeting_chat`; it calls `get_meeting_links`, which resolves the same links the same way and posts nothing, and writes each address on its own line. If the HTML would take a post past Attendee's 10,000 characters, it is sent as escaped lines without links, cut to fit. Each send is logged as `parlume.chat.posted` (the event keeps its name) with `sent`, `delivery: "queued"`, the post's tag and counts, and no content.

**Delivery is confirmed, not assumed.** Attendee only queues a chat message: its Teams bot drops one silently when the meeting gives it no chat box, and reports it sent anyway. So Parlume never says a message is in the chat because Attendee accepted it. The tool answers `{ sent: true, delivery: "queued", tag }`, and the agent says it has *sent* the message. Every Parlume post opens with a short tag, `[P1]`, `[P2]` and so on, numbered in the bridge, which keeps every post of the session (tag, text, request), each under its own storage key, so `go` plays an offer however old it is while the session lasts. Before Fabric has the bot leave (a stop, the idle rule, the four-hour cap, a guest policy, lost access, a failed stream), it calls the bridge's `?action=leaving`, and the bridge posts once "Unavailable: P3 to P5, P8. This meeting has ended for Parlume, so its earlier answers can no longer be played." when the session offered anything. It names only answers and offers Fabric took to send, consecutive tags as a range, never a notice or a post Fabric refused. A line Fabric refuses is tried again by a later `leaving` call, calls at the same time post one line, and a call with no bot in the meeting stores nothing. Fabric gives each `leaving` call four seconds, since the bridge's own calls that lead to a leave allow 15 seconds in all. A meeting that ends on its own takes the bot with it, so no line is posted then. Teams through Attendee cannot edit or disable a posted message, so earlier posts are not marked one by one. A session continues the meeting chat's numbering, so a tag never names two posts in one chat: when Parlume is invited to a meeting it was in before (the same meeting link, within the organization), Fabric counts the tags earlier sessions posted there (the highest tag Fabric relayed for each session, `lastChatTag`, which also covers the notice a session posts as it leaves and whose echo arrives after the session has ended; the bot's own tagged messages the chat showed back; and the channel posts they made; `parlumeChatTagStart`), and the bridge starts after them (`chatTagStart` on the request that arms it). The meeting is stored as its path without a trailing slash, query or fragment (`teamsMeetingJoinUrl`), so a short link's passcode (`?p=`) is never kept. Teams on the web carries the path in its fragment (`/v2/?meetingjoin=true#/l/meetup-join/...`, `/_#/l/meetup-join/...`, `/v2/#/meet/<id>?p=...`), and it is taken out of there, so the web link is the same meeting as the invitation or short link it opens. A link that names no meeting, such as the web client's bare `/v2/`, is not stored and starts at P1: stored, it would continue the tags of every meeting invited that way. Teams join links are compared by `teamsMeetingIdentity`, the decoded path, however either link encodes the thread id; a short `/meet/<id>` link whose invitation Fabric could not resolve counts only the earlier sessions invited through the same short link. Fabric subscribes each bot to Attendee's `chat_messages.update` webhook. A chat message that opens with a waiting post's tag, or comes from the bot's own name, confirms that post (`parlume.bridge.chat.confirmed`, with its latency). A post not seen within 15 seconds is logged as `parlume.bridge.chat.unconfirmed`. If the bridge has seen no chat message at all since the bot joined, it marks the chat unavailable (`parlume.bridge.chat.unavailable`) and Parlume says once, aloud: "I can't write in this meeting's chat. Guests may not have chat here." Later `post_to_meeting_chat` calls then answer `{ sent: false, delivered: false, reason: "chat_unavailable" }` at once, so the agent says the content instead. Any chat message seen later clears the mark. The bridge reports each outcome to `/api/internal/parlume/chat-delivery` (`parlume.chat.delivery`). A post that never appeared, or appeared late, adds a note to its request in the Requests list. The route also stores the outcome on the post's own row (migration `20261121130000_parlume_chat_post_delivery`): a request's answer, detail, rest and error posts put their tag in `ParlumeMeetingTurn.chatTags` when the chat showed them and in `chatUnshownTags` when it did not, a late echo moving the tag from the second to the first; a suggestion's post, and the recap (a reply with no turn, matched by its `RECAP` row's `chatTag`), set `ParlumeSuggestion.chatDelivery`, and a proposal's post sets `ParlumeAction.chatDelivery`, to `SHOWN` or `NOT_SHOWN`. The Parlume page shows "Posted as P7" and "Not shown in the chat: P9" on a request, "Action · Posted as P8" or "Action · Not shown in the chat (P8)" on a proposed change, and "Posted as P8", "Not shown in the chat (P8)" or, before any report, "Sent to the chat as P8" on a suggestion. A notice belongs to no row. A reply that could not be spoken goes to the chat as one tagged post, and its request records the tag that carried it. Whether a Teams bot's own messages come back through `chat_messages.update` has not been verified. If they do not, a meeting where nobody has typed yet will be marked unavailable after Parlume's first post.

**Reading the meeting chat.** Every message in the meeting chat, the bot's own included, is stored with the meeting's transcript segments (`ParlumeMeetingSegment.source = CHAT`), placed on the same clock as the speech around it and stored once per Attendee message id. A private message to the bot (Attendee's `to: "only_bot"`) is not: the bridge stores no segment for it and leaves it out of the recent chat it hands requests, so it is kept only as the request it makes (`ParlumeMeetingTurn.requestText`). A spoken or typed request gets the last 20 chat messages, at most 2,000 characters, as a separate "Recent meeting chat" block, so "Parlume, what did they write in the chat?" works. The spoken transcript block no longer includes chat lines. In the saved transcript and the notes, chat lines are marked `[chat]`.

**How posts look.** Every post other than a suggestion and the recap, whatever wrote it (an answer, a voice reply's detail, a realtime job's result, `post_to_meeting_chat`, a notice), is formatted the same way. A suggestion and the recap are `plain` posts (the bridge's `plain` flag, through `/api/internal/parlume/chat` to `parlumePlainChatHtml`): one escaped paragraph, with no lines, links or emphasis, as before the meeting-chat readability work, which does not cover them. Attendee documents `<p>`, `<br>`, `<b>`, `<i>` and `<a>` for Teams chat and renders no Markdown, so the bridge drops headings and rules but keeps bold, italics and `[label](address)` links for Fabric to render, turns list items into "•" lines (numbered items keep "1."), and keeps one blank line as a paragraph break. Fabric then sends HTML: a paragraph per block and a line per line, a long single first paragraph opened by its first sentence as a lead line, and each link shown by its title (`Title — address`, `Title: address`, `[title](address)` and a short title line followed by a line holding only its address link the title; a line that ends a sentence or opens a list, such as "Here are the pages:", is not a title; a bare address shows its host and path, at most 48 characters, never its query string, and the "…" a shortened post adds after its last address stays out of the link). A post holds at most 600 characters, tag and header included, and at most eight non-blank body lines under its header (`PARLUME_CHAT_MAX_CHARS`, `PARLUME_CHAT_MAX_LINES` in `party-cf/src/parlume-chat.ts`; with a 1,500-character cap, a staging answer posted as 10 lines and 1,438 characters). A longer one is cut at its eighth line, or at a paragraph, line, sentence or word, and ends with `Shortened for the chat. Reply "more P6" for the rest.` A proposal (post kind `proposal`) is never shortened: its template bounds each of its six lines, and its Confirm and Dismiss links must not wait behind `more`. When the part left out reports something that did not complete or could not be confirmed ("unavailable", "unconfirmed", "failed", "could not", "did not" and the like), the post ends with that sentence quoted, `Shortened for the chat. The rest also says: “Tracker sync unavailable.” Reply "more P6" for all of it.`, instead: the rest's own words, never a summary that could claim a failure the rest does not state, so a confirmation that opens with "Created F-12" does not read as full success while a sync that was unavailable or an assignment that was not confirmed waits behind `more`. The chat answer's instructions ask for the answer in one short line, then short lines or a simple list, at most eight short lines and within 360 characters (`PARLUME_CHAT_ANSWER_CHARS`, which leaves room for the longest header; a `post_to_meeting_chat` post, which has no header, keeps within `PARLUME_CHAT_POST_CHARS`, 590), with each link on its own line as `title — address`, and tell the agent not to repeat the question or name the asker. A list the participant asked for ("12 tips", "every open feature") is the exception: the agent writes every item, one per line, and the bridge shows the first eight with the `more` line. With the eight-line rule alone, a staging request for exactly 12 tips got 7 and no word that 5 were left out. The bridge keeps the whole text, which is what `say`, `go` and `more` use.

**Post headers.** A post for a request opens with two lines the bridge writes from the turn, never from the model (`party-cf/src/parlume-post-templates.ts`): the tag and a bold label, then the request in italics, cut to 120 characters, with the marks the chat would read as emphasis or a code span taken out. The worker sends the turn's asker and request on `?action=chat` as `header: { kind, asker, request }`, where `kind` is `answer` (a typed request's reply, a reply that could not be spoken, a realtime job's result), `detail` (what a spoken reply left for the chat) or `error`; the labels are `**Answer** for Sam`, `**Detail** for Sam` and `**Could not answer** Sam`, or the label alone when Fabric could not tell who asked. The rest that `more P7` posts opens with `**Rest of P7**`. The header is stored with the post (`ParlumeChatPost.header`), is never shortened and never read aloud, and the bridge leaves room for it before it shortens the body, so the rest that `more` posts is the same either way. `post_to_meeting_chat` posts and proposals carry no header: a proposal has its own **Proposed change** template, and a tool post is the content the participant asked for. Notices open with their own bold label. Suggestions and the recap stay one plain paragraph with no header, as above: suggestions and the recap stay plain by an earlier deliberate change, a deliberate departure from the plan's suggestion and recap templates. `Parlume, help` posts a notice that lists what can be typed (`PARLUME_HELP_TEXT`).

**Error posts, and quiet stopped requests.** When a turn fails (`failParlumeMeetingTurn` with a `chatReason`: `failed` for an agent that failed or threw, `timed_out` for the workflow's timeout) and that write is the one that ended it, the worker posts the error template, marked final so a typed request's lane is free at once: `I could not finish the answer. Ask again in a minute.` or `The answer took too long. Ask again in a minute.`, then a `[Parlume page](…)` link (`buildParlumePageUrl`). The internal error stays on the request's `error` and never reaches the chat. No error post is made for a request no longer wanted (the session or generation changed), an inviter who lost access (Parlume leaves), a realtime job (its voice says that it failed), a turn whose activity was cancelled, or a turn the interrupt route already ended: a stop records STOPPED, and a newer request or a closed meeting connection records FAILED with "Ended before the answer finished…", so the failure write changes nothing and nothing is posted. Fabric's `/api/internal/parlume/chat` checks every post that names a turn before it counts the tag or sends anything (the bridge forwards `turnId`, and `turnFailed` for an error post): a STOPPED turn posts nothing, a FAILED turn posts only its error line, an error line goes out only for a FAILED turn, and PENDING, RUNNING and COMPLETED turns post as before (a realtime job's answer is posted after its turn is recorded COMPLETED). A refused post answers 409, and the bridge forgets its tag as it does for any post Fabric did not take. The rest `more` posts names no turn to Fabric, so a stopped request's earlier post can still be continued. A meeting in a Teams channel posts through Microsoft Graph the same HTML (`contentType` `html`, from `parlumeChatHtml`), with the tag first and "Fabric Parlume:" after it. Fabric checks each channel post by reading it back: the request digest (`ParlumeChannelPost.requestDigest`) covers the visible text of the HTML it sent, lines trimmed and blank lines dropped, and the read-back digest covers the visible text Graph returns, so markup Graph rewrites around the same text still matches.

**Typing to Parlume.** Teams chat has no buttons, so a post's tag is the handle. A message addressed to Parlume (an @mention of the bot, a message that opens with "Fabric Parlume", "Fabric," or "Parlume,", "Hey Fabric …", or a private message to the bot) becomes a request like a spoken one (`ParlumeMeetingTurn.replyChannel`). It never cuts what Parlume is saying or answering: it waits in the voice floor's request queue (**Requests that wait**) until no reply is being spoken, read or answered, and a chat answer then takes the voice generation that is current, so it starts no new generation and supersedes nothing. Its answer goes back to the chat as one tagged post, without being spoken. A request that asks to be said aloud ("say …", "tell everyone …", "announce …", "… out loud") is answered by voice, on a generation of its own with its typer as the asker; in the realtime voice the realtime voice answers it, after what it is saying. A stop ends only the current answer: a typed request still waiting keeps its place, and starts on the generation after the stop. Short commands work whether or not they are addressed: `say P7` reads post 7 aloud, `go P7` speaks suggestion 7 or reads any other post aloud, and on a proposal (post kind `proposal`) posts `P7 is a proposed change. A signed-in member confirms it in Fabric: [Confirm P7 in Fabric](…)` and starts no turn, `more P7` on a proposal posts the same link, and otherwise posts the rest of post 7 when it was shortened (from the text the bridge kept, as a new tagged post that is shortened again if it is still too long; `chat.more_rest`) and otherwise asks for more on post 7 with the answer in the chat, and `stop` stops what Parlume is answering, as a spoken stop does. Typed and spoken post commands share one grammar (`parseParlumeSpokenReference` in `party-cf/src/parlume-wake.ts`, which `parseParlumeChatCommand` calls): `say` or `read`, `go`, `go with` or `go ahead with`, `more`, `more on`, `more about` or `tell me/us more about`, an optional `please` and `post`, the tag as `P3`, `[P3]`, `P 3` or in words, and a closing `.`, `!` or `?`. The verb always comes first, so a message that opens with a tag is never a command (the bridge also takes any message that opens with a tag for Parlume's own post). `continue` keeps its own rule, and an addressed `help`, `commands` or "what can I type" posts the help notice; a bare `help` is left to people. A private `help` posts the help notice to the whole chat, which shows nothing of what was asked. A `say` or `go` that reads a post aloud never cuts what Parlume is saying, and never cancels a Fabric turn or job: the read waits for the classic speech or read before it, and for the realtime voice to finish what it is playing, and reads play in the order they were asked for, the asker of each being its typer or speaker. While the bridge reads the post word for word with Aura, the realtime voice holds a response that has not been heard yet, and running jobs and the answers queued for them are spoken after the read. A spoken `go` on a proposal posts the same link and says one sentence pointing to it, or, when the link cannot be posted, says that the change waits on the Parlume page; it starts no turn and confirms nothing. A `say`, `go` or `more` that names a tag the session has no post for plays nothing and is answered with a notice (`parlumeMissingPostLine`): a tag at or past the session's next number, which no post carried, gets `[P12] P20: There is no P20 in this meeting's chat. Check the tag on the post you mean.`, and one the session issued but no longer has (a post Fabric refused) gets `[P12] P3: This prepared answer is no longer available. Ask me again.` Every notice is a post of kind `notice` with its own tag, confirmed and reported to `/api/internal/parlume/chat-delivery` like any other post, and commands on a notice work as on an answer. Fabric renders bold, italics and `[label](address)` links as HTML, so the bridge keeps bold marks in a post. A tag below the session's first number was posted by an earlier session in the same meeting, which has ended: it is answered with `P1: This meeting has ended for the Parlume session that posted it, so it can no longer be played.` (aloud when the command was spoken), and no other post is played or asked about in its place. Once the session has ended the bot has left the meeting, so a later selection gets no answer at all; the leaving line (`?action=leaving`) is what tells the meeting, naming the posts that can no longer be played and, apart from them, the proposed changes that stay on their pages in Fabric. A `more` request tells the agent that the tag only labels Parlume's own chat message, with the post's text: given just "more detail on P1", the agent in a staging meeting looked for a work item P1 and answered that there was none. The realtime voice instructions say the same, so the voice describes a post rather than passing its tag to `ask_fabric` (migration `20261026150000_parlume_voice_chat_post_labels`). The bot's own messages are never treated as commands, and a redelivered webhook is recognized by its message id. Text read aloud from a post, in either voice, reads a link's title or "the link" for a bare address, never a formatting mark ("•", "1.", `#`, `**`), and ends each line as a sentence, so a list is read item by item. That speech is synthesized in the bridge, which reports it to `/api/internal/parlume/speech-usage`, and it is recorded in the session's usage as Aura speech.

**Suggestions.** While the meeting stream is live and Parlume is neither speaking nor answering, the bridge runs a suggestion pass once at least two new final speech segments have arrived since the last pass and 45 seconds have passed since it; a meeting's first pass waits for no interval. The segment that makes a pass worth running brings the Durable Object's alarm forward to the moment the pass is allowed; otherwise it would wait for the next access check, up to a minute away, which on staging put passes about 90 seconds after the remarks they answered. A pass Parlume cannot run because it is speaking or answering is tried again five seconds later. No pass runs while the chat is marked unavailable, unless the session's suggestions are for the team only, which needs no chat. The bridge learns the audience when Fabric verifies the stream (`/api/internal/parlume/verify-stream` returns `suggestionAudience` beside `suggestionsEnabled`), so a team-only session runs passes even when its chat went unavailable before the first one; bridge state from a Fabric that predates audiences reads as `MEETING`. A pass posts to `/api/internal/parlume/suggest`, which reads the last three minutes of speech, the meeting's earlier speech (the most recent 10,000 characters before those three minutes, about ten minutes of conversation), the recent chat, the earlier suggestions, the project's open work items (up to 40, highest priority first, each with its identifier, title, status, priority and owner) and three project passages, and, for a session of a linked series, the occurrence's ready agenda (`ProjectMeetingAgenda` with status `READY`, resolved on the UTC day of the occurrence's start, or of the invitation for a session invited by hand, as the Meeting Digest's agenda sheet resolves it) and the open questions of the series' latest synced transcript from before the occurrence (within 90 days, at most ten). Each is fenced as untrusted data (`earlier_meeting`, `agenda` and `previous_meeting_questions` for the three new inputs), and the agenda and previous questions are left out when they cannot be read. The pass sends one user message in two parts: first what the meeting's passes share (the agenda, the previous questions and the work items, listed in a fixed order), then the meeting itself (transcript, earlier speech, chat, passages and earlier suggestions), so the instructions and the shared part form a prefix that repeats from pass to pass. For a direct Anthropic model, or a Claude model through the Vercel AI Gateway (`isPromptCacheTarget`), the shared part carries an ephemeral cache breakpoint (`ANTHROPIC_EPHEMERAL_CACHE`), so a pass within five minutes of the last one reads that prefix from the cache, once it is longer than the model's minimum cacheable length; other providers get the same order with no marker, and those that cache long prefixes on their own can reuse it. It asks the organization's fast model (`SIMPLE`, simple complexity) for `{ suggest, kind, text, speaker, quote, topic }`: whether it is an answer or a missed question, the suggestion, who made the remark it is about, a few of their words, and what it is about in a few words. **Missed questions.** A missed question (`kind` `missed_question`) is a question the meeting should ask but has not, that the current discussion makes timely: the topic being discussed belongs to an agenda item or an open question from the previous meeting nobody has covered yet, or the discussion clearly leaves open a question a newcomer or a client would need answered. The instructions forbid generic checklists and questions already asked earlier in the meeting. Its `text` is the question, and its speaker and quote point at the remark that opened the topic, which may be in the earlier speech; an answer must quote the last three minutes. A missing or unknown `kind` is an answer, so an edited prompt that never mentions it keeps working. The instructions are the seeded, bindable **Parlume Meeting Suggestions** prompt (`parlume_meeting_suggestion`, under Meetings & Intake). They ask for a suggestion when the work items or passages answer a question someone just asked (what is open, what has the highest priority, who owns something, what state it is in), contradict or complete something just said, or when a decision is drifting without an owner, and for nothing otherwise. The passages leave out transcripts of earlier meetings (`MEETING_TRANSCRIPT` contexts): they are what people said, not the project's state. On staging a project's knowledge held only such transcripts, so every pass saw earlier meetings' copies of the same remarks and no facts, and the model declined five passes in a row while the room asked which feature had the highest priority. The work items answer those questions directly. Migration `20261026190000_parlume_suggestion_work_items` carried that wording to deployed environments, and `20261104130100_parlume_missed_question_suggestions` carries the missed-question wording; each rewrites the seeded prompt only while it is still the previous default. The model's output is read leniently: anything malformed counts as no suggestion, and so does one whose quote is not in that speaker's transcript lines (logged as `suggestion.unanchored`), which keeps a suggestion from answering a remark nobody made. Usage is recorded under the `parlume` feature key with the session id as `conversationId`. The model gets 1,500 output tokens because its reasoning counts against them: with 300, a staging pass spent the whole budget and returned nothing (`suggestion.failed`, "the model did not return a response"). Passes run often so a suggestion lands while the room is still on the topic (on staging, one came about 70 seconds after the remark when passes ran every 90 seconds), but the bridge posts at most one suggestion every two minutes and ten an hour. It drops one that answers a remark already answered within the hour, or that shares most of its words with a suggestion from then. A suggestion reads, a line each, `[P8] **Suggestion** · Export owner` / `Re Alex: “who owns the export”` / `…` / `Type "go P8" and I will say it.`; Parlume speaks it only when someone replies `go P8`, as "Alex, on Export owner: …". A missed question reads `[P9] **Possibly missed question** · Data migration` / `Re Alex: “we move the data in March”` / `Who signs off …?` / `Type "go P9" and I will ask it.`, and `go P9` speaks "A question we may not have covered on Data migration: …". **Who sees suggestions.** Each session has an audience (`ParlumeMeetingSession.suggestionAudience`): **Everyone in the meeting (chat)** (`MEETING`) posts as above, and every participant, external guests included, reads it; **Only your team (Parlume page)** (`TEAM`, the default for new sessions and newly linked series) posts nothing in the chat. Migration `20261118140000_parlume_meeting_privacy` changed only the column defaults: existing series and sessions keep the audience they were saved with. The suggestion route answers with the session's current audience on every pass. The bridge says it can keep a suggestion off the chat (`teamAudience: true`), and the route gives a team-only session no suggestion through a bridge that does not, so an older bridge cannot post one to the meeting. The bridge posts a suggestion in the chat only when both the verified audience and the pass's answer say `MEETING`; on any disagreement it treats the suggestion as team-only, and it drops one whose answer carries an audience it does not know. An answer without a suggestion changes nothing. Team-only suggestions count toward the same limits and duplicate check. Every accepted suggestion, whoever it was for, is recorded as a `ParlumeSuggestion` (kind, audience, text, speaker, quote, topic and, when it was posted, its chat tag) through `/api/internal/parlume/suggestions`, which takes the project, organization, owner and audience from the live session whose bot the bridge verified, and ignores any audience the caller sends; a failed record is logged (`parlume.bridge.suggestion.record_failed`) and the meeting goes on. The Parlume page lists them, newest first and at most 50, under the live card (refreshed every ten seconds) and in a finished session's details, each with its kind ("Suggestion", "Possibly missed question" or "Recap"), topic, speaker and quote, text, time, and where it went: "Posted as P8" once the chat showed the post, "Not shown in the chat (P8)" when it did not, "Sent to the chat as P8" before the bridge reports either, "Team only", or that the chat did not take it. A quote is what someone said, word for word, so `projects.parlume.suggestions` returns it only to those who may read the meeting's transcript (the inviter and project managers, `canReadParlumeTranscript`); other project readers get each suggestion with `quote` null, and the page leaves the "Re …" line out. "Sent" means the bridge queued the post: the record is written once and is not updated if delivery later turns out unconfirmed. One failed refresh keeps the items already shown, with a note, rather than replacing them with an error. Deployed environments get the new prompt wording from migration `20261026160000_parlume_anchored_suggestions`, which leaves a prompt edited after seeding alone. An edited prompt that never asks for the speaker, quote and topic produces no suggestions. **Suggestions and recap** is on by default in the invite form and can be switched off per invitation (`ParlumeMeetingSession.suggestionsEnabled`); the bridge learns the setting when the stream is verified, and the suggestion route checks it again. While it is on, the invite form asks **Who sees suggestions**, with **Only your team** chosen by default. A suggestion is model-written text: it may be wrong, and something said in the meeting may steer it. It can only be posted in the chat or read aloud on request; it calls no tools.

**Since last time.** When Parlume is admitted to a meeting of a linked series (an automatic join, or an invitation with the series' link), it posts one short recap in the chat before anyone asks: what the previous meeting of the series decided and left open, and the project's work items created or edited since. **Suggestions and recap** controls it as it controls suggestions: switched off in the invite card, or for an auto-join series in Configure meetings, the session posts no recap (`parlume.recap.skipped` with `suggestions_off`). It is never spoken unprompted; `say P1` reads it aloud like any other post. The recap follows the session's audience: for a team-only session it is not posted in the chat but recorded as a `RECAP` `ParlumeSuggestion` for the Parlume page (`parlume.recap.recorded`); a recap meant for the chat is recorded too, with its tag when the post was taken and without one when it was not, and a failure to record that copy is logged (`parlume.recap.record_failed`) without counting as a failed recap. The first admission of a session, not a reconnect, starts `parlumeRecapWorkflow` under the id `parlume-recap-<sessionId>` with `REJECT_DUPLICATE`, so a session gets at most one recap. The previous meeting is the series' latest earlier Parlume session in the same project, by when its bot was admitted, whose notes were written (`parlumeNotesStatus` `COMPLETED`); without one, it is the series' latest synced transcript, with its summary, decisions, open questions and open action items. Either must be from the last 90 days. The work items come from the daily brief's collector, from the end of that meeting (or its start, for a transcript) to now, at most 15, each marked created or edited, with its current status. The material is fenced as untrusted data and given to the organization's fast model (`SIMPLE`, simple complexity) with the seeded, bindable **Parlume Series Recap** prompt (`parlume_series_recap`, under Meetings & Intake), which asks for a "Since last time" line and at most five bullets. Usage is recorded under the `parlume` feature key with the session id as `conversationId`. With Suggestions and recap off, no previous meeting, a model that finds nothing to recap, or a meeting Parlume has already left, nothing is posted. The worker logs `parlume.recap.posted` (source, work item count, length, and the post's tag or why it was not sent), `parlume.recap.skipped` with the reason, or `parlume.recap.failed`; none of them carry the recap's text. A recap is model-written text and may be wrong.

**Realtime voice.** The classic chain of Flux, the agent and Aura is the default. Parlume talks through an OpenAI Realtime speech-to-speech session (`gpt-realtime-2.1`) only when the organization's **Voice** card names a realtime deployment and its **Azure AI Foundry** resource is set; an OpenAI Direct key is never used for meeting audio. Once the stream is verified, the bridge asks `/api/internal/parlume/realtime-session` once. That route checks the session is live and the inviter still has access, refuses when the session has a guest (`externalInvitees` or `guestJoinedAt`; reason `guests`), resolves the deployment and the Azure resource (reason `not_configured` without either), and mints a short-lived client secret on that deployment (`POST <resource>/openai/v1/realtime/client_secrets` with its `api-key`) whose session carries the instructions, three tools and the audio settings. Azure refuses the mint when the resource has no such deployment (`400 OpperationNotSupported`); the refusal is logged as `parlume.realtime.mint_failed` with the host's own reason, and the meeting stays on the classic voice. The deployment must be in a region that offers the model (East US 2 or Sweden Central); the deployment named in the AI provider's settings is for chat and is not used. A guest arriving later ends the realtime session for the rest of the meeting, and the classic voice, which stays silent while the guest is in, takes over. Azure documents client secrets for WebRTC; a secret minted this way also opens a WebSocket session (checked against an East US 2 resource on 2026-10-24). The session keeps the model's default reasoning effort, so answers stay considered: on that resource a short greeting spent 119 reasoning tokens and its first audio came 2.0 s after `response.create`, against 1.6 s at low effort (one sample each). The answer names the realtime API the secret was minted on (`realtimeUrl`), and the bridge opens only `api.openai.com` or an Azure resource host. The keys themselves never leave the web API and are never logged; the bridge only holds the secret. With no key, every mint refused or a socket that will not open, the route answers `404 { engine: "classic" }` or the bridge gives up, and the meeting uses the classic voice. The choice is logged as `parlume.bridge.engine` with the engine and the reason. A realtime voice that cannot be kept up, a session Fabric minted that the bridge could not open (`connect_failed`) or one whose reconnects all failed (`reconnect_failed`), is logged as `parlume.bridge.engine.fallback` and counted in the speech telemetry (see **Speech telemetry**). The instructions are the seeded, bindable **Parlume Realtime Voice** prompt (`parlume_realtime_voice`, under Meetings & Intake), followed by the project name, whether changes are allowed and who has spoken so far, fenced as meeting data. The session speaks with OpenAI's `marin` voice. The default instructions ask it to sound like a person on the call rather than an assistant: contractions and plain words, varied openings, a small natural reaction where it fits, the room's tone, and at most one filler in an answer. Migration `20261026120000_parlume_voice_natural_speech` carries that wording to environments seeded with the earlier text, and leaves an organization's edited prompt alone.
- The bridge opens the session itself (`wss://<resource>/openai/v1/realtime`, with `?model=gpt-realtime-2.1` and the secret sent as a bearer header only; OpenAI closes a session that also carries it as a subprotocol). It streams the meeting's audio into the session only from a wake phrase to the end of Parlume's reply, resampled from Attendee's 16 kHz to 24 kHz and appended in 100 ms batches (`ParlumeRealtimeAudioWindow` in `party-cf/src/parlume-realtime-listening.ts`). The bridge holds the last five seconds of audio, so the request that carries the wake phrase is sent in full when Parlume is addressed; the window stays open while a response is wanted, running, queued or playing, and when it closes the bridge clears the session's input buffer (`input_audio_buffer.clear`). The rest of the meeting never reaches the Realtime session. Flux keeps running on all of the audio for the transcript, speaker attribution, wake detection and notes. The session's voice activity detection (`semantic_vad`) reports when speech starts and stops, but `create_response` and `interrupt_response` are off, so the session never answers on its own. The bridge creates a response only when someone says a wake phrase (in a Flux partial or final) and then stops talking (OpenAI's `speech_stopped` or Flux's end of turn, whichever comes first), when a chat message asks for a spoken answer, or when a Fabric job has a result. A post read aloud (`say P7`, `go P7` on a suggestion, the chat-unavailable notice) is not a model response: the Realtime API has no call that speaks given text without generating a response, and a response asked to read a post as written is not bound to its words. The bridge synthesizes the text with Aura, word for word, and plays it on the same outlet the realtime voice uses (24 kHz, the same 200 ms lead), in Aura's voice rather than the realtime one. A read never cuts what the realtime voice is playing: it waits for the voice to go quiet and for the read before it, so reads play in the order they were asked for. Meanwhile the realtime voice holds (`holdForRead` in `parlume-realtime-engine.ts`): a response that has started but is not yet heard is cut short and truncated to what was heard, and nothing starts until the read has played. Running jobs, the answers queued for them and a Fabric result the read held back are spoken after it. A read played in full is added to the conversation as a system note saying it was read aloud to the meeting, word for word, so the voice knows what the meeting heard without taking the words as its own; a read cut short is not. A stop or a new turn releases the hold at once, and each Aura sentence that has not started answering within 10 seconds fails, so a hung synthesis cannot keep the realtime voice silent. The voice is played through the same outlet as the classic voice, 24 kHz with the same 200 ms lead.
- Stops follow the classic voice (**Spoken stop**): talk over the realtime voice never stops it, its requester's included, and only a stop phrase does. An addressed stop in a Flux partial holds the outlet; the stop on the final cancels the response (`response.cancel`) and cuts the assistant's audio item to what the meeting actually heard (`conversation.item.truncate`, from the bytes the outlet sent; `parlume.bridge.realtime.truncated`), and the conversation goes on. A spoken stop or `stop` in the chat also cancels a running Fabric job, as `/api/internal/parlume/interrupt` does for the classic voice. A stop phrase is never answered: a partial "Parlume," arms the realtime voice to answer when the speaker stops, and the stop that follows, partial or final, disarms it. In a staging meeting, "Parlume. Stop." was once followed 2.3 s later by a new reply, because the model's own turn detection heard the speech end. Arming also expires: a wake phrase not refreshed by a partial for 5 s is dropped when the voice next hears speech end (`parlume.bridge.realtime.arm_expired`), and a partial whose audio ends before the latest final transcript never arms. Transcripts are handled concurrently, so a partial of a request could be handled after that request's own final and arm Parlume again; on staging it then answered other attendees' side talk eleven seconds later. `parlume.bridge.realtime.armed` records each arming (whether it came from a final, and whether the requester was named), and `realtime.connected` reports `seeded: true` only when the new session was given the meeting so far.
- The session has three tools. `ask_fabric({ request })` hands anything that needs project knowledge, Fabric data or a change to an ordinary meeting turn (`/api/internal/parlume/turns` with `delivery: "realtime"` and a job number such as `J3`), recorded like any other request, with the same actions policy, audit, receipts and history. The tool answers at once with `{ status: "started", job }`, so the voice says a holding line and the meeting carries on; one job runs at a time. Another participant's request made while a job runs answers `{ status: "queued" }` and is handed to Fabric as soon as that job's result comes back (`parlume.bridge.realtime.job_queued`); the same asker asking again, or an asker the bridge could not place, gets `{ status: "busy" }`, since that is the request already running. Waiting requests are not kept across a bridge restart. Parlume says it is on a job at most once every ten seconds: when the answer that called `ask_fabric` already spoke, or a holding line was said in the last ten seconds, the bridge gives the session the tool's answer without asking it to speak again (`parlume.bridge.realtime.holding_skipped`). A request the bridge resolves itself, such as "more on P1", is not answered a second time when the voice already answered the same utterance from its wake phrase (`parlume.bridge.realtime.request_already_answered`). Before this, one "tell me more about P1" on staging produced three spoken lines in six seconds. The worker runs the agent as usual but speaks nothing: it releases the turn, posts an answer longer than 350 characters to the meeting chat in full, and posts the answer to the bridge (`?action=fabric-result`). The bridge waits for any response in progress to finish, adds the answer to the conversation labelled as the result of that job, and has the voice say it. If the bridge can no longer take it, the answer goes to the chat. The worker names the job's turn in `fabric-result`; when the voice plays that answer, the bridge reports when its first audio was queued and when it finished playing, or that it was cut short, to `/api/internal/parlume/realtime-spoken`, which records `firstAudioAt`, `spokenAt` and `interruptedAt` on the turn as the classic voice records its own. `spokenAt` is taken when that answer's own audio has played, not the speech queued after it; an answer dropped before it was spoken (a cancel, the session ending or dropping, or a response the server refused) is reported as cut short. `post_to_chat({ text })` posts a tagged, delivery-confirmed chat message, but refuses one that holds a web address that did not come from a Fabric result or the meeting chat (`{ posted: false, reason: "address_not_from_fabric" }`, `parlume.bridge.realtime.chat_address_refused`) and tells the voice to ask Fabric. Addresses are compared without scheme, `www.`, case or a trailing slash, so a Fabric link restated as `example.com/app/board` still passes. An address is a scheme or `www.` form, or a bare host such as `example.com` with or without a path whose lower-case top-level domain is a common web one, so `Node.js/React`, `ASP.NET`, file names and email domains are not taken for addresses. The addresses Fabric gave (the latest 200) are saved with the realtime context and survive a bridge restart. A request for a link to a project page, work item, document or repository goes through `ask_fabric`, whose turn resolves addresses with the same meeting-link lookup as typed and spoken requests, in the meeting's project, or says it could not find them. The tool descriptions and the default instructions say so; migration `20261118160000_parlume_voice_links_via_fabric` carries the instruction to environments seeded with the earlier text, which sent links to `post_to_chat`. `read_chat({})` returns the last 20 chat messages the bridge saw. The session can change nothing in Fabric by itself. Tools run after their response is done (`answerCalls`, not awaited by the done handler), and the queue moves on at once, so the spoken follow-up to a slow `post_to_chat` can play after another queued response. Nothing is lost; holding the floor while a tool runs would delay all other speech by up to the chat timeout, so the order is left as is.
- OpenAI ends a Realtime session at the `expires_at` its `session.created` event gives (60 minutes when it gives none). From 10 minutes before then, at the first quiet moment (no response in progress, nothing playing, no read aloud), the bridge opens a new session with a fresh secret and seeds it with the meeting so far (the last 40 transcript lines, Parlume's own replies included), then closes the old one. From 2 minutes before, no new response starts: the one in progress ends, and the session is replaced. From 30 seconds before, it is replaced at once, and the response it cuts short is resumed on the new session. Queued requests wait through the swap and start on the new session (`party-cf/src/parlume-realtime-continuity.ts`). The bridge's Durable Object is also reset now and then mid-meeting: the bot's stream ends with "Durable Object connection closed because the object was reset" (outcome `exception`), five times on one day of staging tests, at quiet moments as well as during speech, with no deploy, no other failing invocation in the Worker, and no memory, CPU or exception error recorded. The message does not come from the open-source workerd runtime, so the cause is on Cloudflare's side and not yet known. Each one is logged as `parlume.bridge.bridge.restarted`, once the meeting has heard someone; the bridge's state is stored at invite, so the object's first start is not counted. Attendee reconnects within about two seconds; speech during that gap is not transcribed. The realtime voice's context (those transcript lines and the Fabric jobs still running) is kept in the Durable Object's storage (`realtimeContext`), so the restarted voice continues the meeting and still speaks a job's result instead of sending it to the chat. An unexpected close is retried after 1, 3 and 10 seconds; after that the meeting stays on the classic voice for the rest of the meeting (`parlume.bridge.realtime.reconnect`, `parlume.bridge.realtime.dropped`). Logs never carry transcript text or secrets; `parlume.bridge.realtime.response` records the latency from the trigger to the first audio.
- Speech carries on across a dropped connection. The bridge plays both voices through one meeting outlet, bound to the bot socket Fabric verified last (`party-cf/src/parlume-meeting-outlet.ts`). When the bot connects again on a new socket, the outlet holds its speech from that socket's first message; once Fabric verifies it, the audio not yet sent goes to the new socket after a 300 ms pre-roll, and the reply in progress stays current. A socket that fails verification releases the hold. The lead the old socket had (about 200 ms) is what can be lost. Logged as `parlume.bridge.speech.resumed` with `cause: "socket_swap"`, `gapMs` and `lostMs`.
- A restart of the Durable Object, a deploy included, resumes what Parlume was saying. At each sentence end the bridge stores what it is saying under `spokenRecord`: the worker's reply by its id, or a post read aloud whole, with the voice generation, the sentences and how many were heard (`party-cf/src/parlume-reply-record.ts`). A read the restart cut short is read on from its first unheard sentence when the bot's socket is verified again within 15 seconds (`cause: "restart"`). For a reply, the worker sees that the opening part got no answer (no response, or a 5xx from the edge), asks `?action=verify-generation` with the reply's id, which answers `live` (a bot socket plays speech) and `heard`, polls it each second until `live`, and then speaks the rest from the first unheard sentence through the PCM route (`cause: "bridge_lost"` in the worker's log). When no socket is back within 15 seconds, the worker posts every sentence not heard to the chat, the headline's included (`speech.resume_missed`). The object never hibernates during a meeting, so these resumes are the whole recovery.
- The realtime voice keeps each response's transcript as it streams (`response.output_audio_transcript.delta`) in the saved realtime context. A session that drops, is replaced, or is lost to a restart queues a resume response first on the next session, told what the meeting heard and asked to continue from there; the share heard is measured from the audio played. When no resume starts within 15 seconds, the unheard part goes to the chat, a Fabric result's answer whole (`parlume.bridge.realtime.resume_missed`). A resume still waiting when the meeting's last two minutes begin goes to the chat at once, logged as `realtime.resume_to_chat` at info level and not counted in `failedResumes`. A meeting that fell back to the classic voice stores `realtimeGaveUp`, so a restart keeps it classic. Audio with no outlet to play on is logged once per response (`realtime.audio_dropped`), and a response OpenAI's turn detection cancelled is logged as `realtime.misconfigured`, since only the bridge cancels responses.
- Each response's usage (`response.done`) is reported to `/api/internal/parlume/realtime-usage` and recorded as `AZURE_AI_FOUNDRY` usage of `gpt-realtime-2.1` under the `parlume` feature key with the session id as `conversationId`, priced per 1M tokens at $32 audio input, $0.40 cached input, $64 audio output, $4 text input and $24 text output. Only the audio from a wake phrase to the end of the reply reaches the session, and it is billed when a response reads it, so the responses' usage is the whole bill. At about 10 input audio tokens per second, each minute of request audio heard once costs about $0.02, plus the spoken answers. That estimate, live latency, barge-in behaviour and whether the Workers runtime passes the upgrade's authorization have not been verified in a meeting.
- The hard stop is four hours. The bot waits up to five minutes in the Teams lobby to be admitted before it gives up (`waiting_room_timeout_seconds`, set from `PARLUME_LOBBY_WAIT_SECONDS` = 300 in `packages/api/modules/projects/lib/parlume-lobby.ts`); that wait is billed bot time. Five minutes, down from ten, halves what an unadmitted invite costs. Auto-join asks to join a minute before the start, so the wait still covers an organizer who arrives four minutes late; the Parlume page shows the time the wait ends so the person watching can admit the bot in time. The constant has no imports so the page can read it. Once in, it still leaves a meeting it has been alone in for three minutes (`only_participant_in_meeting_timeout_seconds` 180), and the bridge still leaves a silent meeting after three minutes. Live transcription, speech synthesis, the realtime voice and the agent's configured model accrue costs only during meeting work.
- The notes, suggestions and recap resolve the organization's fast model (`{ taskType: "SIMPLE", complexity: "simple" }`), so the model is organization configuration, not code. The notes evaluation (`packages/api/scripts/parlume-eval.ts`, run 2026-11-21 on the ten synthetic meetings the set held then, before `parlume-chat-post` was added) scored the Claude models only: Claude Haiku 5.5 reached 98% anchor validity (103 of 105), 97% owner and due accuracy, 0 invented decisions in 19 and 73% suggestion precision for $0.0233; Claude Sonnet 5.5 reached 100%, 97%, 2 in 21 and 75% for $0.3328; Claude Opus 5.5 reached 100%, 100%, 1 in 19 and 69% for $0.6342. Haiku 5.5 is the recommended fast model for an Anthropic organization. The current staging default (`gpt-6.1-terra` through a ChatGPT plan) has no score, because the baseline run had no OpenAI credits, so the guidance does not compare Claude with it. A suggestion-only gate on questions and decisions (fewer passes) was not built: at Haiku prices a pass costs well under $0.001, and passes are capped at 80 an hour, so it would save cents an hour while skipping passes after statements.
- Full transcript text is retained as project context for 90 days (see [Transcript access, deletion and retention](#transcript-access-deletion-and-retention)), and notes are generated asynchronously. Context includes separate incoming speech and recorded Fabric responses with request statuses, playback interruptions, and individual action tool names and receipt statuses; generated success claims do not override failed or unconfirmed receipts. The two section headers are shared constants (`@repo/utils/parlume-notes`).
- **Anchored notes.** `parlumeNotesWorkflow` runs `writeParlumeNotes` (`packages/temporal/src/activities/parlume-notes.ts`). The activity numbers each line of the speech section by its 1-based line in the context's content, the line the transcript reader opens at with `#t-<line>`, and asks the organization's fast model (`SIMPLE`, `jobType: "parlume-meeting-notes"`) for `{ discussion, decisions, actionItems, openQuestions }` through `generateText` with `Output.object`. Each entry carries `text`, the cited `segment` and an exact `quote`; action items also `owner` and `due`. The schema is lenient (every field optional, `segment` a number or a string such as `"[12]"`). A model-free check (`parlume-notes-anchors.ts`) keeps an entry only when the cited line was one that pass was shown and the Meeting Digest's `resolveQuoteAnchor` finds the quote in that line; it drops an owner or a due date whose words the cited line does not contain. Fabric's records section is passed fenced and unnumbered, so a note can never cite a generated answer or a receipt, and a "change made" claim has no line to rest on. Parlume's own chat posts arrive in the speech section, because the meeting chat shows them back, so `splitParlumeTranscript` leaves every line of each post out of the numbered lines: a post opens with a `[chat]` line whose sender name starts with `PARLUME_BOT_NAME` (`@repo/utils/parlume-notes`), with any mark after it such as `(unverified speaker)`, the rule the bridge uses for its own messages. A note citing one of those lines is dropped as `segment_unknown`, and the remaining lines keep their numbers in the content. A request's answer stays in the records as its `Response`. Where a segment of several lines ends is told by its line breaks: `parlumeTranscriptLine` writes every line break inside a segment as `\r\n` (`parlumeTranscriptText`), and the segments route trims each segment's text, so a content line that ends in `\r` goes on in the next line and any other line ends its segment (`parlumeTranscriptLineContinues`). A person's chat message of several lines stays citable on every line. The notes are stored on the context's metadata as `parlumeNotesItems` (`{ version: 1, items: [{ kind, text, anchorLine, tentativeOwnerName?, dueHint? }] }`, the owner and due fields named as a Meeting Digest action item's) and rendered to Markdown as `parlumeNotes`, which the Series Recap and older clients read. `withoutParlumeNotes` strips both for a reader who may not see a confidential meeting. The Parlume page shows each note with a `Line N` link to the transcript for a viewer who may open it. The worker logs `parlume.notes.anchored` with the parts, the entries proposed and kept, the drops by reason (`empty`, `segment_unknown`, `quote_not_in_segment`) and the owners and due dates dropped, for the rate of unsupported notes; it carries no note text. The instructions are the seeded, bindable **Parlume Meeting Notes** prompt (`parlume_meeting_notes`, under Meetings & Intake).
- **Long meetings.** A transcript whose numbered lines exceed 40,000 characters (about 40 minutes of speech) is read in consecutive parts cut between lines. Each part gets its own checkpoint pass, whose notes may cite only that part's lines; a final pass gets the checkpoint notes, the lines they cited, Fabric's records (capped at 20,000 characters) and the chat delivery facts, merges them, and is checked again against the cited lines. Nothing is cut from the middle of the meeting any more. The passes are `writeAnchoredNotes` in `packages/temporal/src/activities/parlume-notes-passes.ts`, which the notes evaluation also runs (see [Measuring notes and suggestion quality](#measuring-notes-and-suggestion-quality)).
- **Retries and Regenerate notes.** The activity runs up to three times (`PARLUME_NOTES_MAX_ATTEMPTS`, with a 15-minute start-to-close timeout for a long meeting's several calls). The workflow sets it as the retry policy and passes it to the activity as `maxAttempts`; an activity scheduled before that, under the earlier two-attempt policy, arrives without it and counts two. Every attempt but the last rethrows a model failure, an empty transcript or a plan that ran out mid-reply (`PlanSourceRotatedError`) for Temporal to retry; the last records `parlumeNotesStatus: "FAILED"`, so the notes never stay `PENDING` after the run. A spent ChatGPT plan still goes to the workflow's plan wait, and fails the notes on the attempt after the wait. No `patched()` is needed: retry options, timeouts and activity arguments are not part of the command sequence. `projects.parlume.regenerateNotes` (`POST /projects/{projectId}/parlume/sessions/{sessionId}/regenerate-notes`) needs `PROJECT_READ`, then `canDeleteParlumeSession` and, for a confidential session, `mayReadParlumeSessionContent`: the people who may delete the session. It refuses a session whose transcript is deleted or whose notes are still `PENDING`, marks the notes `PENDING`, and starts `parlumeNotesWorkflow` with `regenerate: true` under its own id `parlume-notes-regenerate-<sessionId>` (`USE_EXISTING`, so a second request joins a running one); if the start fails, the earlier status is put back. A regenerating run writes over the notes; if it fails, the earlier notes stay with status `FAILED`. It is audited as `project.parlume.notes_regenerated`, and stamps `parlumeNotesRequestedAt`. The sessions list returns `notesItems`, `notesRequestedAt` and `canRegenerateNotes`. The Parlume page polls while a session's notes are `PENDING` and the session ended, or the notes were asked for again, in the last 30 minutes; notes stuck longer than that do not keep the page polling.
- **Proposing an action item.** `projects.parlume.proposeActionItem` (`POST /projects/{projectId}/parlume/sessions/{sessionId}/propose-action-item`, input `anchorLine` and `text`) needs `STORY_CREATE`, then `canReadParlumeTranscript`, and refuses every confidential session: the Proposal Inbox shows every proposal to every project reader, with no confidential filter. The item must be an action item of the session's stored `parlumeNotesItems`. It files a `MONITORED_MEETING` pending proposal through `createPendingBacklogProposal`, the same human approval as a Meeting Digest action item, with one feature change (title the item; description its owner, due date and a link to `/app/{slug}/projects/{projectId}/contexts/{contextId}#t-<line>`). `sourceMetadata` holds `parlumeSessionId`, `parlumeActionItemKey`, `anchorLine`, `transcriptHref`, the owner and due hints and the meeting subject and date, never `transcript` or a quote, so approval drafts from the change's reasoning. One `PENDING` proposal per session, line and item wording (`parlumeActionItemKey`); a repeat returns `already-proposed`. Audited as `project.parlume.action_item_proposed`. The sessions list returns `canProposeActionItems`. Parlume items are not written to the Meeting Digest: its rows need a linked meeting, and its transcript tab serves every project reader.
- The bot's data in Attendee is deleted (`delete_data`) after finalization when its API succeeds; Attendee allows that only once the bot has ended, so a failed attempt answers the terminal webhook with an error and Attendee redelivers it. A successful deletion also revokes the session's webhook token. Failed cleanup is left visible for operator recovery.
