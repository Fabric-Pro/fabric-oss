# Parlume meeting preview

- **Audience**: Project administrators and operators
- **Owner**: Engineering team

Parlume is a default-off, project-scoped way to invite the built-in Fabric Agent or a project-bound custom agent to a Microsoft Teams meeting by link. Each project has a **Parlume page** at `/projects/{id}/parlume`, linked from Meeting Digest: administrators invite and remove the bot there, and readers review sessions, requests, and spend. While Parlume is joining, the page shows the invite's progress (invite sent, waiting in the lobby), then a live card with the elapsed time, agent, mode, spend so far and the session's latest requests. Below it, a Sessions and Requests panel lists sessions five at a time and filters requests by session and by question or action. The bot appears as **Fabric Parlume**, records and transcribes meeting audio, responds to “Hey Fabric,” “Hey Parlume,” or “Hey Fabric Parlume,” and saves a transcript and generated notes to the project. The join URL is sent to the meeting provider but is not stored in Fabric.

## Operator setup

1. Deploy the database migration and the updated web API, Temporal worker, and Cloudflare PartyServer/Durable Object together. The Durable Object is event-driven; no dedicated media process runs while there is no meeting. The PartyServer Worker needs its Workers AI binding (`AI`, declared in `party-cf/wrangler.toml`), which it uses to transcribe meetings.
2. Create an API key for the hosted [Attendee](https://app.attendee.dev) project that will run the bots, and configure it as `PARLUME_ATTENDEE_API_KEY` in the web API. Fabric derives the public bridge URL from `NEXT_PUBLIC_PARTYKIT_HOST` and the callback URL from `APP_URL` (or `NEXT_PUBLIC_SITE_URL`). `PARLUME_BRIDGE_WS_URL` and `PARLUME_CALLBACK_URL` remain optional explicit overrides. The existing `AGENT_SERVICE_SECRET` must match between web, Temporal, and PartyServer, and PartyServer needs `FABRIC_API_URL` for the internal callback routes.
3. Ensure the Temporal worker's `NEXT_PUBLIC_PARTYKIT_HOST` points at the same PartyServer host. Parlume speaks with **Deepgram Aura-2** (voice `orpheus`, `@cf/deepgram/aura-2-en`), synthesized inside the bridge on Workers AI, which needs no organization credential. If Aura cannot speak a sentence, the rest of the reply goes through the organization's **Vercel AI Gateway** provider (`openai/tts-1`, the same credential and billing as its language models) and then its **OpenAI Direct** key. The invite fails before starting a provider bot if the Attendee key is missing or neither fallback speech route is configured. A reply that cannot be spoken is posted to the meeting chat instead, and the request records why.
4. Enable `PARLUME_MEETINGS` for the test organization. It defaults off. The default choice is **Fabric Agent — this project**, which uses the project's current knowledge and Fabric Agent behavior. Custom agents remain available when owned by the inviter and bound to the project through `project-context`.
5. Paste an ordinary Teams meeting link. A `teams.microsoft.com/meet/…` link must keep its `?p=` passcode, which Attendee needs to join; `/l/meetup-join/…` links work as copied. The bot joins as an anonymous external guest. The organizer may have to admit it from the lobby, and it leaves on its own after three minutes unadmitted. A meeting that requires signed-in or tenant-only guests cannot be joined through this preview without changing that meeting's policy.

For a smoke test, use a disposable meeting with consenting participants. Confirm the bot joins as **Fabric Parlume**, captures final segments, answers each of the three wake phrases aloud, stops on request, and leaves a project transcript and notes. Check that a flagged-off organization cannot invoke the API. Ask a question that spans a natural pause, for example “Hey Parlume, what is the name … of the project?”, and confirm one answer arrives after the sentence ends. Joining, the agent's answers and speech synthesis were verified on staging on 2026-10-02 with the previous meeting provider. Audible playback and speaker attribution through Attendee are pending verification on staging.

## Boundaries

- The invite form tells the inviter that Parlume records and transcribes the meeting, and that participants should be told before it is invited. It is a notice, not a gate: there is nothing to tick, and Fabric stores no consent record.
- The inviter must have project administration permission. Any attendee able to speak in the meeting can request a spoken answer from the selected project's knowledge; the bot cannot verify each attendee's Fabric identity.
- Parlume is a voice adapter around the selected agent's normal execution path. Each request reloads the current active custom-agent version or the built-in agent's preferences. Configured instructions, knowledge, tools, models and permission checks remain owned by that agent. Agent changes apply to subsequent requests.
- Invitations default to **Read-only**, which refuses every change. Choosing **Actions** lets attendees ask for changes, and Parlume makes each one as soon as it is asked for, using the inviter's current project permissions. There is no confirmation step: the change runs when the agent calls the tool, so anyone able to speak in the meeting can cause a change the inviter could make, and an instruction that reaches the agent through the transcript or a tool result could as well. A change that names another project is refused. A provider speaker label is continuity information, not a verified Fabric identity; people sharing a microphone may share that label, and a change asked for by a speaker Teams gave no label for is recorded as unattributed.
- Each change is recorded before it runs as a `ParlumeAction` with the requester's label, the tool, its arguments, and later its outcome, and writes an audit entry (`project.parlume.action_confirmed`, shown as “Parlume action executed”; the key keeps its original name). An identical call in the same turn runs once. A result that names what it made (for example a work item's identifier and link) and carries no error is recorded as completed; an uncertain outcome such as a timeout is recorded without automatic retry. Check the destination before requesting an uncertain action again. An interruption before dispatch makes no change.
- Creating a work item answers within a few seconds. The item is created from what was said, as the agent named its kind, and its body is drafted afterwards by the same workflow that rewrites a body after a type conversion; the prior body is kept as a version, and the draft is discarded if someone edited the item meanwhile. The agent says what it created and, when asked for the link, posts it in the meeting chat.
- The Fabric Agent in a meeting also has 38 of the Fabric portal's tools: who the inviter is and their organization, the projects, features and their tasks and status, bugs, documents, project contexts, coding instructions (read, propose a change, add a lesson), project knowledge search, workspaces, the inviter's AI chats and their connected servers. They come through the Fabric MCP gateway on a grant the web app signs for each turn. The grant names the meeting's project and the scopes those tools need; the gateway keeps only the scopes within its own ceiling and admits the grant only when the inviter can open that project in the organization acted in. Every call is then held to the inviter and that organization (the agent cannot switch to another organization, and lists only the one it acts in) and to the meeting's project: a call that names another project, a nested project id included, or a feature, document or context of another one is refused, and the project list is the meeting's project alone. Creating a new project is allowed and does not move the meeting off its own. The tools that request, check or revoke delegated authority and the memory tools are not offered, and a test fails when the gateway gains a platform tool that is neither offered nor named as left out. A new feature or bug is filed from the words given and drafted in the background, as for `fabric_create_story`. The portal schemas are about 29 KB, so a turn carries them only when the request asks for something they do (changing a feature or task, writing a document, context or instruction, searching project knowledge, projects, organizations, chats, connected servers or a workspace); a plain question does not. Read or change comes from the gateway's own listing, so a change in a read-only meeting is refused and in an actions meeting runs at once and is recorded.
- Configured built-in actions use the shared agent tool mapping and implementations. Workflow starts use the same execution API as chat, including current organization and project permissions, workflow state, and concurrency limits.
- The Parlume page's **Requests** list is available to project readers. It records questions, requester labels, timestamps, responses, exact action details, and each action's status and outcome. It does not create a personal attendee profile.
- A session ends, and records why (`endReason`), when an administrator presses Stop, when the meeting host removes the bot or the meeting ends (the provider's terminal callback also closes the live stream, and if no stream is open the next access check finalizes, so the transcript is saved within a minute), after **three minutes with no human speech** while Parlume is silent (`IDLE`), when the inviter loses project access, on an unrecoverable stream failure, or at the four-hour cap. Attendee itself gives up after three minutes in a lobby or with nobody else present, and after the hard stop plus a two-minute backstop if Fabric's own leave never lands. Fabric has no live participant count for the people who remain, so "nobody speaking" is detected as silence; raise `IDLE_LEAVE_MS` in the bridge if quiet, attended meetings prove common.
- Spend is recorded in the project's AI usage under the `parlume` feature key with the session id as `conversationId`: every agent turn (built-in or custom), each speech synthesis (priced from text length and audio seconds), post-meeting notes, and at finalization the meeting provider's bot time (one Attendee credit per bot-hour, priced at the $0.50 entry rate) and its live transcription (Deepgram Flux on Workers AI, per audio minute). The Parlume page shows the project total and a per-session split in cents, with “< $0.01” for spend under one cent. A live session's spend so far leaves out the bot's time and live transcription, which are added when the session is finalized.
- Every step logs a structured event (`component: "parlume"`, `event: "parlume.<name>"`, `sessionId`, `botId`, counts and latencies; never the meeting link, tokens, secrets, or transcript text) across the web routes, the API, the Temporal worker, and the bridge (Workers Logs, `parlume.bridge.*`). Rejected provider callbacks log the trigger and whether the token was present.
- Wake phrases are matched by sound, not spelling, because transcription spells the names by ear ("Fabrik", "Parloom", "Perlman"); a whole-word consonant comparison keeps "Fabrication" or "Parliament" from waking it. A leave Fabric requested (Stop, idle, revoked access, hard stop) ends normally even when the provider reports it as a failed bot.
- Attendee connects to the bridge as a WebSocket client, using the per-session URL (with its stream token) Fabric gave it when it created the bot, and streams the mixed meeting audio as 16 kHz JSON `realtime_audio.mixed` messages of 10 ms each. The bridge verifies the bot named by the first message before trusting the stream, and plays replies by sending `realtime_audio.bot_output` messages back on the same socket: 100 ms frames paced in real time, opened with 300 ms of silence so the bot's unmute does not clip the first word. The bot records nothing (`recording_settings.format` is `none`), and Attendee's own transcription is not used. The bridge transcribes the mixed meeting audio with Deepgram Flux on Workers AI, which also decides where a speaker's turn ends; it sends Flux 80 ms batches, as Deepgram recommends, because Flux fed Attendee's 10 ms chunks at 24 kHz transcribed nothing. Replies go back at Fabric's 24 kHz synthesis rate, which each `bot_output` message names. It attributes each turn to the participant Attendee reports as speaking during it: Attendee posts `participant_events.speech_start_stop` webhooks to Fabric, which relays them to the bridge, and both use the bot server's clock. A turn nobody was reported speaking in goes to whoever last started speaking within ten seconds; otherwise the speaker is unknown. Bridge logs `parlume.bridge.audio.started` and `parlume.bridge.transcriber.*` trace the audio path, and `parlume.bridge.audio.health` reports every 10 s how many chunks arrived, the longest gap between them, and how many batches went to Flux and events came back.
- Attendee signs its webhooks with a project-wide secret that is visible only in its dashboard, so Fabric does not verify that signature. Each bot's webhook URL carries a secret derived for that session instead, compared in constant time. Treat the webhook URL as sensitive: Attendee holds it as part of the bot's configuration.
- Replies are spoken a sentence at a time. The worker sends each sentence's text to the bridge as it is written (`?action=say`, newline-delimited JSON); the bridge synthesizes it with Aura and plays it, starting the next sentence's synthesis while the current one plays. Aura streams raw 24 kHz PCM, so the first audio arrives well before a sentence is fully synthesized. Each synthesized sentence is recorded as `CLOUDFLARE_AI` usage (`@cf/deepgram/aura-2-en`, $0.03 per 1,000 characters). When Aura fails on a sentence, the bridge reports where, and the worker speaks the remaining sentences through the fallback routes as PCM (`?action=speak`) without repeating what was already spoken. This starts while the agent is still writing the answer, in read-only and actions meetings alike. On the fallback routes, gateway speech returns each sentence's clip whole and the OpenAI Direct route streams PCM as synthesis produces it. Markdown and URLs are not read aloud (a URL is spoken as "the link"). A request that comes with its wake phrase ("Hey Fabric, what is the status?") is handed to Fabric as soon as Flux ends the speaker's turn, with no extra wait. A request that follows a bare "Hey Fabric" waits until the requester has been quiet for 300 ms (8 s cap); the requester's further words extend it, and Flux's empty start-of-turn events do not. The bridge's `parlume.bridge.turn.dispatched` log records `endpointMs` (wake phrase to the end of the request) and `handoffMs` (until Fabric accepted it). Speech from a participant other than the Parlume bot, including an unknown speaker, interrupts playback while Parlume is audible. Speech attributed to the bot itself never interrupts it, but attribution comes from Attendee's speaker webhooks, which arrive after the audio, so barge-in is best-effort. Attendee cannot drop audio it already holds, so an interruption silences a reply within about 200 ms rather than at once. Model generation, transcription and network latency still affect response time; live meeting latency has not been verified.

Spoken replies are tuned for speed. The model gets the least reasoning effort it accepts (OpenAI reasoning models only), the Fabric prompt enhancer is skipped, and the reply reads a small slice of the meeting: the last three minutes of transcript (at most 4,000 characters, the most recent kept), three project passages, and the last four answered questions. The worker logs one `parlume.turn.timing` record per turn: the milliseconds each step took (agent load, decision, project retrieval, transcript and history queries, MCP and memory lookups, model resolution), the model's time to first text and total time with its token, reasoning-token and cached-token counts, and each sentence's speech route, time to first audio byte and total time. When the bot is admitted, the worker also runs the first steps of a turn once (`parlume.session.warmed`) so the first question does not start cold.

**Writing in the meeting chat.** Ask Parlume to share, post or write something in the chat ("put the link to F-123 in the chat", "post that summary") and it calls `post_to_meeting_chat`. The tool works in read-only and actions meetings alike, because it changes nothing in Fabric, and it posts at most three times per answer. `text` is posted as the participant asked, URLs included. `links` are resolved by the worker from the meeting's own project, after an access check, into full direct addresses: a work item by identifier (`F-123`, `123`, `B-9`) or id, a document by id or exact title, a Context source by id, or the roadmap, decisions, documents or context tab. A reference outside the project is refused and reported back, and the addresses use the project's own organization, so they work for guests of another organization's project. The message is plain text, one link per line (`F-123 · Title — https://…`), within the chat's 4,000-character limit; the text is shortened before any link is dropped. Each post is logged as `parlume.chat.posted` with counts and no content.
- Full transcript text is retained as project context and notes are generated asynchronously. The bot's data in Attendee is deleted (`delete_data`) after finalization when its API succeeds; Attendee allows that only once the bot has ended, so a failed attempt answers the terminal webhook with an error and Attendee redelivers it. Failed cleanup is left visible for operator recovery.
- The hard stop is four hours; a provider bot can incur charges while waiting in a lobby. Attendee, live transcription, speech synthesis, and the agent's configured model accrue costs only during meeting work.
