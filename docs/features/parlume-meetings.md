# Parlume meeting preview

- **Audience**: Project administrators and operators
- **Owner**: Engineering team

Parlume is a default-off, project-scoped way to invite the built-in Fabric Agent or a project-bound custom agent to a Microsoft Teams meeting by link. Each project has a **Parlume page** at `/projects/{id}/parlume`, linked from Meeting Digest: administrators invite and remove the bot there, and readers review sessions, requests, and spend. While Parlume is joining, the page shows the invite's progress (invite sent, waiting in the lobby), then a live card with the elapsed time, agent, mode, spend so far and the session's latest requests. Below it, a Sessions and Requests panel lists sessions five at a time and filters requests by session and by question or action. The bot appears as **Fabric Parlume**, records and transcribes meeting audio, responds to “Hey Fabric,” “Hey Parlume,” or “Hey Fabric Parlume,” and saves a transcript and generated notes to the project. The join URL is sent to the meeting provider but is not stored in Fabric.

## Operator setup

1. Deploy the database migration and the updated web API, Temporal worker, and Cloudflare PartyServer/Durable Object together. The Durable Object is event-driven; no dedicated media process runs while there is no meeting. The PartyServer Worker needs its Workers AI binding (`AI`, declared in `party-cf/wrangler.toml`), which it uses to transcribe meetings.
2. Create an API key for the hosted [Attendee](https://app.attendee.dev) project that will run the bots, and configure it as `PARLUME_ATTENDEE_API_KEY` in the web API. Fabric derives the public bridge URL from `NEXT_PUBLIC_PARTYKIT_HOST` and the callback URL from `APP_URL` (or `NEXT_PUBLIC_SITE_URL`). `PARLUME_BRIDGE_WS_URL` and `PARLUME_CALLBACK_URL` remain optional explicit overrides. The existing `AGENT_SERVICE_SECRET` must match between web, Temporal, and PartyServer, and PartyServer needs `FABRIC_API_URL` for the internal callback routes.
3. Ensure the Temporal worker's `NEXT_PUBLIC_PARTYKIT_HOST` points at the same PartyServer host. Parlume speaks with **Deepgram Aura-2** (voice `orpheus`, `@cf/deepgram/aura-2-en`), synthesized inside the bridge on Workers AI, which needs no organization credential. If Aura cannot speak a sentence, the rest of the reply goes through the organization's **Vercel AI Gateway** provider (`openai/tts-1`, the same credential and billing as its language models) and then its **OpenAI Direct** key. The invite fails before starting a provider bot if the Attendee key is missing or neither fallback speech route is configured. A reply that cannot be spoken is sent to the meeting chat instead, and the request records why and whether the chat showed it.
4. Enable `PARLUME_MEETINGS` for the test organization. It defaults off. The default choice is **Fabric Agent — this project**, which uses the project's current knowledge and Fabric Agent behavior. Custom agents remain available when owned by the inviter and bound to the project through `project-context`.
5. Paste an ordinary Teams meeting link. A `teams.microsoft.com/meet/…` link must keep its `?p=` passcode, which Attendee needs to join; `/l/meetup-join/…` links work as copied. By default the bot joins as an anonymous external guest. The organizer may have to admit it from the lobby, and it leaves on its own after three minutes unadmitted. An anonymous guest cannot join a meeting that requires signed-in or tenant-only guests, and it has no chat box in a channel meeting or in a meeting whose chat policy excludes anonymous users.
6. Optional, for those meetings: run the bot signed in. Create a Microsoft 365 account for the bot, named **Fabric Parlume** so its posts and voice are recognized as the bot's own; for channel meetings, add that account to the team. Enter the account's credentials as the Teams bot login on the Attendee project, then set `PARLUME_ATTENDEE_TEAMS_LOGIN` in the web API to `always` (sign in for every meeting) or `only_if_required` (sign in only when the meeting refuses an anonymous guest). Fabric then creates each bot with `teams_settings: { use_login: true, login_mode }`. Unset keeps the anonymous guest. Any other value makes the invite fail before a bot is created, with the setting named in the session's error.

For a smoke test, use a disposable meeting with consenting participants. Confirm the bot joins as **Fabric Parlume**, captures final segments, answers each of the three wake phrases aloud, stops on request, and leaves a project transcript and notes. Check that a flagged-off organization cannot invoke the API. Ask a question that spans a natural pause, for example “Hey Parlume, what is the name … of the project?”, and confirm one answer arrives after the sentence ends. Joining, the agent's answers and speech synthesis were verified on staging on 2026-10-02 with the previous meeting provider. Audible playback and speaker attribution through Attendee are pending verification on staging.

## Boundaries

- The invite form tells the inviter that Parlume records and transcribes the meeting, and that participants should be told before it is invited. It is a notice, not a gate: there is nothing to tick, and Fabric stores no consent record.
- The inviter must have project administration permission. Any attendee able to speak in the meeting can request a spoken answer from the selected project's knowledge; the bot cannot verify each attendee's Fabric identity.
- Parlume is a voice adapter around the selected agent's normal execution path. Each request reloads the current active custom-agent version or the built-in agent's preferences. Configured instructions, knowledge, tools, models and permission checks remain owned by that agent. Agent changes apply to subsequent requests.
- Invitations default to **Read-only**, which refuses every change. Choosing **Actions** lets attendees ask for changes, and Parlume makes each one as soon as it is asked for, using the inviter's current project permissions. There is no confirmation step: the change runs when the agent calls the tool, so anyone able to speak in the meeting can cause a change the inviter could make, and an instruction that reaches the agent through the transcript or a tool result could as well. A change that names another project is refused. A provider speaker label is continuity information, not a verified Fabric identity; people sharing a microphone may share that label, and a change asked for by a speaker Teams gave no label for is recorded as unattributed.
- Each change is recorded before it runs as a `ParlumeAction` with the requester's label, the tool, its arguments, and later its outcome, and writes an audit entry (`project.parlume.action_confirmed`, shown as “Parlume action executed”; the key keeps its original name). An identical call in the same turn runs once. A result that names what it made (for example a work item's identifier and link) and carries no error is recorded as completed; an uncertain outcome such as a timeout is recorded without automatic retry. Check the destination before requesting an uncertain action again. An interruption before dispatch makes no change.
- Creating a work item answers within a few seconds. The item is created from what was said, as the agent named its kind, and its body is drafted afterwards by the same workflow that rewrites a body after a type conversion; the prior body is kept as a version, and the draft is discarded if someone edited the item meanwhile. The agent says what it created and, when asked for the link, sends it to the meeting chat.
- The Fabric Agent in a meeting also has 38 of the Fabric portal's tools: who the inviter is and their organization, the projects, features and their tasks and status, bugs, documents, project contexts, coding instructions (read, propose a change, add a lesson), project knowledge search, workspaces, the inviter's AI chats and their connected servers. They come through the Fabric MCP gateway on a grant the web app signs for each turn. The grant names the meeting's project and the scopes those tools need; the gateway keeps only the scopes within its own ceiling and admits the grant only when the inviter can open that project in the organization acted in. Every call is then held to the inviter and that organization (the agent cannot switch to another organization, and lists only the one it acts in) and to the meeting's project: a call that names another project, a nested project id included, or a feature, document or context of another one is refused, and the project list is the meeting's project alone. Creating a new project is allowed and does not move the meeting off its own. The tools that request, check or revoke delegated authority and the memory tools are not offered, and a test fails when the gateway gains a platform tool that is neither offered nor named as left out. A new feature or bug is filed from the words given and drafted in the background, as for `fabric_create_story`. The portal schemas are about 29 KB, so a turn carries them only when the request asks for something they do (changing a feature or task, writing a document, context or instruction, searching project knowledge, projects, organizations, chats, connected servers or a workspace); a plain question does not. Read or change comes from the gateway's own listing, so a change in a read-only meeting is refused and in an actions meeting runs at once and is recorded.
- Configured built-in actions use the shared agent tool mapping and implementations. Workflow starts use the same execution API as chat, including current organization and project permissions, workflow state, and concurrency limits.
- The Parlume page's **Requests** list is available to project readers. It records questions, requester labels, timestamps, responses, exact action details, and each action's status and outcome. It does not create a personal attendee profile.
- A session ends, and records why (`endReason`), when an administrator presses Stop, when the meeting host removes the bot or the meeting ends (the provider's terminal callback also closes the live stream, and if no stream is open the next access check finalizes, so the transcript is saved within a minute), after **three minutes with no human speech** while Parlume is silent (`IDLE`), when the inviter loses project access, on an unrecoverable stream failure, or at the four-hour cap. Attendee itself gives up after three minutes in a lobby or with nobody else present, and after the hard stop plus a two-minute backstop if Fabric's own leave never lands. Fabric has no live participant count for the people who remain, so "nobody speaking" is detected as silence; raise `IDLE_LEAVE_MS` in the bridge if quiet, attended meetings prove common.
- Spend is recorded in the project's AI usage under the `parlume` feature key with the session id as `conversationId`: every agent turn (built-in or custom), each speech synthesis (priced from text length and audio seconds), post-meeting notes, and at finalization the meeting provider's bot time (one Attendee credit per bot-hour, priced at the $0.50 entry rate) and its live transcription (Deepgram Flux on Workers AI, per audio minute). The Parlume page shows the project total and a per-session split in cents, with “< $0.01” for spend under one cent. A live session's spend so far leaves out the bot's time and live transcription, which are added when the session is finalized.
- Every step logs a structured event (`component: "parlume"`, `event: "parlume.<name>"`, `sessionId`, `botId`, counts and latencies; never the meeting link, tokens, secrets, or transcript text) across the web routes, the API, the Temporal worker, and the bridge (Workers Logs, `parlume.bridge.*`). Rejected provider callbacks log the trigger and whether the token was present.
- Wake phrases are matched by sound, not spelling, because transcription spells the names by ear ("Fabrik", "Parloom", "Perlman"); a whole-word consonant comparison keeps "Fabrication" or "Parliament" from waking it. A leave Fabric requested (Stop, idle, revoked access, hard stop) ends normally even when the provider reports it as a failed bot.
- Attendee connects to the bridge as a WebSocket client, using the per-session URL (with its stream token) Fabric gave it when it created the bot, and streams the mixed meeting audio as 16 kHz JSON `realtime_audio.mixed` messages of 10 ms each. The bridge verifies the bot named by the first message before trusting the stream, and plays replies by sending `realtime_audio.bot_output` messages back on the same socket: 100 ms frames paced in real time, opened with 300 ms of silence so the bot's unmute does not clip the first word. The bot records nothing (`recording_settings.format` is `none`), and Attendee's own transcription is not used. The bridge transcribes the mixed meeting audio with Deepgram Flux on Workers AI, which also decides where a speaker's turn ends; it sends Flux 80 ms batches, as Deepgram recommends, because Flux fed Attendee's 10 ms chunks at 24 kHz transcribed nothing. Replies go back at Fabric's 24 kHz synthesis rate, which each `bot_output` message names. It attributes each turn to the participant Attendee reports as speaking during it: Attendee posts `participant_events.speech_start_stop` webhooks to Fabric, which relays them to the bridge, and both use the bot server's clock. A turn nobody was reported speaking in goes to whoever last started speaking within ten seconds; otherwise the speaker is unknown. Bridge logs `parlume.bridge.audio.started` and `parlume.bridge.transcriber.*` trace the audio path, and `parlume.bridge.audio.health` reports every 10 s how many chunks arrived, the longest gap between them, and how many batches went to Flux and events came back.
- Speaker attribution uses Flux's first-to-last spoken-word timestamps when valid, falling back to processed-audio windows when word timing is unavailable or invalid.
- Payload-free chat instructions such as "Write in the chat" wait for the same identified speaker's dictated message, adding 2.5 seconds of quiet after the last continuation, with an 8-second total cap; complete inline requests retain no extra wait, a new wake replaces the draft, and expiry passes only the captured text to Fabric without inventing content.
- Attendee signs its webhooks with a project-wide secret that is visible only in its dashboard, so Fabric does not verify that signature. Each bot's webhook URL carries a secret derived for that session instead, compared in constant time. Treat the webhook URL as sensitive: Attendee holds it as part of the bot's configuration.
- Replies are spoken a sentence at a time. The worker sends each sentence's text to the bridge as it is written (`?action=say`, newline-delimited JSON); the bridge synthesizes it with Aura and plays it, starting the next sentence's synthesis while the current one plays. Aura streams raw 24 kHz PCM, so the first audio arrives well before a sentence is fully synthesized. Each synthesized sentence is recorded as `CLOUDFLARE_AI` usage (`@cf/deepgram/aura-2-en`, $0.03 per 1,000 characters). When Aura fails on a sentence, the bridge reports where, and the worker speaks the remaining sentences through the fallback routes as PCM (`?action=speak`) without repeating what was already spoken. This starts while the agent is still writing the answer, in read-only and actions meetings alike. On the fallback routes, gateway speech returns each sentence's clip whole and the OpenAI Direct route streams PCM as synthesis produces it. Markdown and URLs are not read aloud (a URL is spoken as "the link"). A request that comes with its wake phrase ("Hey Fabric, what is the status?") is handed to Fabric as soon as Flux ends the speaker's turn, with no extra wait. A request that follows a bare "Hey Fabric" waits until the requester has been quiet for 300 ms (8 s cap); the requester's further words extend it, and Flux's empty start-of-turn events do not. The bridge's `parlume.bridge.turn.dispatched` log records `endpointMs` (wake phrase to the end of the request) and `handoffMs` (until Fabric accepted it). Speech from a participant other than the Parlume bot, including an unknown speaker, interrupts playback while Parlume is audible, but only when it wants the floor: at least two words that are not an acknowledgement ("yeah", "mm-hmm", "got it, thanks", "right") or a single-word remark. Speaking over Parlume **mutes** the reply rather than cancelling it: the audio stops (`parlume.bridge.speech.muted`), the turn keeps running, its tools stop being narrated, and everything the meeting did not hear to the end goes to the meeting chat as one tagged post when the turn finishes. Fabric notes the time on the request (`/api/internal/parlume/interrupt` with `kind: "mute"`) and neither cancels its workflow nor marks its actions. A change the agent asks for after the mute, and before it started running, is not made: it is recorded as cancelled ("Held before dispatch"), the agent is told so, and the chat gets `[P7] I did not create story “Export” because I was interrupted. Reply "go P7" to do it.` A **cancel phrase** ("stop", "cancel", "never mind", "not that", "hold on", "wait", alone or after the wake word, as in "Parlume, stop"), a new wake phrase, or `stop` in the chat still cancels the answer outright, tools included, and a cancel phrase never becomes a request of its own (`parlume.bridge.turn.cancelled_by_speech`). Speech attributed to the bot itself never interrupts it, but attribution comes from Attendee's speaker webhooks, which arrive after the audio, so barge-in is best-effort. Attendee cannot drop audio it already holds, so an interruption silences a reply within about 200 ms rather than at once. Model generation, transcription and network latency still affect response time; live meeting latency has not been verified.

Spoken replies are tuned for speed. The model gets the least reasoning effort it accepts (OpenAI reasoning models only), the Fabric prompt enhancer is skipped, and the reply reads a small slice of the meeting: the last three minutes of transcript (at most 4,000 characters, the most recent kept), three project passages, and the last four answered questions. The worker logs one `parlume.turn.timing` record per turn: the milliseconds each step took (agent load, decision, project retrieval, transcript and history queries, MCP and memory lookups, model resolution), the model's time to first text and total time with its token, reasoning-token and cached-token counts, and each sentence's speech route, time to first audio byte and total time. When the bot is admitted, the worker also runs the first steps of a turn once (`parlume.session.warmed`) so the first question does not start cold. The prompt is kept lean without removing a tool: an earlier answer replayed in the history keeps its first 600 characters (the latest is replayed whole, so "continue" works), the Fabric Agent reads two workspace passages rather than the workspace default of five, and the inviter's recalled memories are cut to 1,500 characters at a line break. The engine's `System context constructed` log records the characters of the system instructions, each context section, the memory and the history, and the number of tools, so a turn's input can be read off the log.

**Headline, then detail.** A spoken answer is one or two sentences. When more would help, the agent writes a line holding only `---` and then the detail; the worker speaks what comes before the line (at most 350 characters) and posts what follows it, together with anything past that limit when the line is missing, to the meeting chat as one tagged post when the turn finishes. Nothing is dropped: a reply that was spoken over posts everything not heard to its end instead. When the bridge has marked the chat unavailable, the reply speaks its detail too, up to 800 characters, and ends with "There's more; ask me to continue." Live transcription is primed with the single keyterm "Parlume": the Workers AI binding takes one `keyterm` string, and whether it accepts several has not been verified.

**Writing in the meeting chat.** Ask Parlume to share, post or write something in the chat ("put the link to F-123 in the chat", "post that summary") and it calls `post_to_meeting_chat`. The tool works in read-only and actions meetings alike, because it changes nothing in Fabric, and it sends at most three messages per answer. `text` is sent as the participant asked, URLs included. `links` are resolved by the worker from the meeting's own project, after an access check, into full direct addresses: a work item by identifier (`F-123`, `123`, `B-9`) or id, a document by id or exact title, a Context source by id, or the roadmap, decisions, documents or context tab. A reference outside the project is refused and reported back, and the addresses use the project's own organization, so they work for guests of another organization's project. The message is plain text, one link per line (`F-123 · Title — https://…`), within the chat's 4,000-character limit including its tag; the text is shortened before any link is dropped. Each send is logged as `parlume.chat.posted` (the event keeps its name) with `sent`, `delivery: "queued"`, the post's tag and counts, and no content.

**Delivery is confirmed, not assumed.** Attendee only queues a chat message: its Teams bot drops one silently when the meeting gives it no chat box, and reports it sent anyway. So Parlume never says a message is in the chat because Attendee accepted it. The tool answers `{ sent: true, delivery: "queued", tag }`, and the agent says it has *sent* the message. Every Parlume post opens with a short tag, `[P1]`, `[P2]` and so on, numbered per session in the bridge, which keeps the last 50 posts (tag, text, request). Fabric subscribes each bot to Attendee's `chat_messages.update` webhook. A chat message that opens with a waiting post's tag, or comes from the bot's own name, confirms that post (`parlume.bridge.chat.confirmed`, with its latency). A post not seen within 8 seconds is logged as `parlume.bridge.chat.unconfirmed`. If the bridge has seen no chat message at all since the bot joined, it marks the chat unavailable (`parlume.bridge.chat.unavailable`) and Parlume says once, aloud: "I can't write in this meeting's chat. Guests may not have chat here." Later `post_to_meeting_chat` calls then answer `{ sent: false, delivered: false, reason: "chat_unavailable" }` at once, so the agent says the content instead. Any chat message seen later clears the mark. The bridge reports each outcome to `/api/internal/parlume/chat-delivery` (`parlume.chat.delivery`). A post that never appeared, or appeared late, adds a note to its request in the Requests list. A reply that could not be spoken goes to the chat in tagged posts of at most 4,000 characters, and its request records which tags carried it. Whether a Teams bot's own messages come back through `chat_messages.update` has not been verified. If they do not, a meeting where nobody has typed yet will be marked unavailable after Parlume's first post.

**Reading the meeting chat.** Every chat message, the bot's own included, is stored with the meeting's transcript segments (`ParlumeMeetingSegment.source = CHAT`), placed on the same clock as the speech around it and stored once per Attendee message id. A spoken or typed request gets the last 20 chat messages, at most 2,000 characters, as a separate "Recent meeting chat" block, so "Parlume, what did they write in the chat?" works. The spoken transcript block no longer includes chat lines. In the saved transcript and the notes, chat lines are marked `[chat]`.

**Typing to Parlume.** Teams chat has no buttons, so a post's tag is the handle. A message addressed to Parlume (an @mention of the bot, a message that opens with "Fabric Parlume", "Fabric," or "Parlume,", "Hey Fabric …", or a private message to the bot) becomes a request like a spoken one (`ParlumeMeetingTurn.replyChannel`). It replaces whatever Parlume was answering, as a new wake phrase does, and its answer goes back to the chat, in as many tagged posts as it needs, without being spoken. A request that asks to be said aloud ("say …", "tell everyone …", "announce …", "… out loud") is answered by voice. Short commands work whether or not they are addressed: `say P7` reads post 7 aloud, `go P7` speaks suggestion 7 or, on a change Parlume held back, asks for that change again as a request typed in the chat (once), `more P7` asks for more on post 7 with the answer in the chat, and `stop` cancels what Parlume is answering, as a spoken cancel phrase does. The bot's own messages are never treated as commands, and a redelivered webhook is recognized by its message id. Text read aloud from a post says "the link" for an address. That speech is synthesized in the bridge and is not yet recorded in the session's usage.

**Suggestions.** While the meeting stream is live and Parlume is neither speaking nor answering, the bridge's alarm runs a suggestion pass every 90 seconds, once at least three new final speech segments have arrived since the last pass and the chat is not marked unavailable. It posts to `/api/internal/parlume/suggest`, which reads the last three minutes of speech, the recent chat, the earlier suggestions and three project passages, each fenced as untrusted data, and asks the organization's fast model (`SIMPLE`, simple complexity) for `{ suggest, text }`. The instructions are the seeded, bindable **Parlume Meeting Suggestions** prompt (`parlume_meeting_suggestion`, under Meetings & Intake). The model's output is read leniently: anything malformed counts as no suggestion. Usage is recorded under the `parlume` feature key with the session id as `conversationId`. The bridge posts at most one suggestion per pass and twelve an hour, and drops one that shares most of its words with a suggestion from the last hour. A suggestion reads `[P8] Suggestion: … (reply "go P8" and I'll say it)`; Parlume speaks it only when someone replies `go P8`. **Chat suggestions** is on by default in the invite form and can be switched off per invitation (`ParlumeMeetingSession.suggestionsEnabled`); the bridge learns the setting when the stream is verified, and the suggestion route checks it again. A suggestion is model-written text: it may be wrong, and something said in the meeting may steer it. It can only be posted in the chat or read aloud on request; it calls no tools.

**Realtime voice.** When the inviter's organization has an **OpenAI Direct** key, Parlume talks through an OpenAI Realtime speech-to-speech session (`gpt-realtime-2.1`) instead of the classic chain of Flux, the agent and Aura. Nothing turns it on or off: once the stream is verified, the bridge asks `/api/internal/parlume/realtime-session` once. That route checks the session is live and the inviter still has access, resolves the organization's OpenAI key, and mints a short-lived client secret (`POST /v1/realtime/client_secrets`) whose session carries the instructions, three tools and the audio settings. The key itself never leaves the web API and is never logged; the bridge only holds the secret. With no key, a refused mint or a socket that will not open, the route answers `404 { engine: "classic" }` or the bridge gives up, and the meeting uses the classic voice. The choice is logged as `parlume.bridge.engine` with the engine and the reason. The instructions are the seeded, bindable **Parlume Realtime Voice** prompt (`parlume_realtime_voice`, under Meetings & Intake), followed by the project name, whether changes are allowed and who has spoken so far, fenced as meeting data.
- The bridge opens the session itself (`wss://api.openai.com/v1/realtime`, the secret sent both as a bearer header and as the `openai-insecure-api-key` subprotocol) and streams all the meeting's audio into it, resampled from Attendee's 16 kHz to 24 kHz and appended in 100 ms batches. Flux keeps running on the same audio for the transcript, speaker attribution, wake detection and notes. The session's voice activity detection (`semantic_vad`) reports when speech starts and stops, but `create_response` and `interrupt_response` are off, so the session never answers on its own. The bridge creates a response only when someone says a wake phrase (in a Flux partial or final) and then stops talking (OpenAI's `speech_stopped` or Flux's end of turn, whichever comes first), when a chat message asks for a spoken answer, when a chat post is read aloud (`say P7`, `go P7` on a suggestion, the chat-unavailable notice), or when a Fabric job has a result. The voice is played through the same outlet as the classic voice, 24 kHz with the same 200 ms lead.
- Barge-in uses the same rules as the classic voice. Speech that wants the floor stops the response (`response.cancel`) and cuts the assistant's audio item to what the meeting actually heard (`conversation.item.truncate`, from the bytes the outlet sent; `parlume.bridge.realtime.truncated`), and the conversation goes on. A cancel phrase or `stop` in the chat also cancels a running Fabric job, as `/api/internal/parlume/interrupt` does for the classic voice.
- The session has three tools. `ask_fabric({ request })` hands anything that needs project knowledge, Fabric data or a change to an ordinary meeting turn (`/api/internal/parlume/turns` with `delivery: "realtime"` and a job number such as `J3`), recorded like any other request, with the same actions policy, audit, receipts and history. The tool answers at once with `{ status: "started", job }`, so the voice says a holding line and the meeting carries on; one job runs at a time. The worker runs the agent as usual but speaks nothing: it releases the turn, posts an answer longer than 350 characters to the meeting chat in full, and posts the answer to the bridge (`?action=fabric-result`). The bridge waits for any response in progress to finish, adds the answer to the conversation labelled as the result of that job, and has the voice say it. If the bridge can no longer take it, the answer goes to the chat. `post_to_chat({ text })` posts a tagged, delivery-confirmed chat message; `read_chat({})` returns the last 20 chat messages the bridge saw. The session can change nothing in Fabric by itself.
- OpenAI ends a Realtime session after 60 minutes. At 55 minutes, at the first quiet moment, the bridge opens a new session with a fresh secret and seeds it with the meeting so far (the last 40 transcript lines, Parlume's own replies included), then closes the old one. An unexpected close is retried after 1, 3 and 10 seconds; after that the meeting stays on the classic voice for the rest of the meeting (`parlume.bridge.realtime.reconnect`, `parlume.bridge.realtime.dropped`). Logs never carry transcript text or secrets; `parlume.bridge.realtime.response` records the latency from the trigger to the first audio.
- Each response's usage (`response.done`) is reported to `/api/internal/parlume/realtime-usage` and recorded as `OPENAI_DIRECT` usage of `gpt-realtime-2.1` under the `parlume` feature key with the session id as `conversationId`, priced per 1M tokens at $32 audio input, $0.40 cached input, $64 audio output, $4 text input and $24 text output. The meeting's audio streams in continuously but is billed only when a response reads it, so the responses' usage is the whole bill. At about 10 input audio tokens per second, an hour of meeting audio heard once costs about $1.15; with prompt caching on the rereads and a few minutes of spoken answers, an hour of meeting comes to roughly $1.70 at list prices. That estimate, live latency, barge-in behaviour and whether the Workers runtime passes the upgrade's authorization have not been verified in a meeting.
- Full transcript text is retained as project context and notes are generated asynchronously. Context includes separate incoming speech and recorded Fabric responses with request statuses, playback interruptions, and individual action tool names and receipt statuses; generated success claims do not override failed or unconfirmed receipts. The bot's data in Attendee is deleted (`delete_data`) after finalization when its API succeeds; Attendee allows that only once the bot has ended, so a failed attempt answers the terminal webhook with an error and Attendee redelivers it. Failed cleanup is left visible for operator recovery.
- The hard stop is four hours; a provider bot can incur charges while waiting in a lobby. Attendee, live transcription, speech synthesis, and the agent's configured model accrue costs only during meeting work.
