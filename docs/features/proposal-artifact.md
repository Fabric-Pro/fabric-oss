# Proposal Artifact

How one generation request produces a client-ready Proposal, its visuals and a separate Internal Analysis, and how to roll the feature out.

- **Audience**: Developers extending Proposal generation; operators enabling the feature for an organization
- **Owner**: Documents

## What it is

With the `PROPOSAL_ARTIFACT` rollout gate on for an organization, generating or regenerating a Proposal runs one coordinated job instead of the Draft followed by a Glossy edition:

1. the **Main Document** is written from a client-only prompt and its finished sections appear on the page while the agent is still writing;
2. visuals are added to the Main Document in the same job;
3. after the Main Document is saved, an **Internal Analysis** reviews it against the same source context and records findings that only members of the organization can read.

The Main Document is the client artifact: it never carries review notes, citations, a source index or readiness status, and every download exports it alone. Its PDF and Word files are printed by the server from the same theme the page wears (see [Export](#export)). Business Case and every other document type keep their current flow, and a Glossy edition that already exists for a Proposal stays reachable while `GLOSSY_EDITION` is on. The terms are defined in [CONCEPTS.md](../../CONCEPTS.md#proposal-artifact).

## Generation

The decision is made once per run, inside `documentGenerationChildWorkflow`, behind `patched("proposal-artifact-v1")`, so every path that generates a Proposal (editor, documents list, chat, create dialog, setup wizard, uploads) takes the same branch. The plan activity reads the gate for the project's owning organization first and returns nothing when it is off, so organizations without the gate never depend on the new prompt actions.

- **Prompt.** Main is rendered from the prompt bound to the `proposal_client_main` action, at the bound version, on every retry. The editor's prompt choice and `DEFAULT_PROMPTS` are not used. When nothing is bound, generation is refused with a message naming the action: early at dispatch and in the setup wizard, and authoritatively in the workflow before the agent is called. A personal binding on this action is refused, so no individual prompt can steer the client document.
- **Live sections.** The activity reads the agent's cumulative previews, keeps the text up to the last completed H2 or H3 section, and writes it to `ProjectDocument.liveContent` at most every 1.5 seconds, followed by a `document_change` nudge carrying ids only. `content` is untouched until the final save. Every write is owned by the run's `liveRunId`, so a superseded run can write neither previews nor the final document.
- **Long streams.** A client-document Proposal's agent stream gets a first-chunk allowance (300 s) and a wall cap taken from the activity attempt's deadline less a reserve; the idle limit only logs unless `AGENT_STREAM_IDLE_TIMEOUT_MS` is set. When the stream gives up, the live preview is stopped, not cleared (progress milestone "preview stopped"), and a bounded, cancellable plain-generation fallback writes the document with a sign of life. Other document types keep the earlier limits. For every document type, an agent run that ends in an error falls back the same way rather than saving its last preview, and the fallback saves only a document the model finished on its own: an ending at the token limit, on an error, on a content filter or for no stated reason fails that attempt and saves nothing, so a partial document never becomes a version.
- **One run at a time.** A regeneration asked for while a Proposal run is live joins it instead of starting another: dispatch takes a per-document advisory lock, asks Temporal whether the recorded workflow is still running (running, gone or unknown), and answers "already in progress" or "could not confirm the running generation". Its Temporal start and the follow-up check are bounded so the locked section ends well inside its transaction. The queue mark retries once when an unrelated edit (a title change) declined it, unless a newer attempt owns the row.
- **Visuals.** Before the save, timeline, flow, org-chart, architecture-layer and team visuals become Mermaid fences and comparisons become tables, inserted after the first block of their section; a cover letter (see [Markdown the theme styles](#markdown-the-theme-styles)) gets none. Colours come from the shared brand resolver: the document's Style, then the organization's Brand kit, then the colours the organization's website declares, then the neutral style; a recipient colour never stands in for the proposer's. Sections that already hold a Mermaid diagram are skipped. The step is bounded and fails open: the Main Document is saved without visuals rather than lost. For a Proposal, every figure the step adds carries a caption (its title, a short caption the extraction returns, or the section heading without its number), never with a storage path in it; a new timeline needs a short date or period for every entry, or the section keeps its prose; a comparison whose options have uneven points is left out; labels start with a capital; a detail or description too long for its line is left out whole rather than cut, and a team card keeps the person's name under a long role; a title past 56 characters is cut at a word with an ellipsis, and a drawn figure ends a title its box has too few lines for the same way, and cuts short any single word wider than the box. Edit with instructions redraws a figure under the current label rules, but does not hold an existing timeline to the date rule: the model is told to keep its dates as written and add none the section does not state. The diagrams come from this step, not from the bound prompt: a model picks the sections that suit one and code builds the fence, so no prompt text asks for these diagrams (the Main prompt writes only bar charts), and a section whose own text (the prompt's output or a person's edit) already holds a diagram is left alone. The prompt library's binding dialog says so for Client proposal (Main), and the diagram's ⋮ menu labels a generated one "Added automatically". The Style tab's **Add diagrams automatically** switch (on without a saved Style) turns the step off for one document: it then adds none and makes no model call, and diagrams already in the document stay.
- **Analysis.** After save, version and embed, a non-fatal block records an analysis run and starts `proposalAnalysisWorkflow` with an abandon close policy. The run stores the saved Main Document, its hash and a bounded copy of the generation's source context. Analysis is not run for generations a project guest started, and an unbound `proposal_internal_analysis` action records a failed run without affecting Main.

## Internal Analysis

Findings carry a severity (Blocking, Important, Informational) and a type (Scope, Commercial, Assumption, Risk, Gap, Source Validation, Architecture, Branding, Opportunity). The library prompt owns the instructions; the code owns the output contract.

Analysis rows, findings and reports live in `ProjectDocumentAnalysis` and `ProjectDocumentFinding`, organization-only tables (`ORG_ONLY_TABLES`, `org_only` RLS). They are never part of `ProjectDocument.content`, a version, an embedding, an MCP or v1 read, or an export. `projects.proposalArtifact.getAnalysis` returns, to organization members only, the newest complete run whose analysed text matches the current text, else the newest complete run labelled stale, together with the status of any newer run; a newer run that is pending, running or failed never hides a complete one. A project guest receives FORBIDDEN with `ORGANIZATION_MEMBERSHIP_REQUIRED`. Staleness compares a prose hash (see Review), so an editor save or a recolour that leaves the text alone does not mark a run stale. A run is timed out when it has made no progress for 20 minutes.

## Review

Fizzy #2946 makes the analysis something members act on.

- **Sections and prose hashes.** `@repo/utils/proposal-artifact/section-hash` parses the Main Document once with remark and splits it at every heading. A section's key is its heading path (numbering and the document title left out) plus an occurrence index; its prose hash covers its own text after parsing, with separators for blocks, list items and table cells, and without Mermaid fences, visual markers, visual slots or link and image addresses. Keys and hashes carry a `p1:` version prefix, and the same golden fixture is asserted in Node, jsdom and the worker, plus a round trip through the editor's load and save.
- **Findings.** The analysis lists the sections by number and asks for the section index, a short subject and the source numbers each finding relies on. A finding's stable key is its type, section key and normalised subject, never its wording; findings that share a key in one run fold into the first, which keeps the most severe of their severities and the others' titles, details and recommendations.
- **Evidence.** On the Proposal branch, retrieval also returns a manifest of what each source string was (project context, company source, project summary, other). The run keeps the entries for the sources the analysis actually read, numbered as the `### Source N` blocks the model saw. Evidence is read from each source's current row, never from a copy kept with the run, so text removed from a source does not resurface: project contexts and company sources show their current title and the opening of their current text, LINK and meeting transcript contexts also link to their pages, and the project summary and other sources show their label only. A source that no longer exists in the project or organization shows as removed, with nothing else; a run recorded without a manifest shows no evidence rather than calling its sources removed. No source address is ever returned.
- **States.** A finding is Unaddressed, Confirmed, Responded, Resolved or Needs Review. Responses (`ProjectDocumentFindingResponse`, organization-only like the analysis tables) belong to the document and the stable key, not to a run. Needs Review is derived at read time, never stored: the section's prose hash differs from the one the answer was given against ("section changed"), the section is gone ("section not found"), or a later run raised the key again ("raised again"). Answers whose key the shown run does not raise are listed as no longer raised, with their own state. `finding-state.ts` in `@repo/utils` is the one derivation the page and the settled feed both use.
- **Answering.** `respondToFinding`, `clearFindingResponse` and `rerunAnalysis` need `DOCUMENT_UPDATE` and organization membership; commenters and viewers read only, and guests are refused. Writes use a compare-and-swap on the answer's id and version (so an answer cleared and given again never matches a stale tab's copy) and return a stale outcome, not an error, when another member saved first or the run changed. Audit actions `project.document_analysis.responded`, `cleared` and `rerun_started` carry keys and kinds, never answer text, and the error-capture middleware skips `respondToFinding` so a refused call cannot copy an answer into the audit log either.
- **Re-run.** A re-run analyses the current text against the stored sources of the generation that produced it, even when that generation's own analysis failed (or else the newest generation run with sources), through the existing `proposalAnalysisWorkflow` under a per-run workflow id. It is refused while the document is generating or another run is in progress; a run with no update for 20 minutes counts as finished. Re-runs are limited per organization. Regenerating is how new sources are picked up.
- **Report.** When the bound analysis prompt asks for an overall review report, each run keeps it beside its findings, in two columns of the run: the structured fields (overall assessment as the model wrote it, summary, Must/Should/Could scope items, what to resolve before sending and what during discovery, the sources it cites) and the full report text. After the findings call, a second, plain-text call in the same activity asks for it, with the same instructions and sources plus the findings already recorded, so it describes the same review; its Output block defines the format only (Markdown, a length bound, `[S<N>]` citations naming the outer source blocks, a trailing `json fabric-report` block with the fields, or `NONE`). The call is skipped for the seeded findings-only analysis prompt (matched by a hash of its text, so a new library version needs no deploy). The findings call itself is unchanged, and any failure of the report (a provider refusal, the call's own deadline inside the activity window, an empty or unreadable answer, an error writing it) completes the run with its findings and no report. The run completes once, after both calls. Before anything parses the text, a linear check (`reportTextNeedsPlainText` in `@repo/utils/proposal-artifact/report-text`) flags text that would make Markdown parsing slow or crash: deep nesting, large or numerous tables, too many lines or block lines in the whole report, a quote or list item continued on hundreds of unprefixed lines, very long lines, dense emphasis or escapes in one paragraph, long punctuation runs inside a bare link, unclosed inline HTML openers and unbalanced brackets. Its limits were set by timing the parser on hostile shapes, so a parser upgrade should re-run those timing tests. Such a report is shown as plain text. The flag is also set when the worker's own Markdown scan fails, and the check runs again on every read, so a stricter check also covers reports stored before it. Citations are found once, when the run completes, and resolved at read through the same evidence rules as findings, including "source removed". The report is read only by `getAnalysis`, for the run it shows, and never reaches a guest, Main, the settled decisions, a prompt, an export, MCP, an embedding, an SSE payload, workflow history or a log. Runs recorded before it, and runs under a prompt that asks for none, have no report.
- **Settled decisions.** `buildSettledDecisionsBlock` (`@repo/temporal/proposal-artifact-settled-decisions`) turns the document's confirmed, answered and resolved findings into a fenced block for the Main generation and the analysis. It keeps only answers that are not in Needs Review and whose author is still an organization member with edit rights, neutralises and caps each one, and returns nothing for a guest, a system start, a missing organization or any error in its checks. It is joined to the prompt, never assigned over supplied context. Before writing a live preview and before saving a Main Document that carried the block, the generation refuses (`RESPONSE_ECHOED`, not retried) when the text repeats a run of 12 or more words from an answer or a finding title that the sources, the project information in the prompt and the previous Main do not also contain. A whole finding title of four words or more is not refused there, because a generation cannot be retried; the worker logs its key so it can be watched. Chat, Apply recommendation, section revision and the save checks refuse it. The refusal message every reader sees names no answer; the worker log records the stable keys of the answers involved, so the answer to reword or clear can be found. Shorter answers are not checked: a short factual answer is expected to shape Main.

## AI edits of Main

Fizzy #2946: the AI writers Fabric runs inside the document page, chat, Apply recommendation and Revise this section, run on a client-only prompt from the library and are checked on the server, whoever starts them; MCP and v1 updates get the same diagram and echo check.

- **Chat prompt.** The editor adds `documentId` to the CopilotKit route's query. For every agent run (and suggestion) the route loads the document, requires the project's owning organization and project access, and, for a client-document Proposal, resolves the bound **Client proposal (revision)** prompt (`proposal_client_revision`, no personal tier) and the settled decisions for the person chatting (none for a guest). It writes them into the run's `forwardedProps` (`proposal_mode`, `proposal_client_prompt`, `proposal_settled_block`, `proposal_echo_carried`, `proposal_viewer` (member or guest), `proposal_attachments` and `proposal_clarifying_policy`), which the agent reads as config; client values for these keys, and the client's `systemPrompt`, `suppressFabricMethodology`, `activeSkill`, publishing topic, `refreshSpecContexts` and project context (state and readables) are removed; the project id the agent works on is the verified document's. The system prompt is built from server config only, and the document, its section headings and the editor's action definitions come from the server or reach the model as the person's material: the agent reaches project material through its server-side `search_project_knowledge` and `read_project_source` tools, and files attached in the chat reach the model inside the person's latest message, marked as their material, never as instructions. The editor and the agent take the browser actions' definitions from one module (`@repo/utils/editor-frontend-actions`), and the clarifying-question policy is the route's: for a member, the organization's bound Clarifying questions prompt for the project's frequency, otherwise the built-in text; a guest always gets the built-in text. CopilotKit's runtime `properties` never reach the agent, so the route no longer puts prompts there. An unbound prompt leaves the chat without write tools and says what to bind; a Proposal chat from a page without `documentId` (an older bundle) asks the person to reload.
- **Chat edits by section.** In this mode the agent edits only through heading-anchored patches (replace, insert before or after, append or prepend to, or delete a section and its subsections), never a whole-body write or a text replace; diagrams and visual slots reach the model as placeholders and come back unchanged. It refuses a proposal that repeats 12 or more words of a settled answer, or a whole finding title of four words or more, before showing it, and reports which sections it patched. No live preview of a whole-document write is streamed, and when a changed section holds a diagram, the reply says the diagram was left as it is and which of its menu actions changes it.
- **Apply recommendation.** A member with edit rights can apply a finding's recommendation to the finding's section from the Analysis tab. `projects.proposalArtifact.reviseSection` rewrites only that section's own lines with the revision prompt and returns a checked candidate and a signed revision token; it writes nothing. The page switches to Main, the editor shows the change for review, and the finding shows Revision in progress until it is accepted or rejected.
- **Revise this section.** In the editable editor, each `##` heading of Main offers a member with edit rights a "Revise this section" control (shown on hover, when the caret is in the heading or on keyboard focus; the controls follow the editor in the tab order, each named after its section). It opens a box under the heading for an instruction of up to 1,000 characters; Escape closes it and returns focus to the control. Submitting calls the same `reviseSection` with the section's key and the instruction instead of a run and a finding (exactly one of the two, or `BAD_REQUEST`), under the same authorization, rate limit, bound prompt, settled decisions, model resolution in the owning organization and checks, and the editor shows the section's diff for Accept or Reject on Main. Focus follows it: to the "Revising the section…" status while it is drafted, then to the review's summary (its title, with what Accept and Reject do as its description), or back to the editor when it ends without a review, whose reason a toast says. While it runs, every Apply recommendation on the Analysis tab is disabled and says it waits for the section revision. The server accepts a section heading of any level; the preamble is never a target (`SECTION_NOT_FOUND`). The instruction reaches the model in its own block as the member's request, which may supply wording but never changes the rules or the target; it is never treated as internal text, and it appears in no log, audit row or version description (a failed call's error capture records it only as a size and hash, as it does for Edit with instructions' request). Project guests and members without edit rights are not offered the control, and the server refuses them as it does Apply recommendation. Like every oRPC procedure it takes a browser session, not an API key.
- **Checked on save.** An accepted AI change is saved through `projects.documents.update` with an `aiReview` descriptor. For a client-document Proposal the server then refuses a change outside the patched sections or the revised section (`REVISION_OUTSIDE_TARGET`), any change to an existing diagram (`REVISION_CHANGED_DIAGRAM`) and a body that repeats a settled answer (`RESPONSE_ECHOED`). A section outside the target is compared by its fingerprint, not its bytes, since the editor's save re-serialises every section: its heading path, its text (whitespace collapsed, Markdown markers and HTML tags left out), its link and image destinations (a reference resolved by the first definition of its label, as it renders) and its diagrams. A formatting-only change outside the target therefore passes; the editor's own splice leaves those sections as they were. Accepting an applied recommendation also verifies the token and records the finding as Resolved, with `project.document_analysis.resolved`, in the same transaction as the save. Accepting a section revised on an instruction (`aiReview` kind `INSTRUCTION`) verifies its own token, which is signed for the member, the document, the base version and the section and never verifies as a finding's, resolves nothing, and records `project.proposal_artifact.section_revised` with the base and saved versions only, in the same transaction; its version is described generically ("Revised a section with instructions"). The reviewing tab keeps the others held and its own editor read-only until the save answers; a refused accept puts the body from before the proposal back and offers the refused text once.
- **Whole-body rewrites refuse.** "Update using context" and Living Docs auto-refresh would rewrite every section with a fixed prompt, so they refuse a client-document Proposal (`PROPOSAL_USE_CHAT_OR_REGENERATE`, `PROPOSAL_AUTO_REFRESH_UNSUPPORTED`); an enrolled Proposal is skipped and switched to propose-only. Regeneration stays the one whole-body writer.
- **Resolved.** Resolved feeds later work as settled like a confirmation and needs review like the other answers; the answer path never writes it, and confirming one again records a confirmation.

## Editing while a run is live

Fizzy #2946 production feedback: a regenerated Proposal could flash back to, or be saved over with, its previous version in the shared editor.

- **Outside writes wait for the run.** While a Proposal is queued or generating, its body and status cannot be changed by an agent (`fabric_update_document`), the v1 API, a status change, "Update using context", a version restore, a rejected regeneration or its fallback save, or an accepted or scheduled refresh. `updateDocument` refuses such a write at its read and adds the live statuses to the guarded `UPDATE`'s condition by default, so a run queued after the read is refused too (`DOCUMENT_GENERATION_IN_PROGRESS`); only the editor's plain content save opts out. This is decided by the document type (`isRunGuardedDocumentType`), not by the rollout gate, because a run outlives a change of the gate. Ordinary editor saves are not refused by status; they name their base, and the editor's own rule stops saving while a run still writes.
- **Generation statuses belong to runs.** QUEUED and GENERATING cannot be sent on any document create or update through oRPC, v1 or MCP (`DOCUMENT_STATUS_GENERATION_OWNED`); they are set by dispatch with the workflow id and start time the stale-run watchdog needs.
- **Every save names its base.** Reads return `version` and `contentHash` (`contentIdentity`, SHA-256 of the body). A save sends both as its base, and `updateDocument` puts version and body in its `WHERE`, so a run's body saved at the same version is not overwritten. With `DOCUMENT_ROOM_CONVERGENCE` on (default), a client-document Proposal save without a base is refused (`DOCUMENT_SAVE_BASE_REQUIRED`); with it off, saves send no base, except an accepted AI change on a client-document Proposal, which still sends the base the editor loaded so the server's check can compare against it. Agent writes may omit the base; they are then guarded by the body the same call read. The MCP update result carries the next base.
- **The shared room converges.** The room (Yjs in a Durable Object) carries a stamp of the saved body it descends from. A run's start, its final save and its version step each send a `document_change` nudge under an id no member has (so no tab takes it for the echo of its own save): a Proposal's page and a collaborative document's page read the document then (the latter within a second) instead of on their next poll. At the end of a run one editor puts the run's body into the room with its stamp at once: the tab that started the run (through its review), otherwise one tab that followed the run, so it does not matter whether the run was started from an open tab, by a colleague, the API or an agent. A review speaks for its own run only: each tab names the run its role is for, a follower does not wait on a review of another run, and a newer run started anywhere closes the review so its tab follows the newer run. A tab that finds the room behind the saved document claims the update in the room's metadata, one edit-capable peer applies it, and replaced unsaved typing is offered back once with a copy action. That fallback takes a second look one poll later, during which saves wait. When what the tab learned is the end of a run the room has not taken in, its editor (the raw markdown view too) stops taking input at once and, after 750 ms, shows the run's saved body read-only until the room holds it, so nobody types into the previous body. A tab that has not seen the room in step yet, opened or back from a dropped connection with the room already behind, cannot tell a run's end from a rewind and only holds the room's body read-only until the second look. A tab with typing of its own keeps the room's body on screen, and so does any other difference between room and saved document, such as a write outside a run or the rewind of a rejected regeneration. Only an empty room is seeded, and the editor binds the `"default"` fragment. Run state survives the editor's remount on a lost connection; after 45 s without the room the page turns read-only. A run counts as still writing for ten minutes after its last write. An assistant proposal waiting for an answer is in the room too, so the tab reviewing it says so in its awareness state: from the assistant's first frame in its editor through the chat's confirm card (a run that ends without a card, stopped or failed, stops two seconds later, unless the chat's last turn still holds an unanswered `confirm_changes` call, whose card is then waited for up to 20 seconds after the run ended (a run that failed after naming the call never runs it), while the tab's own saves wait too; in a shared room its tab then puts the body from before the run back, says so, and resets the agent's document to it, and a second run started meanwhile is taken back to the body from before the first; alone, the editor keeps the partial text as before), or for an update using context from the moment it starts drafting. Every other tab that may edit holds still until the proposal is answered or that tab goes: its editor and raw view take no input, its saves and autosave wait, the view switch, Update using context, Regenerate (button, menu and chat; the chat's call is answered as not started, and the chat says why rather than that the regeneration completed) and version restore wait, its own assistant puts nothing into the editor (a run that began or wrote meanwhile is answered as not applied, and an Accept of a proposal it already holds waits), the sync pill says why, and no tab brings the room to a newer saved body underneath the proposal. The review is said in the room before any of its body is written there, and a save from another tab is judged by the room as it stands when the save would go, so one due in the moment before that tab shows the hold sends nothing; an update using context whose preview answers meanwhile, or after the body changed since it was asked for, is dropped, and a convergence that already put the saved body in reads it back only after the answer, judging by the room's awareness when it would write. Two tabs that begin a review before either hears of the other settle it the same way everywhere: the review that began first holds (the smaller client id breaks a tie), and the other tab withdraws its own — its card is answered as not applied, its stream stops, its update using context is dropped — without writing the room, while the first one puts its proposal back over anything the other wrote. A tab that drops off stops holding the others once the room drops its awareness state: at once when it closes, otherwise within about 30 s. A reviewing tab whose page is left within the app (the page's Close, a link) while its proposal is still unanswered rejects it on its way out: it puts the body from before the proposal back into the room (the body the chat's run started from, or the one an update using context was drafted from) before the room is torn down, without answering the chat's call, and saves that body when it holds typing of its own that no save covered and nothing else holds saves (a run writing the document, the room behind the saved body, a lost connection); the proposal itself is never saved. Closing or reloading the tab does the same from `pagehide`, as far as the browser still sends it. A proposal left waiting for its answer, while another tab that may edit is in the room, holds the others for at most ten minutes with no key, pointer, wheel or scroll in the reviewing tab and no return of that tab into view: that tab then answers it as rejected (stamped on the chat's tool call as the review bar's Reject stamps it) and says so. The other tabs never stop holding on their own, since they would save the unanswered proposal. The held tabs' status names the person reviewing, as their tab publishes it with its cursor (an editor without a name, published as "Anonymous", names nobody). Limits: a page kept in the back-forward cache (`pagehide` with `persisted`) takes nothing back, since it may come back with the review still open, so its proposal stays in the room once its awareness state lapses; a lost connection is not taken for leaving, and the editor mounted again finds the room as it was; a background tab's timers may run late, so the ten minutes can be longer; and a tab killed without `pagehide` (a crash) leaves its proposal in the room. In those cases another tab can still save the proposal once the hold lapses.
- **Unsaved typing is kept.** A save's answer marks as saved only what it carried, and a failed save leaves its text unsaved — an accepted assistant proposal included, which reads as unsaved from the moment it is accepted until its save lands, and whose outcome the conversation records only once that save answers, showing a card when it was not saved (the assistant's own reply only acknowledges the acceptance); the error a failed save shows is cleared by the next save that lands; an undo in the shared editor counts as typing and is saved; an accepted proposal undone before its save lands is never written; typing that survives a short disconnect stays unsaved and is autosaved, also when the save in flight across the disconnect fails; leaving the page inside the app saves unsaved room typing on the way out, and closing the browser tab asks first. A tab that crashes before its autosave still loses that typing.

## Document page

For organization members, a Proposal in artifact mode shows three tabs:

- **Main Document**: the live sections while the run is queued or generating, then the editor, both on the Proposal theme.
- **Internal Analysis**: the run describing the current text; its report, when it has one: the assessment, summary and what to resolve before sending, with the full report on demand, rendered as Markdown without HTML, links or images, its citations shown as source chips; each finding's state and evidence, Confirm, Answer and Clear for members with edit rights, answers no longer raised, and Re-run. The tab's badge counts Blocking findings still needing a decision.
- **Style**: organization members only. Two groups. Proposer brand: the document's own primary and accent colours, each showing where its value comes from (set for this document, Brand kit, the organization's website, neutral default), with "Use inherited value" and, where another source holds a different value, that value to pick; the logo, fonts and hero from the Brand kit, read-only. Recipient brand: the project's recipient brand, edited by organization members only, and the latest fetch of the recipient's website as a suggestion that applies one field at a time after a member confirms it. The style direction and colours shape the next generation's visuals; the theme follows at once. A Diagrams group holds the **Add diagrams automatically** switch, saved with the rest of the Style; a change applies from the next time diagrams are added.

Project guests see the Main Document only, on the same theme, without the name of the library prompt or a prompt choice: their runs use the bound prompt too.

Members and guests alike have a Download menu at the top of the page, the same menu as on the document's card.

## Proposal theme

A client-document Proposal, one whose owning organization has the `PROPOSAL_ARTIFACT` gate on, is shown on one theme for organization members and project guests alike, so the page a reader edits looks like the document the client receives. The same stylesheet carries a print layer: US Letter pages, running header and footer, the cover and landscape pages. The diff viewer, the other editors and every other document type keep the app's own styling.

- **One predicate.** Whether a document is a client-document Proposal is decided by `isProposalClientDocument` in `@repo/database` (gate on for the project's owning organization, and type Proposal); `projects.proposalArtifact.getThemeTokens` asks it, and the page wears the theme only when that procedure answers. `isProposalInternalReader` adds membership of that organization, the rule the tabs, Analysis and Style follow; their procedures ask it through the member-only loader `loadProposalArtifactDocument`, which keeps its refusals: FORBIDDEN with `ORGANIZATION_MEMBERSHIP_REQUIRED` for a guest, BAD_REQUEST for a document that is not a Proposal. The page itself reads the rollout flag and the document type only to wear the neutral theme while the server's answer is on its way.
- **Tokens.** The theme reads only brand tokens (`@repo/utils/proposal-artifact/theme-tokens`): the proposer's name, logo, primary and accent colours, paper, ink, fonts and hero image, and the recipient's name, logo and colours, each with the source it came from. Each value resolves field by field (see Brand sources): the document's Style, then the Brand kit, then the colours the organization's website declares, then the neutral style; the organization's name and its uploaded logo name the proposer, and the project's recipient brand names the recipient. Everything else is the neutral style: Poppins for display, Inter for body and JetBrains Mono for the mono role (eyebrows, labels, header cells), near-black ink on white paper, one slate accent. The live page loads Poppins and JetBrains Mono through `next/font` on the theme root (`proposal-fonts.ts`; the app already loads Inter), and the theme's fallback stacks name `var(--font-poppins)` and `var(--font-jetbrains-mono)` ahead of the literal families, since `next/font` registers hashed names. A document without brand values shows no logo and the neutral palette.
- **Contrast.** Every colour the theme paints as text, or behind text, is checked against the paper it sits on. A colour that fails is painted with the neutral fallback, and the token keeps its value and source, so a pale brand primary never makes headings unreadable.
- **Colour roles.** Headings, section opener bands, table header rows and the cover's background are ink. The brand primary paints:
  - the number squares of `process` and `timeline` figures (white or black numbers, whichever reads), and a highlighted step's outline, on the page, in the PDF and in the Word file, wherever a brand's primary holds 3:1 against the step's box; elsewhere, and in the neutral style, the square stays ink;
  - in print, the contents eyebrow and section numbers, in the heading colour (the brand primary when it reads as text on the paper, 4.5:1, else ink);
  - in print and Word, the cover's eyebrow and each section opener's "Section N" or appendix eyebrow, on the ink: the brand primary when it reads at 4.5:1 there, else the primary lightened a tenth at a time towards the ink's text colour until it does, over the veiled hero too. The neutral style has no brand primary, so its eyebrows stay in the light text.

  The primary also underlines links and fills every second stat tile. Small mono labels take the label colour:
  - the id column;
  - list markers and the numbers of bold-led steps;
  - card labels;
  - a bar chart's threshold.

  The label colour is the first brand accent that reads as text on the paper (4.5:1), else the heading colour. The neutral accents that stand in for a proposer without its own never become the label colour. Links keep the heading colour. The neutral style, whose primary is no brand's, keeps its number squares in the ink and only a highlighted step's square in its slate primary, without an outline, as it always drew them.
- **Paper in both colour modes.** The document is painted on the theme's own light paper in light and dark mode, as it will print. Editor controls inside the paper read the app's colour tokens remapped onto the paper.
- **Guests.** `projects.proposalArtifact.getThemeTokens` gives the page its tokens. It requires document read access, the document to belong to the project, project access and the client-document predicate, and no membership; anything else answers NOT_FOUND. It returns tokens with short-lived signed reads of the logos and the Brand kit hero, and never the Style's direction or the Brand kit's guidance. Logos and the hero are taken only from the keys their uploads write: `{organizationId}.png` for the organization, a promoted hero of the owning organization's Brand kit, the project's recipient brand prefix for the recipient. An uploaded Brand kit font travels in the tokens as its file id only; `projects.proposalArtifact.getThemeFont`, under the same checks, returns the bytes of the slot's current font for that id, and the same NOT_FOUND for anything else.

### Markdown the theme styles

For the owner of the library's Main prompt: the theme gives these Markdown forms their look, on the page and in print.

| Markdown | Shown as |
|---|---|
| The document's leading `#` title | In print and Word, the document's title: the cover, the contents eyebrow, the footer and the file's title (below) |
| The paragraph right after the document's `#` title | Lead paragraph |
| A `cover` fence before the first `##` | In print and Word, the cover's eyebrow, organization line, prepared-for and prepared-by lines and version (below); the body never prints it |
| A first `##` heading "Cover letter" (or "Anschreiben") | In print and Word, a letter on a page of its own between the cover and the contents, with no number and no contents entry (below) |
| `##` headings | Section headings; in print, a section opener band with a "Section N" eyebrow |
| A `##` heading starting with "Appendix" (or "Anhang") | In print, an opener with an "Appendix A" eyebrow and the letter on the contents page, using up no section number |
| `> ` blockquote, ideally opening with a bold sentence | Callout: left rule, tinted background |
| A table with a header row | Data table: dark header row, small uppercase labels, zebra rows |
| A table whose header cells are all empty | In print and Word, a table without a header row; on the page too while it is read rather than edited, for tables of up to eight columns (the editor keeps the empty row so it can be filled) |
| An ordered list whose every item opens with bold text | In print, steps numbered `01`, `02`… in the label colour |
| A `stat-tiles` fence | Stat tiles (below) |
| A `cards` fence | A grid of bordered cards (below) |
| A `columns` fence | Two columns side by side (below) |
| A Mermaid diagram or an image, with its caption | Figure with caption |

A stat-tiles block is a fenced block with the language `stat-tiles` and one to four lines of `label: value`, the value at most 24 characters and the label at most 80:

````markdown
```stat-tiles
Faster onboarding: 40%
Pilot sites: 3
Annual savings: $1.2M
```
````

A generated block may open with one `%% fabric-visual: <id>` line, the visual's id, which is not a tile. Nothing is evaluated: no HTML, YAML or JSON. A block that breaks the rule is shown as its source with the reason in the editor and as a plain code block elsewhere. In a client-document Proposal the single-user editor, the live sections and both exports draw the tiles; the shared (collaborative) editor, every other document, the other editors and the diff viewer show the fence as code, and the browser downloads of other documents print its lines as text. The shared editor waits because a collaborator's browser on an older release would not know the tiles and would drop the block from the shared document.

A `cards` fence holds one to eight cards separated by blank lines:
- A card's first line is its label (at most 60 characters), kept as written and set in mono capitals in the label colour. It may not be wholly bold.
- A next line that is wholly bold is its title (at most 120).
- The lines after that are its text (at most 600).

Cards sit two to a row, or three in one row when there are exactly three. A label that is only a number (`01`) gives numbered tiles.

````markdown
```cards
01 · Fewer repeat visits
**The part is on the van before the crew leaves**
Parts are reserved against each job the night before.

02 · Shorter mornings
Routes arrive ready, not rebuilt.
```
````

A `columns` fence holds two sides split by one `---` line:
- Each side holds `###` or `####` headings, `-`, `*` or `+` bullet lines and paragraphs.
- Numbered items, indented bullets, tables, quotes, images and fences are refused.
- A column heading is styled text, not a heading, so it never joins the contents.

````markdown
```columns
### In the pilot
- A route view for every crew lead
---
### Planned for later
- Contractor crews
```
````

Card titles and text, column headings, bullets and paragraphs carry bold, italic and code. They are read by the same Markdown parser the section identity uses, and a link keeps only its words. Either fence may open with a `%% fabric-visual: <id>` line. A refused block, the surfaces that draw them and the shared editor's wait are the same as for stat tiles. Neither fence is ever read as a diagram, whatever its first line says.

A `cover` fence sets the cover's details. It sits in the preamble, before the first `##`, with one `key: value` line per field:
- `eyebrow` (at most 80 characters): the line above the title, in place of "Proposal";
- `organization` (at most 120): a line under the recipient's logo;
- `for` and `by` (one to three lines each, at most 120): the prepared-for and prepared-by blocks, in place of the parties' names;
- `version` (at most 24): added to the date line as "Version N", or as written when it starts with "v".

Every key is optional, and a field the fence leaves out keeps its default, so a Main without the fence prints the cover it did before. Each line splits at its first colon and its value is plain text. The editor shows the fields as a summary card, on the stat tiles opt-in, and a refused block as its source with the reason. Print and Word read only the first `cover` fence of the preamble and print no other block the parser takes, wherever it stands, since the editor shows it as a card too; a refused block prints as code.

````markdown
```cover
eyebrow: Proposal · Operations leadership
for: Example Harbor Co
by: Example Studio
by: example.com
version: 1.0
```
````

A cover letter is Main's first `##` section when its heading, without a typed number, is "Cover letter" or "Anschreiben" in any case; a later section of that name is an ordinary section. On the page it reads as a section. Print and Word take it out of the body and set it on a page of its own after the cover and before the contents, under the proposer's logo with the heading as a small label, and its paragraphs take roles:
- a first paragraph of one line, at most 40 characters and with a digit in it, is the date, in the label colour, so a salutation such as "Dear Jordan Example," stays the letter's text;
- a paragraph starting "Re:" is the subject, in bold;
- the last paragraph that is wholly bold is the signer's name, and the paragraph after it is the line under it, in grey, an address included;
- every other block is the letter's text.

A Mermaid fence's opening `%%` lines may hold, in this order, the `%% fabric-visual: <id>` marker, a `%% caption: <text>` line and a `%% figure: <kind>` line. The figure line asks for a fixed figure template instead of the Mermaid layout, on the page and in print: `process` (numbered steps), `timeline` (dated steps), `layers`, `team`, `bars` or `gantt`. A fence without a caption line, such as a diagram added in chat, is captioned with the heading of the section it sits in, without its section number, as the visuals step captions a generated diagram that has no caption of its own: on the page, in the PDF, in the Word file and in the Markdown download alike. The heading is the last one before the diagram at any depth, a heading in a quote or a list and a setext heading included; an empty heading leaves none. A diagram above the first section, under the document's leading `#` title, has none and reads "Figure N." alone.

`process` and `timeline` lay their steps out in rows of at most four, as many rows as rows of four would need, with the steps shared out so no row holds more than one step over another, the longer rows first: five steps draw as three and two, seven as four and three, nine as three rows of three, never a full row followed by a lone box.

A flowchart fence with no figure line at all whose graph is one plain chain of seven to 24 steps draws as `process` too, in those balanced rows with the arrow back to the next row, on a client Proposal's page, in its PDF and in its Word file alike, under the same figure number and caption in all three. Plain means:
- every step has at most one arrow in and one out, and the arrows form one chain: solid, without labels, outside any subgraph;
- no `classDef`, `style` or `linkStyle` line, and no class but `surface`;
- every step is a rectangle, a rounded rectangle or a stadium, with a one-line label the step's box holds whole.

The engine draws a top-down chain about 85 px a step: six steps (481 px) still print at full size on a section's opening page after a short heading and a paragraph, while seven (565 px) would need more room than that at the label floor, so a chain of three to six keeps the Mermaid layout. Only the drawing changes: the fence keeps its Mermaid text. A figure line of any value anywhere in the fence, `none` included, keeps the fence as it asks, and so does a step whose label opens with a slash or a backslash, which Mermaid draws as a parallelogram or a trapezoid.

`bars` reads a horizontal `xychart-beta` source:
- quoted category labels in `x-axis [...]`;
- an optional `y-axis "unit" 0 --> max`;
- one `bar [...]` series;
- optionally a `line [...]` series whose values are all equal, which is the threshold.

The threshold is a ceiling. Bars at or below it are drawn in the primary and the others in a grey, and the dashed line and its value take the label colour. Values print as written. The template takes 2 to 12 bars with labels of at most 40 characters, values from 0, and a unit of at most 24 characters. A `bars` fence it cannot read prints as a plain chart: the page and the export both hand the chart to beautiful-mermaid without its leading `%%` lines, so it looks and is numbered alike in both.

`gantt` reads a Mermaid `gantt` source in week columns:
- an optional `title` and the `dateFormat YYYY-MM-DD` line;
- `section` lines, each task in the section above it;
- tasks written `Name :id, YYYY-MM-DD, Nd` (or `Nw`) or `Name :id, after id, Nd`;
- milestones written `Name :milestone, id, YYYY-MM-DD, 0d`.

Each task is a bar in the primary, and the first section's bars are muted when there are others. Milestones are diamonds in the label colour under the rows, with their names and dates. The template takes 1 to 20 tasks, at most 8 milestones and 8 sections, names of at most 60 characters, and a plan of at most 52 weeks. A `gantt` fence it cannot read (a `crit` or `done` tag, an end date, `excludes`, `axisFormat` and the like) draws with mermaid.js on the page and prints as a numbered placeholder, and so does a `gantt` fence without a `%% figure: gantt` line.

The visuals step writes `process` on a flow without lanes, `timeline` on a timeline, `layers` on architecture layers and `team` on a team. A fence the template cannot draw in any other kind, and a fence without a known kind, draws as Mermaid. A writer that rewrites Main and drops the figure line of an otherwise unchanged generated diagram gets the line back, as it gets back the marker; to keep such a diagram as Mermaid, change the line to `%% figure: none` rather than removing it. A fence that carries a figure line of any value is never given another.

## Brand sources

- **Precedence.** Proposer: the document's Style (a person's choice for this document), then the Brand kit (the organization's own settings), then the colours the organization's website declares, then the neutral style. The proposer's name is the organization's only. The logo is the organization logo; fonts and the hero image come from the Brand kit only, and the hero appears on the cover only. Recipient: the project's recipient brand, else nothing; a fetched suggestion never applies until a member confirms it. No recipient value fills a proposer field.
- **Who writes what.** People write the Style, the Brand kit (admins and owners) and the recipient brand (organization members with edit rights; never a project guest). A website fetch writes only its own row: the organization's site fetch and each project's recipient suggestion keep the attempt apart from the last result, so a running or failed re-fetch never takes applied colours away, and a fetch for an old website or a superseded attempt writes nothing.
- **The organization's website.** An admin sets it on the Brand kit. A fetch reads the home page's `theme-color` and manifest, `/llms.txt` for same-host links, and at most two brand-page candidates (`/brand`, one `llms.txt` link that names the brand), over HTTPS on that host only. Applied colours come only from declared sources: six-digit hex values in a brand page's visible text (a three-digit one is too weak to apply there), `theme-color`, the manifest's theme colour. No model reads any of it, and no fetched name or logo is used.
- **The recipient's website.** A member's save that changes it, opening the Style tab without a fetch for it, or "Fetch again" starts a fetch of the stored website (never one the request names). The logo, colours and site name it finds are stored as a suggestion; a member confirms each field, against the attempt they saw, through the recipient brand's version check.
- **Limits.** One bounded request of at most 15 seconds per fetch, rate limited per user and per organization; an attempt still running after two minutes reads as timed out. Each outbound attempt is audited with its host and a fixed code.
- **Uploads.** The hero (PNG, JPEG or WebP, 10 MiB) is re-encoded with its longest edge at most 2,400 px; font files (woff2 or ttf, 512 KiB) must decode: their container structure is checked first, which also bounds what WOFF2 decompression may allocate, then the server decodes the font's tables before a save stores it and again before the page is served it. Both upload to a pending key, are checked again when a save promotes them, and get a new key per upload. The live page loads an uploaded font through the FontFace API under an alias, and a Brand kit family wins over the neutral face there. Print sets every role in its committed face until Chromium's sandbox runs, so an organization with a brand display font prints Poppins for display; Word names the family.
- **Export record.** Each export records the hash of the brand tokens as its format printed them: uploaded font files never count, and neither do a PDF's font families, which print in the committed faces. The record is stamped with the time the export read the tokens, so of two overlapping exports the one that read them later keeps it. No "brand changed since last export" note is shown yet, and nothing reads these records yet. The hash carries a version prefix: `t3` replaced `t2` when print moved from Inter alone to three faces, so when that note is built it must read a record from an earlier version as a design change, not a brand change.

## Export

A client-document Proposal's PDF and Word file are made in the Temporal worker, not in the browser. Every other document type, and a Proposal whose gate is off, keeps the browser export it had.

- **Who and how.** The Download menu, on the document's card and at the top of its page, calls `projects.proposalArtifact.export` with the format and polls `projects.proposalArtifact.exportStatus`. Export needs document read access, the document to belong to the project and project access, and no organization membership: a project guest exports the same client document a member does. A caller without access gets NOT_FOUND. A readable document that is not a client-document Proposal gets BAD_REQUEST with `PROPOSAL_EXPORT_UNSUPPORTED`, and the menu then exports it in the browser as before. A client-document export that fails never falls back to the browser renderer. Exports are limited to 10 per user per 10 minutes, and each start records `project.proposal_artifact.export_started` with the format, the export id and whether the starter is a guest.
- **Workflow.** The export id is the id of a `proposalExportWorkflow` on its own `proposal-export` task queue, with two activity slots, so at most two exports run a browser in one worker at a time. The workflow's memo binds the export to its starter, organization, project and document, so no table is needed. One activity does all the work, because the document, the rendered diagrams, the print page and the file are too large for workflow history: it checks the starter's access again, reads Main and the guest-safe brand tokens, renders, uploads and returns only the file's key. The status read checks the id's shape, the workflow type, the memo's binding to the caller and project, then the gate and access again, and answers NOT_FOUND to anything else, including another reader of the same project. It signs a five-minute download link with an attachment disposition on every read; the link is never stored.
- **What the file holds.** Main only. Before rendering, `scrubProposalExport` (`@repo/utils/proposal-artifact/export-scrub`) removes citation markers (`[S3]`, `[cite]` and their written forms, never inside code) and Source Index sections. Markers also leave the lines of stat tiles, cards, columns and `cover` fences, which print as prose, and a `cover` line whose whole value was a marker goes with its key, while any other fence keeps them. Everything else, the document's own appendix and TBD lines included, exports as the page shows it. The Markdown download of a client-document Proposal goes through the same scrubber, and once its images are embedded it loses every storage key and signed URL (`withoutStoredObjects` in `@repo/utils/proposal-artifact/storage-references`, the rule the export uses): an image it could not fetch is dropped, and a link to a stored file keeps only its words. Its diagrams become images drawn by the diagram engine, not the figure templates. Each diagram the PDF and Word file number is followed by a "Figure N." line with the same number; one they leave out keeps only its caption, and one the browser cannot draw keeps its code. Brand comes from the guest-safe resolver, so style direction and Brand kit guidance never reach the worker.
- **PDF.** The print page is built from the scrubbed Markdown with the theme's print layer: a cover, a contents page, section openers, styled tables, callouts, stat tiles and figures, US Letter, with no running header and the footer ("proposer · title · date · Confidential" and "Page N of M") drawn by `@page` margin boxes. The cover counts as page 1 and carries no furniture. On a cover with a hero, the rules above the key figures keep 3:1 contrast over the hero under its veil. It shows only fields the data or Main holds: the title, both parties' names and logos and the date, with what Main's `cover` fence sets in their place (see [Markdown the theme styles](#markdown-the-theme-styles)); validity and confidentiality stay in Main's own text. A logo sits straight on the cover unless it would not read there. A mark on transparency is set on a rounded plate of the paper when 15% or more of its opaque pixels (weighted by their alpha) contrast at less than 3:1 with the cover's ink or, under a hero, with either end of the hero under its veil, so a dark wordmark beside a bright icon is plated while a light or coloured mark is not; a logo drawn on a box of its own (its sides opaque) takes none. The cover letter's page turns the rule round: a mark that would not read on the paper takes a plate of the ink. A cover letter prints on the next page, with the running footer, before the contents. The title is Main's leading `#` title when Main opens with one and has sections; it then leaves the body, so it never prints alone on a page, and the document's own name is used only for the file name. Every section opener starts a page, except after a short tail: when the section before it runs onto a page and fills no more than a quarter of it, the opener follows on that page rather than leave it almost empty. An empty block before each opener after the first, as tall as the rest of the page below such a tail, makes that choice in the layout itself, so both print passes make it alike; an opener that starts a landscape page has none. The contents page numbers sections `1`, `2`… in the brand primary as it reads on the paper over dashed rules, with page numbers in grey mono; an appendix takes its letter. Headless Chromium prints the page twice: the first print, which nobody sees, carries a text marker per section, laid out of flow so it moves nothing, whose page is read back with `extractPdfPageTexts` (`@repo/rag`), and the second writes the numbers into fixed-width slots on the contents page, so filling them cannot move anything. When the page lookup fails, the contents page lists the sections without numbers and the export says so.
- **Word.** The same Markdown tree is written with `docx`, laid out as print lays it out where Word can: a cover on the ink (a page-sized picture of it anchored behind the text, since a shaded table or paragraph cannot reach the paper's edges) with print's eyebrow, title, lead, logos (on a plate of the paper only where print plates them, by the same rule) and parties pinned to its foot in a table floated to the bottom margin, the hero as a picture above the title (Word cannot lay print's veil over it) and the key figures left in the body; every section opener an ink card (a one-cell shaded table holding the "Section N" or appendix eyebrow, the heading in a "Section Heading" style based on Heading 2 (so the contents lists it without copying the card's white type) and the subtitle, upright and muted as print sets it) on a new page, since print's short-tail exception is a measurement of the laid-out page Word has no rule for; no running header and print's footer; heading styles in the brand's display font and ink, the neutral style's print faces embedded (see Fonts), a numbering instance per list, tables with a repeated header row filled with the ink in light mono labels as print's (none when every header cell is empty), tables wider than six columns on their own landscape pages, images in their real type, diagrams as PNGs, stat tiles as a borderless table, cards as a table of bordered cells, two columns as a borderless two-cell table, and a contents field Word fills when the file is opened. Links are kept only for `http`, `https`, `mailto` and in-document anchors, never a link to a stored object; the file holds no other external relationship.
- **Images and logos.** Only uploaded images are carried, taken from their `data-s3-key` under the document's own media prefix, read from storage (never from a URL; streamed, and abandoned as soon as one passes 10 MB), checked by their leading bytes (PNG, JPEG, GIF, WebP; never SVG), and re-encoded to PNG or JPEG with their metadata dropped. Each is re-encoded at most 1.5 MB, because print inlines it and Chromium draws no inlined image past 2 MiB: one over that at its longest edge is made again at 1800, 1200 or 900 px until it fits, and one that never fits is left out with a warning. Logos are read the same way from the keys their uploads write. Images linked from elsewhere are left out. Raw HTML that names a stored object (a refused or broken image tag, a file link, a signed storage URL) is never printed as text, and neither is an author's HTML comment; an image tag whose quoting the Markdown parser could not read is treated as the tag it is. A storage URL or media path written into Main's text, code, diagrams, an image's alt text and caption, the title or a party's name is dropped, and a link to a stored object keeps only its words.
- **Diagrams.** Mermaid fences render in the worker with beautiful-mermaid, the engine the page uses, in the brand's colours. Flowcharts and state diagrams are drawn with an 8 px margin rather than the engine's 40 px default, so a figure takes only the room its drawing needs and a short one is not pushed to a new page. A flowchart node label is broken into lines when Inter would draw it closer than 4 px to the sides of the box beautiful-mermaid sizes from its own width estimate, judged from Inter's glyph widths for Latin, Cyrillic and Greek (any other capital counted as a wide one) rather than a character count, on the page, in print and in the browser download alike; print and a Proposal's page never keep a layout whose labels spill out of their boxes over one whose labels fit, even when that one prints smaller. A figure's drawing prints no taller than the page body less an inch for its caption, shrunk with its shape kept, so a tall diagram never runs off the page. The first figure on a section opener's page, right under the opener (past its subtitle and any block that prints nothing, such as a comment or a dropped image) or after its paragraphs and plain lists, is offered less: two inches less again, and less by every line the opener's text and those blocks are estimated to take. It is shrunk to that height only while its labels still print at the 9 pt floor there: a flowchart's 13 px node labels down to 9/9.75 of its drawn height, a figure template's 12 px text, at the floor at full size, not at all. Otherwise it keeps the page body's height and, when it does not fit beside the opener as drawn, moves whole to the next page. Only a figure whose labels fall below the floor even at the page body's height prints below it, which the export reports. `%%{init}%%` directives, front matter and `click` lines are removed first, and every SVG passes an allowlist that keeps no script, foreign content, event attribute or external reference, and exactly one cleaned style element. Kinds beautiful-mermaid does not draw (Mermaid `timeline` syntax, a gantt without a `%% figure: gantt` line or one its template cannot read, front matter) print as a captioned placeholder; a diagram never fails an export. Layout runs in a worker thread of its own, 10 seconds at most per diagram, and stops 50 seconds before the export's deadline, so a document of slow diagrams prints placeholders for the rest rather than timing out. A fence the engine refuses is left out unnumbered, as the page does not number it either; one the export could not lay out in time, or that passes a size limit, is drawn on the page, so it prints as a numbered placeholder and the figure numbers after it stay the page's.
- **Fonts.** The print page embeds three faces from committed files under the SIL Open Font License (`packages/temporal/src/lib/proposal-export/fonts/`, each with its licence and a `THIRD_PARTY_NOTICES.md` entry), as base64 `@font-face` rules with the MIME type and format of each file: Poppins 4.004 Bold (TTF) for display, Inter 4.1 at 400, 500, 600, 700 and 800 (woff2) for body and diagram node labels, which the engine draws at 500 as the page does, and JetBrains Mono 2.305 at 400 and 500 (woff2) for the mono role. The running footer stays on a literal Inter stack. Print sets body text at 10.5 pt with 1.6 leading, h3 in Poppins at 12.5 pt, eyebrows in mono at 7.5 pt with 0.16em tracking, and captions in mono at 7.75 pt. The Word file sets each role the brand left neutral in its print face and embeds that face from committed TrueType files beside the woff2 ones: Inter Regular, with Inter Bold in the family's bold slot so bold text is the real bold face; Poppins Bold, in the bold slot of "Poppins" and, unless a brand chose Poppins for another role, its regular slot too, since display text is always bold; JetBrains Mono Regular, for mono text print sets at 400; and JetBrains Mono Medium under its own family name, "JetBrains Mono Medium", as its file names it, for the eyebrows, labels and header cells print sets at 500, so Word draws the real Medium face rather than a thickened Regular (a brand's mono font is set bold there instead). The embedded faces add about 0.7 MB to a file, and the file asks Word to embed its fonts again when it is saved, so a copy edited on a machine without the faces keeps them. A role the brand chose a font for names that font and embeds nothing, even when it names one of the print faces; Word substitutes it where it is not installed.
- **Budgets.** Main up to one million characters, 40 diagrams, 30 images (10 MB each, 40 MB with the logos), 150 pages and 150 seconds per export. An image placed many times counts again at every placement, up to about 80 MB of image data on the print page and 60 MB in the Word file (cover images and diagrams included, the cover first); placements past that are left out with a warning. A budget that is exceeded fails the export for good; an image over its own limit is left out with a warning, and a diagram over its own limit prints as a placeholder with one. The menu names what was left out after a download.
- **Files.** Exports are stored under `proposal-exports/{projectId}/` in the project contexts bucket. A daily schedule (`proposal-export-cleanup`, 06:15 UTC) deletes those older than 24 hours, in sweeps of up to 5,000 that repeat (up to 20 a day) while one stops at that cap, the status read stops signing links for them, and deleting a project deletes its exports.

### Print acceptance

A change to the PDF export is accepted on rendered Linux pages, not on string tests alone. `packages/temporal/__tests__/proposal-export-print.e2e.test.ts` prints six synthetic Proposals through the export's own path (Markdown preparation, diagram rendering, the two-pass print) with a real Chromium:
- one with every element the print design draws (a cover fence, lead and key figures, a cover letter, openers with subtitles, an id table, a callout, bold-led steps, the process, timeline, layers, team, bars and gantt figure templates, a bars fence the template refuses, a Mermaid flowchart, a broken fence, card grids, two columns and an appendix with a headerless table);
- one shaped like a generated Main, opening with its own `#` title;
- one shaped like a Main written before figure lines, with plain Mermaid fences: a top-down chain of twelve steps after its section's first paragraph, and a sideways chain of labels dense in dashes, m, w and hyphens;
- one whose opener has a heading on three lines and the longest subtitle, with a chain of twenty steps right under it;
- one with a branched top-down flowchart right under its opener, taller than the room there at the label floor;
- one with a shorter branched flowchart under an opener whose heading takes three lines, a little taller than the room there, where its labels still reach the floor.

It checks:

- [ ] the cover is a full US Letter page (8.5 × 11 in), and with the longest lead the cover takes and a three-line title its body ends above the parties block;
- [ ] page 1 prints no page number;
- [ ] the contents page lists each section once, without the number typed in its heading;
- [ ] every figure template is drawn at the 662 px print column, its text at 12 px or larger and inside the box it labels;
- [ ] figure text is never cut inside a word: every line of the long-named layers and the long-phrased timeline ends at a space, and a layer description is drawn whole or not at all;
- [ ] figures are numbered "Figure 1." onwards in document order, the gantt drawn by its template with its milestone, the refused bars fence drawn as a chart in its place in the order, the broken fence left out with none of its text printed, and no diagram warns that its labels print below the floor;
- [ ] the cover prints the cover fence's fields in place of the defaults and the body never prints the fence; the cover letter prints on page 2 with the running footer, and every contents entry points at its opener's page past it;
- [ ] card grids sit two to a row (three for three cards) with tops aligned and body text at 9 pt or larger, each card kept whole; two columns sit side by side; a table with an empty header row prints without it;
- [ ] the contents page numbers sections without leading zeros and an appendix by its letter, and the appendix opener reads "Appendix A" without using up a section number;
- [ ] a generated Main's leading `#` title is the cover's title and no page holds it alone;
- [ ] in both the full and the generated fixture, no page is left almost empty before a page a section opener starts (a section's short tail shares its page with the next opener), and every page an opener starts has its text at the same height; the full fixture's short flowchart prints on its opener's page, under the layers figure;
- [ ] in the older fixture, the twelve-step chain prints as a grid of numbered steps, its text at 12 px or more, whole with its caption on its opener's page after the paragraph, and no diagram warns;
- [ ] the twenty-step chain under the long opener prints as a grid of numbered steps at 12 px or more, with its caption, on the opener's page;
- [ ] the branched flowchart under its opener is not shrunk below the floor: it prints at full size, whole with its caption, on the next page, without a warning;
- [ ] the shorter branched flowchart is shrunk to the room under its opener, its labels at 9 pt or more, and prints on the opener's page with its caption and the paragraph after it;
- [ ] in the older fixture, no label of the dense sideways chain crosses its box, the labels too wide for their boxes broken into lines and the others left on one line;
- [ ] the PDF embeds Poppins Bold, Inter and JetBrains Mono;
- [ ] glyph advances are not rounded to whole pixels (fewer than 30 % on a whole pixel), the sign that font hinting is off.

CI runs the file in the `browser-security` job of `.github/workflows/unit-tests.yml`, on Linux, the platform the worker prints on. The job sets `PROPOSAL_PRINT_ARTIFACT_DIR`, the test writes `full.pdf`, `generated.pdf`, `older.pdf`, `long-opener.pdf`, `branched-opener.pdf`, `shrunk-opener.pdf` and `frame.pdf` there, and the job uploads them as the `proposal-print-pdfs` artifact, kept for five days.

The human review uses that artifact:

1. Push the branch and start the **Unit Tests** workflow on it with *Run workflow* (a dispatch run includes the `browser-security` job); no PR is needed.
2. Download `proposal-print-pdfs` from the run and render its pages to PNG with any PDF rasterizer.
3. Compare them page by page with the reference design, element by element, and record what differs before the PR is opened.

Print on Linux only for this review. macOS Chromium does not apply Linux font hinting, so a local print can look right while the worker's does not; locally the test can run against an already-downloaded Chromium through `PROPOSAL_PRINT_CHROMIUM_PATH`, which checks layout but not hinting.

## Decisions and limits

- **Retired Proposal actions.** With the gate on, the Prompt Library, binding dialogs, nominations, governance view, project prompt defaults and the setup wizard offer only Client proposal (Main) for a Proposal. The Project Document Generator and Document Generator Proposal slots are hidden, saved overrides there are listed as no longer used, and new organization or project defaults at them are refused (`PROPOSAL_ACTION_SUPERSEDED`); nothing is deleted, and organizations with the gate off see the slots as before.
- **Agents follow the status, people the ten-minute rule.** The editor lets people save over a Proposal whose run has written nothing for ten minutes; agent and API writes stay refused until the watchdog fails such a run.
- **Forms come from the Main prompt, not the visuals step.** The seeded Main prompt asks for stat tiles, cards, columns, bar charts, steps, id tables, the cover fence and a cover letter where the inputs give their content; the visuals step writes none of them. An organization's own Main prompt writes them once its owner adds them (see [Rolling it out](#rolling-it-out)).
- **Diagrams change only through their own menu.** Chat and an applied recommendation leave every existing diagram as it is, the automatic ones included; Edit with instructions on the diagram is the way to change one.
- **MCP and v1 updates are checked too.** `fabric_update_document` and the v1 document update, including calls from agents that hold Fabric's portal tools, refuse a body that changes or removes an existing diagram, renamed section or not, or repeats a settled answer for the caller; prose edits go through as before, and a diagram may move between sections.
- **A guest's chat reply is checked before it is shown.** For a project guest on a client Proposal, a reply or an action the browser runs (a clarifying question, a drawing, Regenerate, a repository or meeting lookup) that repeats the bound prompt is replaced with a refusal, the arguments and results of tools that run on the server are not sent to the browser, the model's reasoning is not shown, and an error from the model provider or a tool reaches the guest as a general message. A guest's reply, the actions their browser runs and the change they are asked to review are checked for runs of eight words of the prompt rather than twelve, and characters that draw nothing (a zero-width space, a soft hyphen) are ignored in every echo check; a paraphrase or a shorter fragment is not caught. The prompt, settled decisions and echo texts never appear in the run events or a reconnect replay, and a chat thread replays only for the person who started it.
- **An attached file reaches the model once.** On a client Proposal, a file attached in the chat goes to the model in full only in the turn it was attached; later turns name it, and the assistant asks for it again when it needs the content. Chat uploads are not in the project's search index, so the content is not otherwise available in later turns.
- **Provider error text stays out of server logs.** A failed model or tool call on a Proposal run, a member's or a guest's, is logged by error class, code, HTTP status and ids; the error's text, the error object and previews of a reply that repeats it are not. On these runs the logs also leave out reply previews and tool-call arguments; tool-call names and counts are kept. The body of a `/runs/stream` request is not logged for any run, only its keys and flags. A member still sees the provider's error in the chat.
- **Assistant threads follow project access.** The live updates of a document's assistant thread and the thread the sidebar restores on load require access to the document's project, as reading the thread does; organization membership alone is not enough.
- **Refused saves keep their body out of the audit log.** A failed document save is still captured for the audit log, with the body replaced by its length and hash.
- **An applied recommendation is accepted or rejected whole.** Its revision token covers the checked candidate, so accepting or rejecting single changes in its review makes the save refuse it (`REVISION_TOKEN_INVALID`); Accept all or Reject all is the way through.
- **A chat edit may touch more sections than asked.** The model chooses which sections to patch; the review shows each one, and the server only refuses changes outside the sections it reported.
- **Free-form instructions stay.** Instructions typed when generating are appended to the Main prompt as before; the Main prompt is what keeps the result client-facing.
- **No model check before guests read Main.** The separation is structural: Analysis runs only after Main is saved, and its output lives only in organization-only tables. The Main generation never sees a finding's detail or evidence; it sees members' answers and the titles they answer, as settled decisions, guarded by the echo check above.
- **Raised again means Needs Review**, even when the section's text has not changed, and such an answer stops feeding generations until a member confirms it again. A re-run can therefore move answers to Needs Review when the model repeats a finding.
- **Old runs cannot be answered.** Findings recorded before Fizzy #2946 have no stable key; the page offers a re-run instead.
- **Analysis sees visuals as Mermaid source**, not as rendered images, so it cannot judge their appearance.
- **A report needs a prompt that asks for one.** The seeded analysis prompt asks for findings only, so organizations on it get no report. When a report is asked for, findings arrive with it, a minute or more later than they would alone, and the analysis input is sent to the model twice. A report keeps its text after a cited source is deleted, as Main does; only its chip turns to "Source removed", and deleting the document, project or organization removes it with its run.
- **Operational choices.** Analysis runs on the `project-documents` task queue. Style changes are not audit events: they are presentation settings, not security-relevant mutations.
- **Exports print without Chromium's sandbox, for now.** The sandbox does not start under the worker image's default seccomp profile. Until it runs, or exports move to a render container without secrets, Chromium is launched with an environment of only a search path and a scratch directory (no database, storage or model credentials), runs no page JavaScript, loads nothing from the network and embeds only the committed faces. So the PDF is set in Poppins, Inter and JetBrains Mono even where the page shows an uploaded brand font, and Mermaid `timeline` diagrams and gantts the gantt template does not draw, which would need the browser engine, print as placeholders; a `%% figure: timeline` or `%% figure: gantt` fence its template reads prints as a figure.
- **The Word contents page fills itself when the file is opened**, so Word asks to update fields; other word processors may show it empty until updated.

## Rolling it out

1. Create the client-only Main prompt, the revision prompt and the analysis prompt in the organization's prompt library and bind them to the **Client proposal (Main)**, **Client proposal (revision)** and **Proposal internal analysis** actions. The revision prompt is what chat and applied recommendations follow, so it must carry the organization's audience rules. The seed creates synthetic defaults for fresh environments only; existing environments need the binding by hand. The Main prompt should structure its sections with H2 or H3 headings, which is what live sections cut on.
2. Enable `PROPOSAL_ARTIFACT` for the organization on its per-organization feature flag page, not the global panel.
3. Keep `GLOSSY_EDITION` on wherever existing Glossy editions must stay viewable.

The release in which generation writes the forms (see [Markdown the theme styles](#markdown-the-theme-styles)) changes the seeded **Client proposal (Main)** text. The seed only inserts, so a data migration (`20261030120000_proposal_client_main_forms`) carries the new text to existing environments. It rewrites the SYSTEM default version of `proposal_client_main` only while that version still holds the text the seed wrote and the prompt has no later version, so an edited SYSTEM prompt is left alone. An organization's own Main prompt, bound in its library, outranks the SYSTEM one and is never changed: its owner adds the forms by hand, as a new version that takes the seeded text's `# FORMS` section and its `# STRUCTURE` lines on the title, the preamble, subtitles and appendices, and binds that version. Until then the organization's Proposals are generated without the forms. The migration runs before the new web and worker are out, so a Main generated in that window may hold a `cover` fence that the older release shows as code. It may also hold a `## Cover letter` section, to which the older worker's visuals step may add a diagram and whose print numbers it as an ordinary section.

The same release adds a `# COVER AND COVER LETTER` section to the seeded **Client proposal (revision)** text. Chat and applied recommendations keep the cover block exactly as it is: their edits are anchored on headings and cannot reach the preamble in place, so a request to change the cover details is sent to the editor. They write a cover letter in the Main prompt's form, as the first H2. A second data migration (`20261030130000_proposal_client_revision_forms`) carries this text the same way: it rewrites the SYSTEM default version of `proposal_client_revision` only while that version still holds the text the seed wrote and the prompt has no later version. An organization's own revision prompt is never changed; its owner adds the section by hand as a new version.

The scoped-revisions release adds the Resolved response kind in its own migration and changes the document assistant; deploy the migration, then the agents, then the web. A newer web with an older agent runs chat on the built-in template until the agent is out.

The review release adds a migration and changes the analysis activity, so it deploys in the usual order: migration, then the Temporal worker, then the web. A re-run started by a newer web on an older worker would analyse without its sources and record findings that cannot be answered.

The report release adds two nullable columns to `ProjectDocumentAnalysis` and deploys in the same order. A worker that runs before the migration still completes runs without a report and loses only reports; the previous web and worker ignore the columns.

The release that adds card grids and two columns leaves both fences as code in editors without them. A browser still on the previous release, a stale tab during a deploy or every client after a rollback, does not know that, and its Mermaid first-line check can save a `cards` or `columns` fence whose first line starts with a diagram keyword ("timeline", "graph", "block"…) as `mermaid`. Before rolling that release back, look for Mains holding such fences.

The export release deploys the worker before the web too: the web starts exports on the `proposal-export` queue, which only the new worker polls, so an export started first would wait there until the menu stops waiting. The worker image already carries Chromium for frame export.

Visuals and Analysis resolve their model like generation does. An organization without a configured AI provider gets Proposals without visuals and an analysis that reports the provider as not configured.
