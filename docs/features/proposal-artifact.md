# Proposal Artifact

How one generation request produces a client-ready Proposal, its visuals and a separate Internal Analysis, and how to roll the feature out.

- **Audience**: Developers extending Proposal generation; operators enabling the feature for an organization
- **Owner**: Documents

## What it is

With the `PROPOSAL_ARTIFACT` rollout gate on for an organization, generating or regenerating a Proposal runs one coordinated job instead of the Draft followed by a Glossy edition:

1. the **Main Document** is written from a client-only prompt and its finished sections appear on the page while the agent is still writing;
2. visuals are added to the Main Document in the same job;
3. after the Main Document is saved, an **Internal Analysis** reviews it against the same source context and records findings that only members of the organization can read.

The Main Document is the client artifact: it never carries review notes, citations, a source index or readiness status, and every download exports it alone. Its PDF and Word files are printed by the server from the same theme the page wears (see [Export](#export)). Business Case and every other document type keep their current flow, and a Glossy edition that already exists for a Proposal stays reachable while `GLOSSY_EDITION` is on. The terms are defined in [CONCEPTS.md](../../CONCEPTS.md#proposal-artifact).

## Generation

The decision is made once per run, inside `documentGenerationChildWorkflow`, behind `patched("proposal-artifact-v1")`, so every path that generates a Proposal (editor, documents list, chat, create dialog, setup wizard, uploads) takes the same branch. The plan activity reads the gate for the project's owning organization first and returns nothing when it is off, so organizations without the gate never depend on the new prompt actions.

- **Prompt.** Main is rendered from the prompt bound to the `proposal_client_main` action, at the bound version, on every retry. The editor's prompt choice and `DEFAULT_PROMPTS` are not used. When nothing is bound, generation is refused with a message naming the action: early at dispatch and in the setup wizard, and authoritatively in the workflow before the agent is called. A personal binding on this action is refused, so no individual prompt can steer the client document.
- **Live sections.** The activity reads the agent's cumulative previews, keeps the text up to the last completed H2 or H3 section, and writes it to `ProjectDocument.liveContent` at most every 1.5 seconds, followed by a `document_change` nudge carrying ids only. `content` is untouched until the final save. Every write is owned by the run's `liveRunId`, so a superseded run can write neither previews nor the final document.
- **Long streams.** A client-document Proposal's agent stream gets a first-chunk allowance (300 s) and a wall cap taken from the activity attempt's deadline less a reserve; the idle limit only logs unless `AGENT_STREAM_IDLE_TIMEOUT_MS` is set. When the stream gives up, the live preview is stopped, not cleared (progress milestone "preview stopped"), and a bounded, cancellable plain-generation fallback writes the document with a sign of life. Other document types keep the earlier limits.
- **One run at a time.** A regeneration asked for while a Proposal run is live joins it instead of starting another: dispatch takes a per-document advisory lock, asks Temporal whether the recorded workflow is still running (running, gone or unknown), and answers "already in progress" or "could not confirm the running generation". Its Temporal start and the follow-up check are bounded so the locked section ends well inside its transaction. The queue mark retries once when an unrelated edit (a title change) declined it, unless a newer attempt owns the row.
- **Visuals.** Before the save, timeline, flow and org-chart visuals become Mermaid fences and comparisons become tables, inserted after the first block of their section. Colours come from the shared brand resolver: the document's Style, then the organization's Brand kit, then the colours the organization's website declares, then the neutral style; a recipient colour never stands in for the proposer's. Sections that already hold a Mermaid diagram are skipped. The step is bounded and fails open: the Main Document is saved without visuals rather than lost. The diagrams come from this step, not from the bound prompt: a model picks the sections that suit one and code builds the fence, so no prompt text asks for Mermaid, and a section whose own text (the prompt's output or a person's edit) already holds a diagram is left alone. The prompt library's binding dialog says so for Client proposal (Main), and the diagram's ⋮ menu labels a generated one "Added automatically". The Style tab's **Add diagrams automatically** switch (on without a saved Style) turns the step off for one document: it then adds none and makes no model call, and diagrams already in the document stay.
- **Analysis.** After save, version and embed, a non-fatal block records an analysis run and starts `proposalAnalysisWorkflow` with an abandon close policy. The run stores the saved Main Document, its hash and a bounded copy of the generation's source context. Analysis is not run for generations a project guest started, and an unbound `proposal_internal_analysis` action records a failed run without affecting Main.

## Internal Analysis

Findings carry a severity (Blocking, Important, Informational) and a type (Scope, Commercial, Assumption, Risk, Gap, Source Validation, Architecture, Branding, Opportunity). The library prompt owns the instructions; the code owns the output contract.

Analysis rows, findings and reports live in `ProjectDocumentAnalysis` and `ProjectDocumentFinding`, organization-only tables (`ORG_ONLY_TABLES`, `org_only` RLS). They are never part of `ProjectDocument.content`, a version, an embedding, an MCP or v1 read, or an export. `projects.proposalArtifact.getAnalysis` returns, to organization members only, the newest complete run whose analysed text matches the current text, else the newest complete run labelled stale, together with the status of any newer run; a newer run that is pending, running or failed never hides a complete one. A project guest receives FORBIDDEN with `ORGANIZATION_MEMBERSHIP_REQUIRED`. Staleness compares a prose hash (see Review), so an editor save or a recolour that leaves the text alone does not mark a run stale. A run is timed out when it has made no progress for 20 minutes.

## Review

Fizzy #2946 makes the analysis something members act on.

- **Sections and prose hashes.** `@repo/utils/proposal-artifact/section-hash` parses the Main Document once with remark and splits it at every heading. A section's key is its heading path (numbering and the document title left out) plus an occurrence index; its prose hash covers its own text after parsing, with separators for blocks, list items and table cells, and without Mermaid fences, visual markers, visual slots or link and image addresses. Keys and hashes carry a `p1:` version prefix, and the same golden fixture is asserted in Node, jsdom and the worker, plus a round trip through the editor's load and save.
- **Findings.** The analysis lists the sections by number and asks for the section index, a short subject and the source numbers each finding relies on. A finding's stable key is its type, section key and normalised subject, never its wording; findings that share a key in one run fold into the first, which keeps the most severe of their severities and the others' titles, details and recommendations.
- **Evidence.** On the Proposal branch, retrieval also returns a manifest of what each source string was (project context, company source, project summary, other). The run keeps the entries for the sources the analysis actually read, numbered as the `### Source N` blocks the model saw. Evidence is read from each source's current row, never from a copy kept with the run, so text removed from a source does not resurface: project contexts and company sources show their current title and the opening of their current text, LINK and meeting transcript contexts also link to their pages, and the project summary and other sources show their label only. A source that no longer exists in the project or organization shows as removed, with nothing else; a run recorded without a manifest shows no evidence rather than calling its sources removed. No source address is ever returned.
- **States.** A finding is Unaddressed, Confirmed, Responded or Needs Review. Responses (`ProjectDocumentFindingResponse`, organization-only like the analysis tables) belong to the document and the stable key, not to a run. Needs Review is derived at read time, never stored: the section's prose hash differs from the one the answer was given against ("section changed"), the section is gone ("section not found"), or a later run raised the key again ("raised again"). Answers whose key the shown run does not raise are listed as no longer raised, with their own state. `finding-state.ts` in `@repo/utils` is the one derivation the page and the settled feed both use.
- **Answering.** `respondToFinding`, `clearFindingResponse` and `rerunAnalysis` need `DOCUMENT_UPDATE` and organization membership; commenters and viewers read only, and guests are refused. Writes use a compare-and-swap on the answer's id and version (so an answer cleared and given again never matches a stale tab's copy) and return a stale outcome, not an error, when another member saved first or the run changed. Audit actions `project.document_analysis.responded`, `cleared` and `rerun_started` carry keys and kinds, never answer text, and the error-capture middleware skips `respondToFinding` so a refused call cannot copy an answer into the audit log either.
- **Re-run.** A re-run analyses the current text against the stored sources of the generation that produced it, even when that generation's own analysis failed (or else the newest generation run with sources), through the existing `proposalAnalysisWorkflow` under a per-run workflow id. It is refused while the document is generating or another run is in progress; a run with no update for 20 minutes counts as finished. Re-runs are limited per organization. Regenerating is how new sources are picked up.
- **Report.** When the bound analysis prompt asks for an overall review report, each run keeps it beside its findings, in two columns of the run: the structured fields (overall assessment as the model wrote it, summary, Must/Should/Could scope items, what to resolve before sending and what during discovery, the sources it cites) and the full report text. After the findings call, a second, plain-text call in the same activity asks for it, with the same instructions and sources plus the findings already recorded, so it describes the same review; its Output block defines the format only (Markdown, a length bound, `[S<N>]` citations naming the outer source blocks, a trailing `json fabric-report` block with the fields, or `NONE`). The call is skipped for the seeded findings-only analysis prompt (matched by a hash of its text, so a new library version needs no deploy). The findings call itself is unchanged, and any failure of the report (a provider refusal, the call's own deadline inside the activity window, an empty or unreadable answer, an error writing it) completes the run with its findings and no report. The run completes once, after both calls. Before anything parses the text, a linear check (`reportTextNeedsPlainText` in `@repo/utils/proposal-artifact/report-text`) flags text that would make Markdown parsing slow or crash: deep nesting, large or numerous tables, too many lines or block lines in the whole report, a quote or list item continued on hundreds of unprefixed lines, very long lines, dense emphasis or escapes in one paragraph, long punctuation runs inside a bare link, unclosed inline HTML openers and unbalanced brackets. Its limits were set by timing the parser on hostile shapes, so a parser upgrade should re-run those timing tests. Such a report is shown as plain text. The flag is also set when the worker's own Markdown scan fails, and the check runs again on every read, so a stricter check also covers reports stored before it. Citations are found once, when the run completes, and resolved at read through the same evidence rules as findings, including "source removed". The report is read only by `getAnalysis`, for the run it shows, and never reaches a guest, Main, the settled decisions, a prompt, an export, MCP, an embedding, an SSE payload, workflow history or a log. Runs recorded before it, and runs under a prompt that asks for none, have no report.
- **Settled decisions.** `buildSettledDecisionsBlock` (`@repo/temporal/proposal-artifact-settled-decisions`) turns the document's confirmed and answered findings into a fenced block for the Main generation and the analysis. It keeps only answers that are not in Needs Review and whose author is still an organization member with edit rights, neutralises and caps each one, and returns nothing for a guest, a system start, a missing organization or any error in its checks. It is joined to the prompt, never assigned over supplied context. Before writing a live preview and before saving a Main Document that carried the block, the generation refuses (`RESPONSE_ECHOED`, not retried) when the text repeats a run of 12 or more words from an answer or a finding title that the sources, the project information in the prompt and the previous Main do not also contain. The refusal message every reader sees names no answer; the worker log records the stable keys of the answers involved, so the answer to reword or clear can be found. Shorter answers are not checked: a short factual answer is expected to shape Main.

## Editing while a run is live

Fizzy #2946 production feedback: a regenerated Proposal could flash back to, or be saved over with, its previous version in the shared editor.

- **Outside writes wait for the run.** While a Proposal is queued or generating, its body and status cannot be changed by an agent (`fabric_update_document`), the v1 API, a status change, "Update using context", a version restore, a rejected regeneration or its fallback save, or an accepted or scheduled refresh. `updateDocument` refuses such a write at its read and adds the live statuses to the guarded `UPDATE`'s condition by default, so a run queued after the read is refused too (`DOCUMENT_GENERATION_IN_PROGRESS`); only the editor's plain content save opts out. This is decided by the document type (`isRunGuardedDocumentType`), not by the rollout gate, because a run outlives a change of the gate. Ordinary editor saves are not refused by status; they name their base, and the editor's own rule stops saving while a run still writes.
- **Generation statuses belong to runs.** QUEUED and GENERATING cannot be sent on any document create or update through oRPC, v1 or MCP (`DOCUMENT_STATUS_GENERATION_OWNED`); they are set by dispatch with the workflow id and start time the stale-run watchdog needs.
- **Every save names its base.** Reads return `version` and `contentHash` (`contentIdentity`, SHA-256 of the body). A save sends both as its base, and `updateDocument` puts version and body in its `WHERE`, so a run's body saved at the same version is not overwritten. With `DOCUMENT_ROOM_CONVERGENCE` on (default), a client-document Proposal save without a base is refused (`DOCUMENT_SAVE_BASE_REQUIRED`). Agent writes may omit the base; they are then guarded by the body the same call read. The MCP update result carries the next base.
- **The shared room converges.** The room (Yjs in a Durable Object) carries a stamp of the saved body it descends from. A run's start, its final save and its version step each send a `document_change` nudge under an id no member has (so no tab takes it for the echo of its own save): a Proposal's page and a collaborative document's page read the document then (the latter within a second) instead of on their next poll. At the end of a run one editor puts the run's body into the room with its stamp at once: the tab that started the run (through its review), otherwise one tab that followed the run, so it does not matter whether the run was started from an open tab, by a colleague, the API or an agent. A review speaks for its own run only: each tab names the run its role is for, a follower does not wait on a review of another run, and a newer run started anywhere closes the review so its tab follows the newer run. A tab that finds the room behind the saved document claims the update in the room's metadata, one edit-capable peer applies it, and replaced unsaved typing is offered back once with a copy action. That fallback takes a second look one poll later, during which saves wait. When what the tab learned is the end of a run the room has not taken in, its editor (the raw markdown view too) stops taking input at once and, after 750 ms, shows the run's saved body read-only until the room holds it, so nobody types into the previous body. A tab that has not seen the room in step yet, opened or back from a dropped connection with the room already behind, cannot tell a run's end from a rewind and only holds the room's body read-only until the second look. A tab with typing of its own keeps the room's body on screen, and so does any other difference between room and saved document, such as a write outside a run or the rewind of a rejected regeneration. Only an empty room is seeded, and the editor binds the `"default"` fragment. Run state survives the editor's remount on a lost connection; after 45 s without the room the page turns read-only. A run counts as still writing for ten minutes after its last write. An assistant proposal waiting for an answer is in the room too, so the tab reviewing it says so in its awareness state: from the assistant's first frame in its editor through the chat's confirm card (a run that ends without a card, stopped or failed, stops two seconds later, unless the chat's last turn still holds an unanswered `confirm_changes` call, whose card is then waited for up to 20 seconds after the run ended (a run that failed after naming the call never runs it), while the tab's own saves wait too; in a shared room its tab then puts the body from before the run back, says so, and resets the agent's document to it, and a second run started meanwhile is taken back to the body from before the first; alone, the editor keeps the partial text as before), or for an update using context from the moment it starts drafting. Every other tab that may edit holds still until the proposal is answered or that tab goes: its editor and raw view take no input, its saves and autosave wait, the view switch, Update using context, Regenerate (button, menu and chat; the chat's call is answered as not started, and the chat says why rather than that the regeneration completed) and version restore wait, its own assistant puts nothing into the editor (a run that began or wrote meanwhile is answered as not applied, and an Accept of a proposal it already holds waits), the sync pill says why, and no tab brings the room to a newer saved body underneath the proposal. The review is said in the room before any of its body is written there, and a save from another tab is judged by the room as it stands when the save would go, so one due in the moment before that tab shows the hold sends nothing; an update using context whose preview answers meanwhile, or after the body changed since it was asked for, is dropped, and a convergence that already put the saved body in reads it back only after the answer, judging by the room's awareness when it would write. Two tabs that begin a review before either hears of the other settle it the same way everywhere: the review that began first holds (the smaller client id breaks a tie), and the other tab withdraws its own — its card is answered as not applied, its stream stops, its update using context is dropped — without writing the room, while the first one puts its proposal back over anything the other wrote. A tab that drops off stops holding the others once the room drops its awareness state: at once when it closes, otherwise within about 30 s. A reviewing tab whose page is left within the app (the page's Close, a link) while its proposal is still unanswered rejects it on its way out: it puts the body from before the proposal back into the room (the body the chat's run started from, or the one an update using context was drafted from) before the room is torn down, without answering the chat's call, and saves that body when it holds typing of its own that no save covered and nothing else holds saves (a run writing the document, the room behind the saved body, a lost connection); the proposal itself is never saved. Closing or reloading the tab does the same from `pagehide`, as far as the browser still sends it. A proposal left waiting for its answer, while another tab that may edit is in the room, holds the others for at most ten minutes with no key, pointer, wheel or scroll in the reviewing tab and no return of that tab into view: that tab then answers it as rejected (stamped on the chat's tool call as the review bar's Reject stamps it) and says so. The other tabs never stop holding on their own, since they would save the unanswered proposal. The held tabs' status names the person reviewing, as their tab publishes it with its cursor (an editor without a name, published as "Anonymous", names nobody). Limits: a page kept in the back-forward cache (`pagehide` with `persisted`) takes nothing back, since it may come back with the review still open, so its proposal stays in the room once its awareness state lapses; a lost connection is not taken for leaving, and the editor mounted again finds the room as it was; a background tab's timers may run late, so the ten minutes can be longer; and a tab killed without `pagehide` (a crash) leaves its proposal in the room. In those cases another tab can still save the proposal once the hold lapses.
- **Unsaved typing is kept.** A save's answer marks as saved only what it carried, and a failed save leaves its text unsaved — an accepted assistant proposal included, which reads as unsaved from the moment it is accepted until its save lands, and whose outcome the conversation records only once that save answers, showing a card when it was not saved (the assistant's own reply only acknowledges the acceptance); the error a failed save shows is cleared by the next save that lands; an undo in the shared editor counts as typing and is saved; an accepted proposal undone before its save lands is never written; typing that survives a short disconnect stays unsaved and is autosaved, also when the save in flight across the disconnect fails; leaving the page inside the app saves unsaved room typing on the way out, and closing the browser tab asks first. A tab that crashes before its autosave still loses that typing.

## Document page

For organization members, a Proposal in artifact mode shows three tabs:

- **Main Document**: the live sections while the run is queued or generating, then the editor, both on the Proposal theme.
- **Internal Analysis**: the run describing the current text; its report, when it has one: the assessment, summary and what to resolve before sending, with the full report on demand, rendered as Markdown without HTML, links or images, its citations shown as source chips; each finding's state and evidence, Confirm, Answer and Clear for members with edit rights, answers no longer raised, and Re-run. The tab's badge counts Blocking findings still needing a decision.
- **Style**: organization members only. Two groups. Proposer brand: the document's own primary and accent colours, each showing where its value comes from (set for this document, Brand kit, the organization's website, neutral default), with "Use inherited value" and, where another source holds a different value, that value to pick; the logo, fonts and hero from the Brand kit, read-only. Recipient brand: the project's recipient brand, edited by organization members only, and the latest fetch of the recipient's website as a suggestion that applies one field at a time after a member confirms it. The style direction and colours shape the next generation's visuals; the theme follows at once. A Diagrams group holds the **Add diagrams automatically** switch, saved with the rest of the Style; a change applies from the next time diagrams are added.

Project guests see the Main Document only, on the same theme, without the name of the library prompt or a prompt choice: their runs use the bound prompt too.

Members and guests alike have a Download menu at the top of the page, the same menu as on the document's card.

## Proposal theme

A client-document Proposal, one whose owning organization has the `PROPOSAL_ARTIFACT` gate on, is shown on one theme for organization members and project guests alike, so the page a reader edits looks like the document the client receives. The same stylesheet carries a print layer: US Letter pages, running header and footer, the cover and landscape pages. The diff viewer, the other editors and every other document type keep the app's own styling.

- **One predicate.** Whether a document is a client-document Proposal is decided by `isProposalClientDocument` in `@repo/database` (gate on for the project's owning organization, and type Proposal); `projects.proposalArtifact.getThemeTokens` asks it, and the page wears the theme only when that procedure answers. `isProposalInternalReader` adds membership of that organization, the rule the tabs, Analysis and Style follow; their procedures ask it through the member-only loader `loadProposalArtifactDocument`, which keeps its refusals: FORBIDDEN with `ORGANIZATION_MEMBERSHIP_REQUIRED` for a guest, BAD_REQUEST for a document that is not a Proposal. The page itself reads the rollout flag and the document type only to wear the neutral theme while the server's answer is on its way.
- **Tokens.** The theme reads only brand tokens (`@repo/utils/proposal-artifact/theme-tokens`): the proposer's name, logo, primary and accent colours, paper, ink, fonts and hero image, and the recipient's name, logo and colours, each with the source it came from. Each value resolves field by field (see Brand sources): the document's Style, then the Brand kit, then the colours the organization's website declares, then the neutral style; the organization's name and its uploaded logo name the proposer, and the project's recipient brand names the recipient. Everything else is the neutral style: Inter, near-black ink on white paper, one slate accent. A document without brand values shows no logo and the neutral palette.
- **Contrast.** Every colour the theme paints as text, or behind text, is checked against the paper it sits on. A colour that fails is painted with the neutral fallback, and the token keeps its value and source, so a pale brand primary never makes headings unreadable.
- **Paper in both colour modes.** The document is painted on the theme's own light paper in light and dark mode, as it will print. Editor controls inside the paper read the app's colour tokens remapped onto the paper.
- **Guests.** `projects.proposalArtifact.getThemeTokens` gives the page its tokens. It requires document read access, the document to belong to the project, project access and the client-document predicate, and no membership; anything else answers NOT_FOUND. It returns tokens with short-lived signed reads of the logos and the Brand kit hero, and never the Style's direction or the Brand kit's guidance. Logos and the hero are taken only from the keys their uploads write: `{organizationId}.png` for the organization, a promoted hero of the owning organization's Brand kit, the project's recipient brand prefix for the recipient. An uploaded Brand kit font travels in the tokens as its file id only; `projects.proposalArtifact.getThemeFont`, under the same checks, returns the bytes of the slot's current font for that id, and the same NOT_FOUND for anything else.

### Markdown the theme styles

For the owner of the library's Main prompt: the theme gives these Markdown forms their look, on the page and in print.

| Markdown | Shown as |
|---|---|
| The paragraph right after the document's `#` title | Lead paragraph |
| `##` headings | Section headings; in print, a section opener band with a "Section N" eyebrow |
| `> ` blockquote, ideally opening with a bold sentence | Callout: left rule, tinted background |
| A table with a header row | Data table: dark header row, small uppercase labels, zebra rows |
| A `stat-tiles` fence | Stat tiles (below) |
| A Mermaid diagram or an image, with its caption | Figure with caption |

A stat-tiles block is a fenced block with the language `stat-tiles` and one to four lines of `label: value`, the value at most 24 characters and the label at most 80:

````markdown
```stat-tiles
Faster onboarding: 40%
Pilot sites: 3
Annual savings: $1.2M
```
````

A generated block may open with one `%% fabric-visual: <id>` line, the visual's id, which is not a tile. Nothing is evaluated: no HTML, YAML or JSON. A block that breaks the rule is shown as its source with the reason in the editor and as a plain code block elsewhere. In a client-document Proposal the single-user editor, the live sections and both exports draw the tiles; the shared (collaborative) editor, every other document, the other editors and the diff viewer show the fence as code, and the browser downloads of other documents print its lines as text. The shared editor waits because a collaborator's browser on an older release would not know the tiles and would drop the block from the shared document.

## Brand sources

- **Precedence.** Proposer: the document's Style (a person's choice for this document), then the Brand kit (the organization's own settings), then the colours the organization's website declares, then the neutral style. The proposer's name is the organization's only. The logo is the organization logo; fonts and the hero image come from the Brand kit only, and the hero appears on the cover only. Recipient: the project's recipient brand, else nothing; a fetched suggestion never applies until a member confirms it. No recipient value fills a proposer field.
- **Who writes what.** People write the Style, the Brand kit (admins and owners) and the recipient brand (organization members with edit rights; never a project guest). A website fetch writes only its own row: the organization's site fetch and each project's recipient suggestion keep the attempt apart from the last result, so a running or failed re-fetch never takes applied colours away, and a fetch for an old website or a superseded attempt writes nothing.
- **The organization's website.** An admin sets it on the Brand kit. A fetch reads the home page's `theme-color` and manifest, `/llms.txt` for same-host links, and at most two brand-page candidates (`/brand`, one `llms.txt` link that names the brand), over HTTPS on that host only. Applied colours come only from declared sources: six-digit hex values in a brand page's visible text (a three-digit one is too weak to apply there), `theme-color`, the manifest's theme colour. No model reads any of it, and no fetched name or logo is used.
- **The recipient's website.** A member's save that changes it, opening the Style tab without a fetch for it, or "Fetch again" starts a fetch of the stored website (never one the request names). The logo, colours and site name it finds are stored as a suggestion; a member confirms each field, against the attempt they saw, through the recipient brand's version check.
- **Limits.** One bounded request of at most 15 seconds per fetch, rate limited per user and per organization; an attempt still running after two minutes reads as timed out. Each outbound attempt is audited with its host and a fixed code.
- **Uploads.** The hero (PNG, JPEG or WebP, 10 MiB) is re-encoded with its longest edge at most 2,400 px; font files (woff2 or ttf, 512 KiB) must decode: their container structure is checked first, which also bounds what WOFF2 decompression may allocate, then the server decodes the font's tables before a save stores it and again before the page is served it. Both upload to a pending key, are checked again when a save promotes them, and get a new key per upload. The live page loads an uploaded font through the FontFace API under an alias; print stays in Inter until Chromium's sandbox runs, and Word names the family.
- **Export record.** Each export records the hash of the brand tokens as its format printed them: uploaded font files never count, and neither do a PDF's font families, which print in Inter. The record is stamped with the time the export read the tokens, so of two overlapping exports the one that read them later keeps it. No "brand changed since last export" note is shown yet.

## Export

A client-document Proposal's PDF and Word file are made in the Temporal worker, not in the browser. Every other document type, and a Proposal whose gate is off, keeps the browser export it had.

- **Who and how.** The Download menu, on the document's card and at the top of its page, calls `projects.proposalArtifact.export` with the format and polls `projects.proposalArtifact.exportStatus`. Export needs document read access, the document to belong to the project and project access, and no organization membership: a project guest exports the same client document a member does. A caller without access gets NOT_FOUND. A readable document that is not a client-document Proposal gets BAD_REQUEST with `PROPOSAL_EXPORT_UNSUPPORTED`, and the menu then exports it in the browser as before. A client-document export that fails never falls back to the browser renderer. Exports are limited to 10 per user per 10 minutes, and each start records `project.proposal_artifact.export_started` with the format, the export id and whether the starter is a guest.
- **Workflow.** The export id is the id of a `proposalExportWorkflow` on its own `proposal-export` task queue, with two activity slots, so at most two exports run a browser in one worker at a time. The workflow's memo binds the export to its starter, organization, project and document, so no table is needed. One activity does all the work, because the document, the rendered diagrams, the print page and the file are too large for workflow history: it checks the starter's access again, reads Main and the guest-safe brand tokens, renders, uploads and returns only the file's key. The status read checks the id's shape, the workflow type, the memo's binding to the caller and project, then the gate and access again, and answers NOT_FOUND to anything else, including another reader of the same project. It signs a five-minute download link with an attachment disposition on every read; the link is never stored.
- **What the file holds.** Main only. Before rendering, `scrubProposalExport` (`@repo/utils/proposal-artifact/export-scrub`) removes citation markers (`[S3]`, `[cite]` and their written forms, never inside code) and Source Index sections; everything else, the document's own appendix and TBD lines included, exports as the page shows it. The Markdown download of a client-document Proposal goes through the same scrubber. Brand comes from the guest-safe resolver, so style direction and Brand kit guidance never reach the worker.
- **PDF.** The print page is built from the scrubbed Markdown with the theme's print layer: a cover, a contents page, section openers, styled tables, callouts, stat tiles and figures, US Letter, with the running header (the title) and the footer ("proposer · title · date · Confidential" and "Page N of M") drawn by `@page` margin boxes. The cover counts as page 1 and carries no furniture. It shows only fields the data holds: the title, both parties' names and logos, and the date; prepared-by lines, validity and confidentiality stay in Main's own text. Headless Chromium prints the page twice: the first print, which nobody sees, carries a text marker per section, laid out of flow so it moves nothing, whose page is read back with `extractPdfPageTexts` (`@repo/rag`), and the second writes the numbers into fixed-width slots on the contents page, so filling them cannot move anything. When the page lookup fails, the contents page lists the sections without numbers and the export says so.
- **Word.** The same Markdown tree is written with `docx`: heading styles in the brand's display font and heading colour, a numbering instance per list, tables with a repeated shaded header row, tables wider than six columns on their own landscape pages, images in their real type, diagrams as PNGs, stat tiles as a borderless table, and a contents field Word fills when the file is opened. Links are kept only for `http`, `https`, `mailto` and in-document anchors, never a link to a stored object; the file holds no other external relationship.
- **Images and logos.** Only uploaded images are carried, taken from their `data-s3-key` under the document's own media prefix, read from storage (never from a URL; streamed, and abandoned as soon as one passes 10 MB), checked by their leading bytes (PNG, JPEG, GIF, WebP; never SVG), and re-encoded to PNG or JPEG with their metadata dropped. Logos are read the same way from the keys their uploads write. Images linked from elsewhere are left out. Raw HTML that names a stored object (a refused or broken image tag, a file link, a signed storage URL) is never printed as text, and neither is an author's HTML comment; an image tag whose quoting the Markdown parser could not read is treated as the tag it is. A storage URL or media path written into Main's text, code, diagrams, an image's alt text and caption, the title or a party's name is dropped, and a link to a stored object keeps only its words.
- **Diagrams.** Mermaid fences render in the worker with beautiful-mermaid, the engine the page uses, in the brand's colours. `%%{init}%%` directives, front matter and `click` lines are removed first, and every SVG passes an allowlist that keeps no script, foreign content, event attribute or external reference, and exactly one cleaned style element. Kinds beautiful-mermaid does not draw (timeline and gantt syntax, front matter) print as a captioned placeholder; a diagram never fails an export. Layout runs in a worker thread of its own, 10 seconds at most per diagram, and stops 50 seconds before the export's deadline, so a document of slow diagrams prints placeholders for the rest rather than timing out.
- **Font.** The print page embeds Inter 4.1 (SIL Open Font License, `packages/temporal/src/lib/proposal-export/fonts/`), weights 400, 600, 700 and 800. The Word file names the fonts the brand chose and embeds none; the neutral style is written as Arial, which every Word has, because a missing Inter would fall back to Word's default serif.
- **Budgets.** Main up to one million characters, 40 diagrams, 30 images (10 MB each, 40 MB with the logos), 150 pages and 150 seconds per export. An image placed many times counts again at every placement, up to about 80 MB of image data on the print page and 60 MB in the Word file (cover images and diagrams included, the cover first); placements past that are left out with a warning. A budget that is exceeded fails the export for good; an image or diagram over its own limit is left out with a warning. The menu names what was left out after a download.
- **Files.** Exports are stored under `proposal-exports/{projectId}/` in the project contexts bucket. A daily schedule (`proposal-export-cleanup`, 06:15 UTC) deletes those older than 24 hours, in sweeps of up to 5,000 that repeat (up to 20 a day) while one stops at that cap, the status read stops signing links for them, and deleting a project deletes its exports.

## Decisions and limits

- **Retired Proposal actions.** With the gate on, the Prompt Library, binding dialogs, nominations, governance view, project prompt defaults and the setup wizard offer only Client proposal (Main) for a Proposal. The Project Document Generator and Document Generator Proposal slots are hidden, saved overrides there are listed as no longer used, and new organization or project defaults at them are refused (`PROPOSAL_ACTION_SUPERSEDED`); nothing is deleted, and organizations with the gate off see the slots as before.
- **Agents follow the status, people the ten-minute rule.** The editor lets people save over a Proposal whose run has written nothing for ten minutes; agent and API writes stay refused until the watchdog fails such a run.
- **Stat tiles are not generated yet.** The visuals step still does not produce them; a stat-tiles block appears only where a person or the Main prompt writes one.
- **Free-form instructions stay.** Instructions typed when generating are appended to the Main prompt as before; the Main prompt is what keeps the result client-facing.
- **No model check before guests read Main.** The separation is structural: Analysis runs only after Main is saved, and its output lives only in organization-only tables. The Main generation never sees a finding's detail or evidence; it sees members' answers and the titles they answer, as settled decisions, guarded by the echo check above.
- **Raised again means Needs Review**, even when the section's text has not changed, and such an answer stops feeding generations until a member confirms it again. A re-run can therefore move answers to Needs Review when the model repeats a finding.
- **Old runs cannot be answered.** Findings recorded before Fizzy #2946 have no stable key; the page offers a re-run instead.
- **Analysis sees visuals as Mermaid source**, not as rendered images, so it cannot judge their appearance.
- **A report needs a prompt that asks for one.** The seeded analysis prompt asks for findings only, so organizations on it get no report. When a report is asked for, findings arrive with it, a minute or more later than they would alone, and the analysis input is sent to the model twice. A report keeps its text after a cited source is deleted, as Main does; only its chip turns to "Source removed", and deleting the document, project or organization removes it with its run.
- **Operational choices.** Analysis runs on the `project-documents` task queue. Style changes are not audit events: they are presentation settings, not security-relevant mutations.
- **Exports print without Chromium's sandbox, for now.** The sandbox does not start under the worker image's default seccomp profile. Until it runs, or exports move to a render container without secrets, Chromium is launched with an environment of only a search path and a scratch directory (no database, storage or model credentials), runs no page JavaScript, loads nothing from the network and embeds only the committed Inter. So the PDF is set in Inter even where the page shows an uploaded brand font, and timeline and gantt diagrams, which would need the browser engine, print as placeholders.
- **The Word contents page fills itself when the file is opened**, so Word asks to update fields; other word processors may show it empty until updated.

## Rolling it out

1. Create the client-only Main prompt and the analysis prompt in the organization's prompt library and bind them to the **Client proposal (Main)** and **Proposal internal analysis** actions. The seed creates synthetic defaults for fresh environments only; existing environments need the binding by hand. The Main prompt should structure its sections with H2 or H3 headings, which is what live sections cut on.
2. Enable `PROPOSAL_ARTIFACT` for the organization on its per-organization feature flag page, not the global panel.
3. Keep `GLOSSY_EDITION` on wherever existing Glossy editions must stay viewable.

The review release adds a migration and changes the analysis activity, so it deploys in the usual order: migration, then the Temporal worker, then the web. A re-run started by a newer web on an older worker would analyse without its sources and record findings that cannot be answered.

The report release adds two nullable columns to `ProjectDocumentAnalysis` and deploys in the same order. A worker that runs before the migration still completes runs without a report and loses only reports; the previous web and worker ignore the columns.

The export release deploys the worker before the web too: the web starts exports on the `proposal-export` queue, which only the new worker polls, so an export started first would wait there until the menu stops waiting. The worker image already carries Chromium for frame export.

Visuals and Analysis resolve their model like generation does. An organization without a configured AI provider gets Proposals without visuals and an analysis that reports the provider as not configured.
