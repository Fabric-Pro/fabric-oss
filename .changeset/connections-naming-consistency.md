The Get Started guide now calls the connections area "Connections", matching the page it opens, and that page explains when to use a native Integration versus an MCP server — both as an introduction above the two options and as an on-demand hint at the control where the choice is made.

The catalogue moved out from under Settings to a top-level Connections destination in an earlier release, which renamed the sidebar item, the page title and the heading. Three Get Started registry entries pointing at that destination kept their old "Integrations" labels: their `href` values were repointed in the same object literals, and a sibling entry in the same block was relabelled and had its description rewritten to name Connections, so the labels were missed rather than deliberately retained. The drawer has been describing the old destination since. One of those entries — a settings-list card — no longer led anywhere under Settings at all and duplicated the area card's destination, so it is removed rather than renamed.

The page's own copy had drifted the same way. Its list holds MCP registry tiles beside the integration providers and its search box filters both, yet the loading, error, empty and placeholder strings all said "integrations". They now say "connections", the superset that is accurate on every tab. The three "Back to Integrations" buttons on provider, connection and workflow-integration detail pages now say "Back to Connections"; their routes are unchanged, because the route was already correct and only the label was wrong.

Two things deliberately keep the old word. The segmented control's "Integrations" tab, the action-integrations group and the browse item name a real sub-kind of Connections, not the container. And the settings breadcrumb map still reads "Integrations", because provider and action detail pages genuinely still live under that slug — renaming it would assert that Connections sits under Settings, which is the structure the move removed.

Every onboarding identifier is untouched. The registry ids, the `nav-integrations` anchor, the in-page onboarding targets and the page-tour tab key are all load-bearing: the tab key in particular is a stored per-user marker for which page tours someone has already seen, so renaming it would orphan that state. Only human-facing labels changed, and those labels carry no translation keys — the drawer's registry copy is inline by design, so there is no message catalogue to update alongside them.

Tests: a new registry test pins that exactly one Get Started entry resolves to the connections destination and is labelled "Connections", that no entry is still labelled "Integrations", that the removed settings card is gone, and that the frozen id and anchor survive — deliberately in a new file so the existing drift guard stays byte-identical. A first test file for the connections page asserts its heading, that the introduction renders above the list component, that it covers each required point, that exactly one explanatory paragraph renders, that the measure stays clamped, that the "Integrations" sub-kind tab survives the rename, that the introduction survives when the list component fails, that the hint at the control reveals the same decision sentence, and that the hint repeats the introduction's closing sentence word for word rather than paraphrasing it. The other half of that ordering claim — that the list component puts its toolbar above the provider catalogue — is pinned separately against the real component, since a stubbed child can only speak for its own placement. The page-content tests cover the four renamed strings and guard that the onboarding target on the search box is still in place, and the provider-page test now pins the back link's route alongside its new label.
