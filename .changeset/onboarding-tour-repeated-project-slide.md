Show the onboarding tour's "Create your first project" card once instead of five times in a row when the account has no project yet (Fizzy #2360).

Five of the tour's nine steps target a project — `overview`, `documents`, `roadmap`, `proposals` (`kind: "projectComponent"`) and `atlas` (`kind: "projectTab"`). `GetStartedSpotlight` resolves a project id per step and falls back to the shared `onboarding.tour.noProject` card when it can't find one. That fallback is correct for a single step, but each of the five hit it independently, so a brand-new account saw the identical card at positions 4 through 8 with the counter still reading "Step 4 / 9". The reporter observed steps 4-6; the true span was 4-8.

The triage hypothesis — an off-by-one or duplicate index in the step registry — was wrong. `ONBOARDING_STEPS` is clean; the repeat is emergent from a per-step fallback that cannot see the whole sequence. The fix therefore lands where the sequence is assembled, not where a step is drawn.

`resolveTourSteps` is a new pure helper in `tour-steps.ts`: it applies the existing tab-visibility filter (card #1837) first, then, when the viewer has no project, keeps the first *surviving* project-scoped step and drops the rest. "First surviving" matters because tab customization can hide Overview. The step counter and dot navigation both derive from `steps.length`, so a five-step list reports itself honestly with no separate change.

`GetStartedController` feeds it a three-state answer from a `projects.list({ limit: 1 })` probe fired on mount. Only a successful empty response collapses; pending and failed both read as "don't know" and leave the tour intact. Collapsing on an error was tried and rejected — sharing an endpoint with the spotlight is not sharing an outcome, and a transient failure would then hide four real steps from someone who does have projects, frozen for the rest of the run. The accepted residual is that while the endpoint is failing outright the five steps fall back to the same card as before; nothing available can tell "no projects" from "can't reach the API", and during an outage the tour is already navigating to project pages that won't load.

Both lookups now state `includeDraft: false` explicitly, and must keep agreeing. The property that prevents the repeat is that the controller's existence probe and the spotlight's `resolveProjectId` answer the same question — if one counted drafts and the other did not, the controller would keep all five project steps while the spotlight still failed to resolve a project, restoring the exact five-card repeat. Counting drafts was tried and reverted for a second reason: `list` orders by `updatedAt DESC` and takes one, so a half-finished draft could outrank a real active project and send the tour to spotlight components that do not exist on it yet. An account whose only project is still a draft has not finished making one, and pointing it at "Create your first project" — once — is the right guidance.

The controller freezes the collapse *decision* for a tour run — one boolean — and only once the probe has answered. Freezing the resolved step list instead was tried and reverted twice over. Freezing it eagerly stranded a tour that started during a slow request on the uncollapsed nine steps for its whole duration, which is the original bug merely narrowed. Freezing it at all was worse: tab visibility resolves per project and its query is disabled until one is on screen, so a tour launched from the sidebar starts with every tab looking visible, and a frozen list would keep steps for tabs the viewer turns out not to have and then wait on anchors that never render. Visibility therefore stays live, and an index clamp is what makes a shrinking list safe — the render gate is `steps[index]`, so an index past the end would otherwise unmount the tour outright. That last hazard predates this ticket, via the same late-resolving `tabCustomization`.

Because that list is live, the tour now tracks its position by step id rather than by array slot, resolved by a second pure helper, `resolveTourPosition`. Removing a step *before* the current one shifts every later index down, so a bare index silently moved the viewer elsewhere — hiding the stories tab while they were on Atlas landed them on the wrap-up, skipping Atlas outright. When the remembered step is itself removed, the successor is found by walking *registry* order rather than by reusing the old index, because one visibility result can remove several steps at once: with both `overview` and `documents` gone, the old index no longer addresses `documents`' successor at all and skips `roadmap`. The helper never returns an out-of-range index, which is what keeps the tour mounted at all — its render gate is `steps[index]`. This part is a pre-existing defect rather than a regression from this branch (`master` filters the same live list against a bare index, and without even a clamp), but it sits in the code this change touches and is fixed here.

The reporter's second ask — a new first slide pointing at AI-key configuration — is deliberately not included; the ticket's own triage recommends tracking it separately.

Covered by `tour-step-resolution.test.ts` (20 cases over the two pure helpers) and `GetStartedController.tourSteps.test.tsx` (12 cases over the wiring). The decision freeze, the live-visibility behaviour, the step-id tracking and the probe-input coupling were each verified by reverting them and watching the matching test fail, so none of the guards is vacuous. `drift.test.ts` passes unmodified — the static registry is unchanged.
