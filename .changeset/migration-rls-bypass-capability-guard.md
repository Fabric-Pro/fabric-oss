Ship a corrective migration so the publishing-topic enum contract also applies where no role can bypass row-level security.

Fizzy #2307. The contract half of the publishing-topic enum pair opens with an unconditional `SET LOCAL row_security = off` before draining stray DEFERRED rows. That statement grants nothing: for a role that bypasses RLS it is a no-op, and for a role that cannot it makes the next query whose result RLS would affect raise 42501, then 25P02 for everything queued behind it. The asymmetry was deliberate — a loud alarm instead of a silent `UPDATE 0` — and it is correct on a host where the bypass attribute is the only way to see every row.

Databricks Lakebase is not such a host. It grants BYPASSRLS to no role at all, and RLS runs in policy mode there with permissive `app_bypass` / `worker_bypass` policies standing in for the attribute. So the migration failed on dev, and because the reconciler promotes a release whole, it blocked every staging deploy behind it.

**The fix is a second migration rather than an edit to the first, because the first has already applied.** Production is Neon, whose migration role carries the bypass attribute, so it applied there cleanly in the v1.14.0 promotion — 492 migrations found, 492 recorded, nothing pending — roughly two hours before dev ever attempted it. (The release commit holds exactly 492 migration directories and its parent 491, with this migration the sole addition between them; the runner was `migration-runner@sha256:afcb78b107a154fd5540a0a5015da4fe3b2e5e47fb7a4363f3978d17ef30fdcc`, recorded in full so the reading does not rest on count equality alone.) `docs/database-promotion.md` names this case exactly: Prisma stores a checksum per applied migration, so editing one that has applied elsewhere is rejected there. An in-place fix would have traded a staging blocker for a production one. The original stays byte-identical.

The corrective migration is idempotent by construction, because it has to run against both worlds: it keys on whether the `DEFERRED` label still exists, so it is a no-op where the original succeeded and does the whole rebuild where it failed. The label's own existence is the check rather than a ledger lookup, so it stays correct however the failed row was resolved by hand. The check is bound to the OID of the type `publishing_topic.status` actually uses, not to the type NAME: enum names are unique per schema rather than per database, so a same-named enum elsewhere that still carried DEFERRED would otherwise send an already-contracted production database down the rebuild path, take an ACCESS EXCLUSIVE lock, and fail parsing 'DEFERRED' against the contracted type it really has. Confirmed on a clone with exactly that decoy present: the name-based form proceeds, the OID-bound form does not. Its guard fires only when `pg_roles` reports `rolsuper` or `rolbypassrls` for `current_user`, and every statement inside the block is `EXECUTE`d because half of them reference a type created earlier in the same block.

Two properties of that guard were established on a clone rather than assumed: BYPASSRLS is **not** conferred by role membership (a role inheriting from a BYPASSRLS role still raises 42501, so a membership-aware condition reads as a capability check and is not one), and `SET LOCAL` inside a `DO` block persists for the rest of the transaction. Where the guard stands down, correctness does not rest on the drain: the `ALTER COLUMN ... TYPE ... USING` cast is DDL and so is not RLS-filtered, so a surviving DEFERRED aborts the transaction with 22P02.

Verified against six shapes on a local clone — policy-mode bypass and own-BYPASSRLS both apply and drain; no bypass at all aborts loudly with 22P02; a second run is a clean no-op; and the production shape, where the label is already gone, is a no-op that never touches RLS even for a role with no bypass of any kind.

**The operator step differs from the runbook's usual one.** `prisma migrate resolve --rolled-back` on the failed environment would make `migrate deploy` re-run the ORIGINAL file and fail on the same SQL again — the runbook records a rehearsal that put four mid-flight rows in one ledger that way. The failed row is resolved `--applied` instead, which is safe only because this migration performs that one's work idempotently right after it.

Adds `packages/database/__tests__/migration-rls-bypass-capability.test.ts`. Its static half needs no database: it scans a migration into two length-aligned views — comments blanked in both, string literals kept in one and blanked in the other, where "literal" includes the dollar-quoted kind — then requires every `row_security` token to sit inside the BODY of an `IF` whose condition mentions `rolbypassrls` and `current_user` and not `pg_has_role`. Control dependence rather than mere containment is the point: a block holding an unrelated capability check followed by an unconditional write reads as guarded and is not. The block is walked as an ordered token stream, so `END IF` is a single token and the `IF` inside it can never read as an opening one — a fixed backward window gets `END /* ... */ IF` wrong once the comment outgrows it. A top-level `ELSE` or `ELSIF` disqualifies the body, since on either branch the write might be the one taken when the role cannot bypass. It remains a text-level rule, not a plpgsql parse: a `CASE ... THEN` inside an `IF` condition, or a quoted identifier containing a control keyword, would confuse the tokenizer. Neither appears in the migrations this guards, and the rule is deliberately conservative — it fails an unusual guard rather than passing an unsafe one. The original migration is exempt by name, because it is applied and therefore immutable; nothing else belongs in that set. That rule matters because CI cannot catch this class on its own — `db-integration.yml` applies migrations as the `postgres` superuser, which bypasses FORCE ROW LEVEL SECURITY by design, so a migration written against the bypass attribute passes there and fails only on the host that has no such attribute.
