The web app now forwards its server logs and unexpected client-side oRPC failures to Application Insights, like every other backend service.

Every Azure-hosted service (temporal-worker, agents, weave, mcp) already reports to Application Insights; the web app, running on Vercel and hosting the whole oRPC API, sent 0 records — its logs were reachable only through Vercel's own runtime log viewer. `@repo/observability`'s existing App Insights client is now shared between the flag-gated `trackEvent`/`trackMetric` path and a new, always-on log-forwarding path (`initAppInsightsLogs`, `trackLog`, `trackLogException`, `flushAppInsights`), sampled per key (20/min default) so a hot-path failure cannot flood the workspace. `@repo/logs` gained a generic `addLogSink` hook (consola `addReporter`) that `apps/web/instrumentation.ts` wires to it — `@repo/logs` never depends on `@repo/observability` directly, avoiding the cycle a `@repo/database` import would create. Every forwarded record — message and structured properties alike — goes through the shared sensitive-key + value-shape redactor first (`@repo/utils/log-redaction`). Vercel's Fluid Compute can freeze the process between requests, so `app/api/[[...rest]]/route.ts` flushes on every request via `after()`.

On the server, `packages/api/orpc/handler.ts`'s two bare `logger.error(error)` calls are replaced by two interceptors. An `interceptors` entry captures the thrown error, stack included; `clientInterceptors` never sees an input-decode failure, because a malformed body throws before the procedure client is invoked. A `rootInterceptors` entry then logs exactly once from the FINAL response status, so a raw exception is classified the way oRPC itself classified it (decode failure → 400, procedure failure → 500). 4xx are logged as a warning and 5xx as an error with the original stack, tagged `event: "rpc.error"` with the procedure path, code, status and a message truncated to 300 characters. Input payloads are never logged.

On the browser, an expected 4xx (one the caller already handles) now logs to `console.warn` with the procedure and code instead of staying silent; other failures still go to `console.error`. Two failure shapes the server-side change above cannot have seen — a transport failure and a rewrapped proxy/platform error page — are queued (deduped, capped at 20 per page session) and flushed to a new `/api/client-errors` ingest route via `sendBeacon`/`fetch(keepalive)` every 10 seconds and on `pagehide`/a hidden `visibilitychange`. Sent always, never gated on analytics consent — this is operational telemetry about the app breaking, not tracking. The payload carries no message text, only a masked route, procedure, kind, and status/code; the ingest route requires a session, rejects cross-site posts, caps the body at 16 KB, validates the batch (zod, max 20 items), and rate-limits per user (30/min) before logging each item (the sink then forwards it).
