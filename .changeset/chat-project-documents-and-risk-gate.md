The AI assistant lists and reads a project's documents and Context-tab sources, and no longer asks approval for read-only searches.

Fizzy #2578 (and #2570, unified AI chat #2040). A staging retest found three problems in the Fabric Agent chat with a project attached.

A. Documents and Context-tab sources. "List all the documents in this project" ran 18 semantic searches over 3.7 minutes and returned a guessed list; "What does the PRD say about auth?" got an intake question about how many PRDs there are. Four live, read-only chat tools now exist, following the `project-feature-reads.ts` pattern (one shared implementation in `activities/shared/project-document-reads.ts`, bound by Direct's built-ins and the orchestrator's catalog adapter, access via `getProjectAccessContext`, project from the chat and never from the model): `fabric_list_project_documents`, `fabric_get_project_document`, `fabric_list_project_sources`, `fabric_get_project_source`. Lists have type/search filters, limit/offset/total/hasMore and a `summary` sentence; sources exclude repository code-index entries by default and say how many were left out. Gets return the body in pages (15k default, 40k max, `nextOffset`) with `contentAvailable`/`unavailableReason`, and refuse a row from any other project. They reuse the MCP gateway's queries (`listDocuments`, `getDocumentById`, `listProjectContextSummaries`, `getContextById`); the gateway's context title/provider/unavailable-reason helpers and its body-page reader moved into `@repo/database` (`src/project-context-presentation.ts`, `prisma/queries/projects/context-body.ts`) so Temporal can import them, and the export's `classifyConversationPointer` moved with them. `listDocuments` and `listProjectContextSummaries` gained an optional `search`. Registered in the orchestrator catalog, the catalog adapter (READ), capability keywords, the tool index's always-on set, Direct's built-ins and interactive-chat ride-along, the `project-context` built-in capability (database and web copies), the Direct grounding line and the trajectory labels. The iterative loop pre-registers them behind `orch-project-document-tools-v1` and appends a listing hint to `project_rag_query`'s description there; the catalog's `project_rag_query` description carries the same hint. `INTENT_CLARITY_PROMPT` now says never to ask which documents or sources exist.

B. Read-only search held for "delete" approval. `assessToolCallRisk` in `workflows/orchestrator/risk-assessment.ts` substring-matched keywords against the tool name and serialized args, so a `project_rag_query` mentioning "unclear risks" matched "clear". New rules (`read-only-exempt-v1`): a Fabric-owned read is never scanned. The call must be routed to Fabric — one of the loop's own built-ins (dispatched by name ahead of MCP) or the Fabric catalog's virtual config — which the call site passes in from `discoveredToolConfigIds`; a same-named tool on another MCP server is scanned as usual. The READ declarations live in the workflow-safe `workflows/orchestrator/fabric-catalog-access.ts`, shared with the catalog adapter. The tool name keeps legacy substring matching (so `bulkdelete`, `HTTPDelete`, `deletefile` stay gated); arguments match by word, split at camelCase and acronym boundaries, with inflections (`deleted`, `removal`, `archived`, `cleared`…), so `unclear`, `address`, `call` and `small` no longer match. Chosen at the call site in `phases/iterative-execution.ts` behind `patched("orch-risk-read-only-exempt-v1")`; recorded histories keep the legacy rules. The activity-side `assessToolCallRisk` in `planning/operation-risk-detector.ts` has the same substring flaw but no production caller (tests and a barrel export only), so it is unchanged.

C. Code index not ready. `code_search` (Direct's builder, which the orchestrator also runs) returned `{ success: false }` for an index that was still building, which counted toward the loop's three-strike breaker and aborted the turn with the raw operator string. It now returns a plain `{ available: false, status, results: [], message }` telling the model to answer from other sources; `code_search_semantic` says the same instead of "No semantic code matches found". A wrong repository name is still a failure. The breaker's message is now "I couldn't complete this: `<tool>` kept failing (<error>). Try again, or ask differently." (text only; on the iterative path it feeds no command or activity input). The failed turn did not render live because the orchestrator chat had no render branch for a finished, failed turn: the stream route sent the `error` event, the hook stored it and the client persisted it, but the JSX only showed streaming, a `response`, or cancelled turns. `FabricTemporalOrchestratorChat` now shows `state.result.error` for a failed turn until it moves into the completed list.
