Publishing Suite: marking a topic Selected no longer waits for its planning analysis to start, so the status saves as quickly as any other.

Fizzy #2651. The report was that status changes appeared not to save, and then did after a delay. The list-side half of that was fixed by the optimistic status overlay (Fizzy #2646), which shows the new status at once; what remained was the server holding the SELECTED response on the analysis auto-start — `updateTopicStatus` awaited `autoStartPlanningAnalysis` before responding, so a Selected change on a topic with no analysis attempt yet, in a project with fewer than five analyses already running, waited on the Temporal availability probe, the attempt insert under the Project-row lock and the workflow start, plus a TLS connect to Temporal on a cold instance. The start is now handed to `runInBackground` (Vercel `waitUntil`, rejection logged) once the status write has resolved, and the procedure returns without waiting on it; the topic page's own load-time auto-starts remain the fallback, and when a page start races the background one the server claims attempts under that lock and a partial unique index over GENERATING rows, so at most one of them runs while either is GENERATING. One accepted edge, on the topic page: the post-write re-read of `getPlanningAnalysis` can now land before the background start has created its attempt, so a page that holds no attempt (its own auto-start refused, e.g. Temporal unavailable at page load) can keep showing none — a refocus after the read goes stale finds the run, and Generate or a remount finds it while it is still running, but after it has finished either can start a second run.
