Feature and bug statuses can now follow their linked PM ticket's mapped status, including GitLab label maps, behind a per-project switch.

Fizzy #2304. A new per-project setting, "Keep status in sync with the PM tool", is off by default and needs PROJECT_SETTINGS_EDIT to change. With it on, the hourly PM poll moves a linked feature or bug to its ticket's mapped status (REST GitLab through the project's label map, other tools by case-insensitive status-name match). A move made only in Fabric stands until the ticket's mapped status next changes; if both change between two polls, the ticket wins. Each applied move is a compare-and-set on the row the poll read, writes a story.pm_status_synced audit row (shown in the story's change history as synced from the tool) and one SUCCESS pull sync-log row, and fires no push, automation or notification. Ambiguous labels and unverified links raise one deduplicated CONFLICT row. With the switch on, a REST GitLab push replaces the story's mapped status labels only when Fabric's status changed since the last observation and the ticket's did not, and a push that creates the issue sends exactly the story's mapped status labels and records the new link's sync base. With the switch on, the poll reads linked tickets from a random offset each cycle and caps its result at the Temporal payload budget, leaving any overflow for the next cycle. GitLab over MCP is refused. The settings card shows the last status-sync run: fetch and outcome counts, failures and staleness.

Default-on changes (these apply with the switch off):
- A REST GitLab settings re-save that keeps the same server and container no longer counts as a disconnect, so it no longer switches the hourly poll off and no longer clears attachment sync where the attachment-sync flag allows it.
- The GitLab REST project picker keeps a container saved as GitLab's numeric project id, and keeps one that the 100-project listing does not include as an explicit "Current project" option instead of preselecting another repository.
- The REST GitLab branch of the hourly poll's item fetch is now concurrent (a read abandoned at its timeout keeps its slot until the request settles, so at most eight GitLab requests are open per project fetch attempt), timed out per call, budgeted and heartbeated, so enrolled REST GitLab projects stop timing out. The fetch stops starting new reads after GitLab answers with a rate-limit (429) response and leaves the rest for the next cycle; large projects on GitLab.com, whose authenticated API limit is 2,000 requests per minute per user, may still spend part of their token's per-minute budget each hour. Those projects then also complete their terminal-status, content-drift and missing-ticket passes, so expect a one-time burst of content-drift CONFLICT rows and notifications on the first runs after deploy. Before deploy, count the enrolled REST GitLab projects and their stories with a sync baseline (lastSyncedPmHash) to size it.
- REST GitLab item reads for selective story and test-case pulls and the one-off test-case import now send an activity heartbeat every 10 seconds while a read is in flight, so a pull longer than 30 seconds is no longer cancelled by its heartbeat timeout (the 60-second activity limit still applies). A REST read abandoned at its timeout is not aborted, because GitLab requests carry no cancel signal, so its connection stays open until GitLab answers or the HTTP client's own 300-second timeout ends it.

Out of scope, tracked as separate tasks: the inert state-poll watermark (an ISO string compared with a Date, so the poll re-reads every linked item each cycle), REST GitLab auto-push never enqueueing, and the project wizard saving a null container for REST GitLab.
