Add a per-organization feature-flag control to the admin console, so a rollout can be scoped to named organizations without a deploy-time script.

Slices 1-3 made the server and the client resolve `PUBLISHING_SUITE` per organization, but nothing in the product could create the row they resolve. The only writer was `packages/database/prisma/seed-publishing-suite-orgs.ts`, which is `createMany` with `skipDuplicates` — enrolling an organization needed a script run with a database URL, and un-enrolling needed raw SQL. That script's own header names this admin picker as its successor.

The organization's admin page (`admin/organizations/{id}`) now renders `OrgFeatureFlagsPanel`: one row per org-scopable flag with a three-position control — Inherit / Enabled / Disabled. Inherit is not a stored value; it deletes the row, which is why it is a separate procedure rather than a write of `false`. A stored `false` is the exclusion case and stays meaningful: it holds one organization out of a deployment-wide rollout.

Three procedures under `admin.featureFlags`: `listForOrg`, `setForOrg`, `clearForOrg`. Each is `adminProcedure` + `requirePermission`, validates the key against the registry, and resolves the organization so an unknown id is a clean 404 rather than a foreign-key 500. Two new closed-taxonomy audit actions carry the change — `featureFlag.orgUpdated` and `featureFlag.orgReset` — written durably with the organization at TOP LEVEL, not in metadata: the organization audit log filters strictly on that column, so a metadata-only reference would hide the change from the tenant whose features it altered. Each write also marks the request as having emitted a curated row, or the activity middleware appends a second, differently-scoped generic event.

The load-bearing guard is `orgScopable`. `resolveFlag` ignores an org-level value for any flag that does not declare it, so a row written for one is inert — it would read back as a working switch while changing nothing, and nothing would clean it up. The guard now sits at the database write boundary, not only in the procedure, because the helper is exported through the `@repo/database` barrel and scripts reach it without going through oRPC; the enrolment seed, which writes through `createMany` for atomicity and so bypasses the helper, restates the check at module load. The panel is fed from `ORG_SCOPABLE_FLAG_KEYS`, derived in the registry rather than restated, so a flag becomes per-organization configurable by declaring the marker and nothing else.

Both mutations re-resolve after their write through a new UNCACHED reader and return that state; the panel patches its query cache from it and never refetches. The web service runs at `replicas: 2` with an independent 10s flag cache each, so a refetch right after a write can land on a replica that has not caught up and visibly flip the control back (#2138) — which makes the response the only thing correcting the UI, so it cannot itself be cached. Two ways a cached read would have been wrong: an organization's entry can be refilled by a fetch that began before the write evicted it, and the global entry is not evicted by an organization write at all, so a cleared row could report `env` for a flag an admin turned off instance-wide seconds earlier. The writers still evict the written organization's entry, pinned by a test that a second organization is *not* re-read, so a blanket cache clear cannot pass.

Known limitation, unchanged from the instance-wide control next door: the override row commits before the durable audit write, so a failing audit reports failure for a change that happened. Retrying is safe — the upsert and the delete are both idempotent. Making it atomic requires `recordAuditTx` inside a transaction and therefore a `Prisma.TransactionClient` parameter on the writer, which is worth doing for both halves of this control together rather than for one of them.

Also corrects three comments this made false. The `PUBLISHING_SUITE` registry note — rendered to operators by the admin console — ended with "Read in server activities and procedures only, never in workflow code", which stopped being true when slice 3 made the flag a client read; it also still described a per-personal-project sweep that ADR-018 removed. It now states the visibility consequences (project tab, project settings, Get started drawer and page tour) and keeps the determinism rule as a rule rather than a description. `FeatureFlagsPanel` no longer claims flags are global with no per-organization scope, and the two admin pages no longer point at a personal route tree that is now a redirect.

Tests: 14 new in `@repo/database` covering tri-state semantics, both allowlist directions, the write-boundary refusal and targeted cache busting; 16 new in `@repo/api` covering the registry and organization guards, the top-level audit scope, curated-row marking and the uncached post-write resolution. The permission-coverage gate was confirmed to actually cover the new procedure file by removing its decorators and observing it fail.
