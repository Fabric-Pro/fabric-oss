Add an opt-in ngrok tunnel resource to the Aspire AppHost so OAuth callbacks and webhooks reach local development without a hand-fed URL.

Local development had a Better Auth allowlist for ngrok hosts (`NGROK_URL`) but nothing that started a tunnel or told the app about it, and the AppHost pinned `NEXT_PUBLIC_SITE_URL` to localhost, so server-generated OAuth redirect URIs never used a tunnel even when one was running. The AppHost now reads `Parameters:ngrok-domain` and `Parameters:ngrok-auth-token`; when both are set it runs the ngrok agent as a `tunnel` container forwarding the reserved domain to the web app via host.docker.internal, points `NEXT_PUBLIC_SITE_URL` at the tunnel, injects `DEV_TUNNEL_URL`, and shows the public URL on the resource. With either parameter blank nothing changes. `DEV_TUNNEL_URL` replaces `NGROK_URL` in `packages/auth/lib/trusted-origins.ts`, which now accepts both ngrok hosts (one label) and Microsoft dev tunnel hosts (two labels), and `next.config.ts` adds the tunnel host to `allowedDevOrigins` so Next's dev server does not block `/_next/*` requests arriving under the public hostname. The integration connect flow (`packages/api/modules/mcp/procedures/connect.ts`) now derives its OAuth callback from `getBaseUrl()` when `NEXT_PUBLIC_APP_URL` is unset, instead of `APP_URL`, which local dev never sets. The ngrok agent runs as a plain container rather than through CommunityToolkit.Aspire.Hosting.Ngrok because that package writes `localhost` as the upstream on Linux, which is unreachable from inside a container, and never injects the public URL anywhere. (Fizzy #2374)
