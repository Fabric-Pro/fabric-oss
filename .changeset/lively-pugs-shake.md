Make auto-refresh and document regeneration report the failure that actually happened instead of a generic or misattributed one

Fizzy #2210. Three user-visible errors, none of which named its own cause.

**What the report turned out NOT to be.** The obvious reading was that the auto-refresh capability was gated twice and the two gates had drifted apart: the API tier resolved `FABRIC_FEATURE_LIVING_DOCS_REFRESH` at runtime while the masthead control resolved `NEXT_PUBLIC_FABRIC_FEATURE_LIVING_DOCS_REFRESH` — a different variable, a stricter parser, and inlined at build time so it could never change without a rebuild. Checked against the deployment, both were `true`, so both gates were open and neither explains the reported failure. The split gate is a real defect and is fixed here; it is not the cause of the report.

**The cause is still unknown, and that is the actual bug.** `onError` discarded the error entirely and showed one generic sentence, so a permission denial, a tenant mismatch, and a genuine server fault were all indistinguishable — to the reporter and to everyone who looked afterwards. Two weeks of investigation had nothing to work from but a string that named no cause. The settings surface now surfaces the server's own message, and a failed read is no longer collapsed into "the feature is off": a denial hides the control, a transport fault renders it inert and says so, and a failed background refetch leaves the control where it was rather than making it vanish mid-interaction. That is what will identify the remaining failure.

**The gate is no longer able to disagree with itself.** Both halves resolve through the shared feature-flag registry at runtime — the server via `isFeatureEnabled`, the client via the existing provider, which resolves server-side and rides the RSC payload, so there is no build-time inlining and no flash. There is no public client twin any more, and a test fails if one returns.

Two flags, not one, deliberately. The infrastructure already treated these as separate concerns and said so: the worker's variable is documented as "TRUE in every environment, prod included — this is deliberately NOT the rollout switch", because it is the pre-write kill switch that stops an unattended refresh mid-run. Merging that into the rollout gate would have turned an always-armed brake into a feature that launches on deploy. So `LIVING_DOCS_REFRESH` is the rollout on its own new variable, and `LIVING_DOCS_REFRESH_SWEEP` keeps the original variable and the original meaning. The sweep requires BOTH: the brakes must never be able to drive, or a document enrolled earlier would keep being rewritten while its owner could not see the control, let alone reach it. All six call sites became async, and a source-scanning guard fails the build when any is not awaited — a missing `await` yields a truthy Promise and silently opens the gate.

**Deploy note:** the rollout variable is a new name on purpose, so an environment that had the old one set does not silently inherit a launch. Set `FABRIC_FEATURE_LIVING_DOCS_REFRESH_ROLLOUT` wherever the feature should stay available.

**Regeneration blamed the document for a dependency it never reached.** Generation calls a separate agent service; when that call failed it was swallowed into a warning log and a fallback ran, and only the fallback's failure reached the user — phrased as "the document is too large for the configured model's output limit". The document that produced the report needed roughly a third of the budget the message accused it of exceeding. The primary failure is now recorded durably in the audit ledger under a registered taxonomy action, because an unregistered action is written as `audit.unknown_action` and drops out of the admin filter — being in the closed list is what makes it retrievable rather than merely durable. The surfaced error names that dependency without quoting its transport error, which renders verbatim to every project member. The truncation message reports the budget requested *and* the tokens actually produced, which is what separates a provider clamping below the request from a generation that ran away, and the fallback's ceiling now matches the agent's own: a stand-in that asks for less output than the thing it replaces turns an outage into a truncated document.

**Stored documents were accumulating quote corruption.** Every typographic quote in an affected document carried a leading tilde, in runs that doubled on each regeneration. No code in this repository produces the pattern and the editor's save round-trip is a fixed point, so this ships as content hygiene rather than a fix for a located bug. The normalization keys on a document-level signature rather than a local shape: a lone tilde before a quote is not evidence of anything — `~'90s` is prose, `Table~"A"` is a reference, and GFM accepts single-tilde strikethrough — so inferring corruption from shape alone would have rewritten legitimate text in documents that were never damaged. A doubled run is the signature. It runs at every seam that persists model-generated content, and at the activity boundary rather than only at the save, so the version snapshot and the document can no longer diverge.

A one-time repair fixes what was written before the guard existed: dry-run by default, one transaction per document with a compare-and-set on version AND content because not every writer bumps the version, a pre-repair snapshot attributed to the content's own prior author rather than to the repair, and documents carrying a proposal awaiting review are skipped rather than having that draft invalidated.
