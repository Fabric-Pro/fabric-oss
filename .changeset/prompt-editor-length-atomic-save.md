Prompt bodies are now capped at 50,000 characters, a rename and a body edit save together or not at all, and an empty or over-long body shows an inline error.

Fizzy #2250, three defects on the prompt edit screen. First, the only length rule on a prompt body was a minimum of one character (plus the 200,000-character abuse ceiling every free-text field shares), so a 100,000-character body saved cleanly and could then be bound as an organization default, riding every generation under it. A shared `PROMPT_CONTENT_MAX_LENGTH` (50,000; the largest seeded system prompt is roughly 22,600) now lives in `@repo/utils/prompt-content` and is enforced on every content-writing path: `prompts.create`, `prompts.update`, `prompts.version.create`, and the v1 `POST /prompts` route. The existing latest body is not re-checked against the limit on a metadata-only edit, so a legacy over-limit prompt can still be renamed. Second, the editor saved in two requests — `prompts.update` for metadata, then `prompts.version.create` for the body — so a rename plus a blank body committed the rename and then reported failure. `prompts.update` now accepts optional `content`/`changeNote`, validates the new body against the new format before any write, and writes the metadata and the version in one transaction (`updatePromptWithVersion`, which shares the version-insert-and-advance-bindings step with `createPromptVersion`); the editor makes that single call. Third, a cleared body disabled Save with no message at all and a whitespace-only body failed only in a global toast. The editor, the preview sheet and the AI enhancer now render the same message the server would return, inline under the textarea, with `role="alert"`, `aria-invalid` and `aria-describedby`, and the editor's character counter shows the limit.
