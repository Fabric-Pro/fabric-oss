Skills package a repeatable procedure, such as reviewing a pull request or preparing a weekly delivery brief. They contain instructions and may include reference files. A skill is not an autonomous agent, and sharing it does not grant access to its referenced documents, tools or connections.

## Find a skill

Open **Skills** in the left sidebar. Use **Organization**, **Built-in**, **Your drafts** and **Archived** to find the right material. Search and page through the catalog. Built-in skills are read-only; private drafts belong to their creator within the organization.

## Create a skill

The **Create skill** menu offers three starting points that lead to the same editor:

- **From conversation**: describe the procedure in the assistant. Send a message to request help, inspect the proposed instructions, then choose **Apply** to update your unsaved draft. Suggestions never save or publish automatically.
- **From scratch**: write when the skill should be used and its Markdown instructions. Give it a clear name and description.
- **From existing**: upload a `SKILL.md`, `.zip` or `.skill` package, or import a public GitHub repository. Review the available skills, instructions, files and warnings before creating a private draft. For private repositories, upload the selected package instead.

GitHub imports resolve to a specific commit. File imports show a content hash; if the package changes after review, preview it again. Supported packages use YAML frontmatter with `name` and `description`, followed by Markdown instructions. Extra metadata is shown as a warning rather than silently enabling runtime permissions.

Repository imports include files inside skill folders; unrelated repository files and links are excluded. Review the warnings for skipped candidates that exceed the supported limits.

Runtime files can be inspected or downloaded. Importing and previewing a package never runs its scripts. Uploads are limited to 8 MiB, with bounded extraction and individual file sizes; credential files, unsafe paths, symbolic links and corrupt archives are rejected.

## Review and share

Save creates a private organization draft. Publication and automatic discovery are separate choices:

| Availability | Who can find or use it |
|---|---|
| Private draft | Its creator, subject to current organization permissions |
| Published to members | Organization members with skill access; agents can use explicitly selected skills |
| Discoverable by agents | Published skills also appear in automatic skill discovery |
| Archived | Hidden from normal use; the creator can restore it as a private draft |

Publication does not expand source access. A person or agent still needs current permission for every referenced project, workspace, document and connection. Automatic discovery is a catalog setting, not a security boundary for a known, authorized reference.

If a save cannot be confirmed, another create is paused. Use **Check saved drafts** to open a matching draft or review the catalog before choosing another attempt; the original request may still finish.

Changes use version checks. If someone changes a skill while you are editing or inspecting a file, refresh before applying further changes. Permanently deleting a skill requires its creator's current delete permission and removes its linked memory copies.

## Use with agents and reports

Attach authorized skills to an agent or report template. Agent instances materialize instructions in `skills/{slug}/SKILL.md` and retain the source link. Execution and memory reads recheck current source access. A stale or unavailable source copy is withheld rather than returning old content after publication or permissions change.

To recover an outdated attachment, remove it and attach the current authorized skill again. Editing a linked memory copy does not silently turn it into an independent skill. Reports pin authorized skill instructions to the admitted execution and check current access before using them.

## Governance

Administrators can open **Organization settings → Skill governance** to restrict:

- creating skills;
- publishing skills to members;
- making skills discoverable by agents.

Each policy permits either members with the required role capability or administrators. Policies can restrict a role's existing permissions; they do not add permissions. Built-in roles and organization membership are enforced on the server. Group-specific rules are not currently available.

## API, CLI and MCP

The same operations are available through the API, SDK, CLI and MCP: catalog and detail reads, create/update, archive/restore, publication, assistance, import preview/create, runtime-file inspection and governance.

API keys require the declared scope **and** their creator's current permissions. Relevant scopes are `skills:read`, `skills:write`, `skills:publish`, `governance:read` and `governance:write`. A wildcard key does not bypass live membership or role checks. Runtime and project-bound credentials do not gain global authoring or governance privileges.

Use `fabric skills --help` for commands and `fabric skills import --help` for the reviewed import flow. Import creation requires the candidate and hash returned by preview; mutation commands do not automatically retry uncertain writes.
